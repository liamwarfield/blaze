## What was checked and found faithful

Dynamic execution:

- Winner and loser. `stop_branch` (`dynamic_spawn_strategy.rs:580`) keeps Java's order: cancelled
  check, compare-and-set of `strategyThatCancelled`, `otherBranch.cancel()`, the
  "could not be cancelled" case when the other future is already `SUCCESS`, then the wait on the
  loser's `done` semaphore. The semaphore is released in `call_impl_common` after the strategy has
  returned, or by the future's listener when the branch never reached `callImpl`
  (`branch.rs:403`). I walked the interleavings (loser not yet scheduled, loser between
  `start_running` and the `starting` flag, both branches reaching `stop_branch` together, loser
  already successful) and found no path where both branches pass their `lockOutputFiles`. No S1.
- A cancelled branch's stdout and stderr are not moved (`branch.rs:505`), as in `Branch.call`
  where only `ExecException` is caught. The sandbox of the cancelled branch is the runner's
  business and is unchanged in this range.
- `--experimental_dynamic_local_load_factor`: permits are `numCpus` when the factor is positive,
  else `jobs`; the float division in `update_load` and the truncation in `set_shrink_factor`
  match. `--dynamic_local_execution_delay` is applied only after a remote cache hit set the flag.
  `--experimental_dynamic_ignore_local_signals`: `exitCode - 128`, local branch only.
- Exclusions: `--experimental_dynamic_exclude_tools` runs tool-configuration spawns remotely
  only when both sides can execute, as in Java. There is no Xcode exclusion in Java at the pin
  (no `xcode` or `darwin` in `lib/dynamic/`), so nothing is missing.
- Error precedence: a non-interrupt failure of one branch cancels the other through the
  listener; `wait_branches` reports the local error first and cancels the remote branch; an
  interrupt of the waiting thread cancels both. The oneof in the failure detail keeps `Spawn`.
- The declared deviation (a thread per branch inside `exec`, `exec` returns after both threads
  ended) does not change which result wins.

Docker: container name (`--name <uuid>`), label `command_id=`, `-u uid:gid` (set only when
positive), `--network=none|host`, `--privileged`, `-e`, the exec root mount and `-w`, additional
mounts, image from the platform's `container-image` property with the `docker://` prefix, the

Old cgroups: mount pattern, v1 over v2 preference, the `blaze_<pid>_spawns[.slice]` directory,

## Findings

No S1.

### S2

- **E3-1. `Future.get` on a done branch ignores a pending interrupt.**
  Rust `dynamic/branch.rs:213-228`: the state is tested before the interrupt status. Java
  `Branch.getResults` is Guava's `AbstractFuture.get()`, which throws `InterruptedException` on
  entry when the thread is interrupted, even if the future is done. Input: the user interrupts
  the build at the moment the local branch completes. Java: `waitBranch` cancels the branch,
  `waitBranches` cancels the remote branch and `exec` throws `InterruptedException`. Blaze:
  `exec` returns the results with the interrupt status still set. Masked because the status
  stays set and the next interruptible point sees it. Fix: test `interrupted()` first in `get`.

### S3

- `tests/dynamic_spawn_strategy_test.rs:650`: one test ignored (needs a single-threaded
  executor, which the thread-per-branch port has no place for). Honest.
- `--debug_spawn_scheduler`: the `Event.info` lines are ported, the logger lines are skipped
  with `PORT` notes.
- Docker: never executed. `is_supported` and the verbose error text cannot be compared with the
  oracle on this machine.

### S4

- `docker_sandboxed_spawn_runner.rs:112-118`: an interrupt during `docker info` returns
  "unsupported" and sets the status again; Java lets the `InterruptedException` leave
  `isSupported`. `dynamic_spawn_strategy.rs:203`: a negative delay is clamped where
  `Thread.sleep` throws. `cgroups_info.rs:178`: other I/O errors carry Rust's `(os error N)` in
  a string that Java only logs.
