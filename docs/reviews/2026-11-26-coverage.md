## Findings

### S1

**V1. Every build without merged analysis and execution now fails with "not ported yet", with
or without coverage.**
Rust: `crates/blaze_runtime/src/commands/build.rs:2142-2151`. Inside the block that runs after
every successful (or `--keep_going`) execution phase, `if
!request.with_merged_analysis_and_execution_source_of_truth() { unported!("BuildView.update",
"coverage report artifacts without merged analysis and execution") }` is not guarded by anything
about coverage. `unported!` panics. At e8b79c0 this path had no such call and the function
handles the non-merged case throughout (`build.rs:1930`, `2053`, `2230`).
Java: `analysis/BuildView.java:656-659` adds
`memoizedGetCoverageArtifactsHelper(...)` to `artifactsToBuild`; without
`--collect_code_coverage` the wrapper is null and the set is empty
(`CoverageReportActionBuilder.java:241`), so nothing happens.
Input: `blaze build //pkg:ok --noexperimental_merged_skyframe_analysis_execution` (scenarios
31-33 of `scripts/w4/scenarios/incompat-toplevel`, and the non-Skymeld half of
`scripts/bep-matrix`). Bazel: builds. Blaze at 5f68157: panic at the end of execution. This is
the same class as the "plain `test` crashed" bug: a coverage hook that fires without coverage.
Not probed (suite running); root can confirm with one of the scenarios above.
Fix: in the non-merged path, do what `BuildView.update` does (compute the coverage artifacts
with the targets and build them with the rest), or at the least call `unported!` only when the
factory returns a wrapper, i.e. only when coverage was requested and collected.

### S2

**V2. The `_lcov_files.tmp` order is a real Bazel non-determinism, but it is not written down.**
With merged analysis and execution Java passes `buildResultListener.getAnalyzedTargets()` and
`getAnalyzedTests()` (`SkyframeBuildView.java:799-801`). Both are `ConcurrentHashMap.newKeySet()`
of `ConfiguredTarget` (`BuildResultListener.java`), and no configured target class overrides
`hashCode`, so the iteration order is the identity-hash order: it changes from one server to the
next. `coverage_lcov_files.tmp` (test `coverage.dat` files in test order, then baseline files in
target order) and `baseline_lcov_files.tmp` therefore have no reproducible order in Bazel when
there is more than one top-level target; Java's own comment says so
(`CoverageReportActionBuilder.java:230`). The implementer's statement is correct, and this
cannot be matched. What is fixed and must match: with one top-level target the order is fully
determined (its `coverage.dat` per shard/run in creation order, then its baseline nested set in
stable order); the choice of action owner and report generator (the comparator); the report
action's key, which hashes only the command line; and the final `_coverage_report.dat`, which
the merger sorts. The gap is that nothing at 5f68157 records this (no `// PORT:` note at
`build.rs:2154-2160` or in `coverage_report_action_builder.rs`, nothing in `docs/decisions.md`),
and a comparison tool that diffs the two `.tmp` files byte for byte will report noise. Fix: a
`PORT:` note at the call site and a decisions entry; comparisons of these two files compare
them as sets (or use single-target probes).

**V3. `coverage_environment` keeps the wrong position for a repeated key.**
`instrumented_files_info.rs:310-313` and `483-487` use `IndexMap::insert`, which keeps the
position of the first occurrence; `ImmutableMap.Builder.buildKeepingLast`
(`InstrumentedFilesCollector.java:319`) keeps the entry at its last occurrence. Masked: the only
readers today are `TestActionBuilder` (copies into a `TreeMap`) and the Starlark accessor, which
is `unported!`. It becomes visible when `InstrumentedFilesInfo.coverage_environment` is ported.
Fix: `shift_remove` before `insert`.

## Questions of the task, answered

- Filter heuristic: packages of the tests to run plus the packages of the labels in `tests` of
  each `test_suite`; `/internal`, `/public`, `/tests` stripped (one of them, in that order of
  test); first `javatests/` and then first `test/java/` at a segment start rewritten; nested
  prefixes dropped by `PathFragment.startsWith` over the sorted set (so the top-level package
  swallows everything and gives `^//`); joined with `[/:],^//`; the two INFO lines only when the
  set is not empty. All as Java. It runs only for `test`/`coverage` with
  `--collect_code_coverage` and no explicit `--instrumentation_filter`, as `TestCommand.doTest`.
- Test action under coverage: inputs are added in Java's order (runfiles tree, `$test_runtime`,
  setup script, XML generator, collect-coverage files-to-run, coverage support files, metadata
  files, `:coverage_support` files and data runfiles, `$collect_cc_coverage`,
  reported-to-actual-sources file, LCOV merger files-to-run, instrumented-file manifest,
  run-under executable); the environment is a sorted map, as Java's `TreeMap`, and goes into the
  key through `addStringMap`; `coverage.dat` and the `_coverage` tree are created per shard and
  run as in Java.
- Where the actions sit: the manifest action is registered inside `create_test_action` before
  the test runner actions; the reported-to-actual-sources write before it; the baseline action
  when the `InstrumentedFilesInfo` is built, and for Starlark rules through the thread's ordered
  action list (the `registrar`), so at the position of the `coverage_common` call. As Java.
- Report action: created once after execution from the analyzed targets and tests; null when no
  test has coverage params (the plain-`test` case), when all tests are incompatible, or with
  `--combined_report=none`; "Cannot generate coverage report - no coverage information was
  collected" when the artifact set is empty. As Java. A mix of tests with and without coverage
  params crashes in both (NPE in the comparator / `expect`).
- Post-processing spawn: without split post-processing there is none and `coverage.dat` is an
  output of the test spawn; with it, the spawn runs the collect-coverage executable alone with
  the test environment plus `TEST_SHARD_INDEX`, `TEST_TOTAL_SHARDS`, `TEST_NAME`,
  `IS_COVERAGE_SPAWN=1`, minus `RUNFILES_DIR`/`JAVA_RUNFILES`/`PYTHON_RUNFILES`; inputs in compile
  order (action inputs, expanded `_coverage` tree, manifest); output `coverage.dat`; fixed
  resources; failure handling (catastrophic, setup failure, timeout) and the log appending as
  Java; the missing-tree case gives the `LOCAL_TEST_PREREQ_UNMET` message.
- Nothing changes without `--collect_code_coverage`: true for the filter, the test action
  builder, the collector (`forward`, `forward_all`, `collect`), the report builder and the
  post-processing. Not true for the non-merged build path (V1).
