## Findings in the diff (none blocks the commit)

- **A-3 (S2). `compare` presents a legacy, unlocked run as a clean full-run total.** A run record
  without `complete` counts as complete (`compare:57`, `summarize:101`), and nothing records
  which harness measured a run. `blaze-v0.1.0` prints "mode suite, 237 of 237 default targets
  ran" with no mark. The header also hides how many runs were merged into a label (per target
  the latest wins, so selective reruns can replace failures) and `oom_kills`. Fix: store the
  scripts' sha256 and `locked: true` in each run record; print run count and OOM kills; mark a
  label with a legacy record or more than one run as not a single full run.
- **A-4 (S2). Completeness is the BEP's `lastMessage` only** (`run:288-289`). An interrupted
  outer build still ends with `lastMessage` (stored examples: `~/.cache/blaze/work/remote/
  bip-p2-*/run1/bep.json`, exit code `INTERRUPTED`). Its unfinished targets carry `aborted`,
  become `build_fail` and replace earlier results; `summarize` would accept the run. For an
  oracle baseline this shrinks the pass list. Fix: also require a `buildFinished` exit code
  other than `INTERRUPTED`, and map abort reasons that are not failures to `not_run`.
- **A-5 (S3). The process scan has two holes.** An unregistered `run` younger than 60 seconds is
  skipped rather than waited for (`ut_common.py:412`). An old script that starts after the check
  is never seen, and it resets the cache under the lock holder. After this commit old scripts
  exist only in older checkouts. Fix: wait while an unregistered script is young; scan again
  before releasing the lock and record what was found in the run record.
- **A-6 (S3). A killed `run` leaves its unit running.** SIGTERM or Ctrl-C ends `run`, releases
  both locks and kills only the `systemd-run` client. The next run then depends on the scan.
  A per-function `_inner` left behind keeps writing into the label's directory without the label
  lock. Fix: name the unit and stop it on exit.
- **A-7 (S3). The log fallback lets the last line win** (`run:246`) and takes any
  `PASSED: test_x` or `[ OK ] A.b` line, including one printed by an inner test in a dumped log.
  A fail could become a pass, or a name appear that the script does not define. Not exercised
  today. Fix: a fail wins; accept only names the source defines.
- **A-8 (S3). `reparse` rewrites results.json without a trace** in `runs`. The accepted label
  was reparsed in place before this audit, with the only backup in a session scratchpad. Fix:
  append a `reparsed` record (time, scripts' sha256) and keep the previous file beside it.
- **A-9 (S4).** A pager or editor opened on `scripts/upstream-tests/run` blocks every run after
  60 seconds (the scan matches the path in argv). `compare` and `summarize` do not recognise the
  legacy `--test-filter=F` form that `run`'s `label_mode` does. `summarize --mark-flaky` writes
  results.json without the label lock. The manifest is read before the lock. `prepare` trusts
  the wrapper's exit status, which is 0 when the wrapper is terminated (B2). `inner` loses a
  negative exit in `max(worst, rc)`.
- **A-10 (S3, baseline, known).** The oracle baseline is built from four runs, two with OOM
  kills (1 and 4). `bazel_proto_library_test` is flaky for that reason and so outside what Blaze
  is held to (the README says so). `summarize` should flag runs with OOM kills.

## Ruling on per-function results

- The progress measure stays the suite-mode count against the suite-mode baseline. A
  per-function count is never added to it and never replaces part of it.
- Until the oracle has its own per-function baseline (the same mode, two runs, flaky names
  removed, written by `summarize` to its own file), per-function results are diagnostic only.
  They may appear on a separate line next to the suite total with this wording: "run alone (one
  invocation per function, sharding off, function names read from the sources; not how upstream
  runs them): M of the K functions that did not report in suite mode pass". K and the label are
  named. No percentage of 2,878.
- Once that oracle baseline exists, a second total may be reported, per-function against
  per-function, under the name "per-function", beside the suite total and never summed with it.
- Reasons. The mode changes what is tested: no shared server or workspace state between the
  functions of a script, no sharding, and only functions the regular expressions find in the
  target's own sources (functions from sourced files are never run and count as absent).
  Removing the XML-writer flaw is legitimate for diagnosis, but real Bazel would lose the same
  functions if it failed the same way, so the suite count is the like-for-like figure.

## B1. D12: fresh server or warm server (S2)

- **What is true for the oracle.** `scripts/oracle/record` deletes the output user root, then
  runs every command with the same startup options on one server and shuts down once at the end
  (`record:323-401`). The build is the second command; `mod graph` starts the server
  ("Starting local Bazel server" is in `raw/mod_graph.stderr`, not in `raw/build.stderr`). The
  README sentence "The build runs right after `mod graph`, on a fresh server" is false. It is
  true only with `--surfaces build`.
- **What is true for Blaze.** No server: every command is a new process with empty memory. Blaze
  prints the "Starting local Bazel server" line on every command; `_STDERR_KEEP` drops it, so
  the referee does not see that.
- **Effect on the accepted scores.** The open item "1 extra stderr line on re2" is this
  asymmetry. The oracle prints `WARNING: …/MODULE.bazel:7:7: The attribute 'compatibility_level'
  … is a no-op` during `mod graph` and not again in the build on the warm server; Blaze prints
  it in both commands. A correct Blaze behind a persistent server would match. The score files
  stay as recorded. Two cautions: no implementer may "fix" that line by suppressing the warning
  in a cold process; and the allow-listed `buildGraphMetrics` counters hide other cold-against-warm
  differences. Query, cquery and aquery surfaces come from stdout and are not affected.
- **Required in the referee before package S5.**
  1. Rule which protocol is the reference and make the README and the script agree. My
     recommendation: keep the order, and record the server state as a fact rather than assume it.
  2. Per command, store the server pid before and after (pid file or `info server_pid`) and
     whether the client started a server. `compare` fails a surface whose commands ran in
     different server states on the two sides.
  3. Add a cold build (a `shutdown` between `mod graph` and the build, on both sides) and keep
     the warm sequence as its own surface, so the same Blaze is judged both ways. This changes
     the reference recording (`--force`, protected, oracle-against-oracle checks after it).
  4. Compare the server-start line instead of dropping it, record the `shutdown` exit code
     (`record:401` discards it) and check that no server of the label is alive after it.
  5. Check that `kill_servers` finds a Blaze server (`<root>/*/server/server.pid.txt`) and that
     the daemonized server stays inside the memory scope.
  6. Score the last accepted label again under the changed referee before the first comparison.
