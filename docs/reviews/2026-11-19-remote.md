# Review: remote caching and execution (`blaze_remote` and its integration)

- Date: 2026-11-19. Reviewer: remote reviewer (Fable 5.2), with five Fable 5.2 sub-reviewers
  (digests/protos, transport/retries, cache clients, build-without-the-bytes/integration, tests).
- Commit read: `ef66f55` (Checkpoint 8), from a `git archive` export; the live tree was not read.
- Method: Rust read against the pinned Java (Bazel 9.3.2). Read-only: nothing was built, run or
  edited. Every finding below is from reading both sides; none was reproduced by running a build.
  Scenarios are reasoned from the code.
- Paths: Rust relative to `crates/`; Java relative to
  `src/main/java/com/google/devtools/build/lib/`.

## Verdict: STOP

Blocking findings: R1 to R6 (S1). R7 (S2, security) should be fixed in the same round.

The transfer and digest layers are in good shape: no byte-level digest deviation and no download
path that skips a check Java performs were found. The blocking problems are all in the
integration: Blaze has no action file system, and the places where Java relies on
`RemoteActionFileSystem`, on `OutputService.finalizeAction`, on the connection factory's
capabilities gate and on thread interruption are not covered. Four of the six S1 are reachable
with default flags (`--remote_download_outputs=toplevel` is the default) on projects that have
tree artifacts, symlink outputs or generated executables, none of which brotli has.

## S1: wrong behaviour on valid input

### R1. Tree artifact outputs lose their remote-only children (silent empty tree)

- Rust: `blaze_sky_exec/src/skyframe_action_executor.rs:1702`
  `construct_tree_artifact_value_from_filesystem` enumerates only the local directory
  (`TreeArtifactValue::visit_tree`, :1724). `remote_execution_service_download.rs:1436-1472`
  injects the files of an output directory that are not downloaded into `RemoteOutputTree` by
  path (`blaze_exec/src/exec/action_execution_context.rs:202`), which has no directory listing.
- Java: `remote/RemoteExecutionService.java:1334-1358` injects into the action's
  `RemoteActionFileSystem`; its readdir and stat merge the remote output tree
  (`remote/RemoteActionFileSystem.java:667-706`), so `ActionOutputMetadataStore` sees the children.
- Scenario: default flags with any cache (`--disk_cache` is enough). A non-top-level action with a
  tree output is a cache hit, or runs remotely. The tree root exists locally (created before
  execution), so the output check passes and the action's `TreeArtifactValue` has zero children.
  Consumers get an empty directory and no error; a remote consumer is sent an empty input
  directory.
- Fix: build tree values from the injected entries too (a per-directory index in the remote output
  tree), or fail loudly when an output directory has injected children.

### R2. `finalizeAction` is never called: top-level symlink outputs to remote-only files dangle

- Rust: `blaze_remote/src/abstract_action_input_prefetcher.rs:773` `finalize_action` has no
  caller; `blaze_sky_exec/src/skyframe_action_executor.rs:796` says "finalizeAction is a no-op".
- Java: `skyframe/SkyframeActionExecutor.java:1340-1343` calls `outputService.finalizeAction`;
  `remote/RemoteOutputService.java:170-174` forwards to
  `remote/AbstractActionInputPrefetcher.java:849`, which downloads every output whose metadata is
  remote and which the `RemoteOutputChecker` wants.
- Scenario: default flags, warm cache, `blaze build //:t` where an output of `t` is created by
  `ctx.actions.symlink` (or a `_solib_*` link of a dynamically linked `cc_binary`/`cc_test`) and
  points at a file that is not itself a top-level output. The link is created locally, its target
  stays remote, the build reports success and `bazel-bin` holds a dangling link.
- Fix: call `finalize_action` after the output check when a prefetcher is registered.

### R3. The server-capabilities check does not gate RPCs and its result is discarded

- Rust: `blaze_remote/src/remote_module.rs:1041-1046` starts the check in a detached task and
  drops the result (`let _ =`); :1000-1006 reports all errors but the last and returns the last
  as an `Err` that nobody reads. `grpc/channel.rs:436` `start_call` never awaits the capabilities.
  The two blocking readers ignore errors (`remote_execution_service.rs:1305`,
  `combined_cache.rs:371`). The `RemoteExecutionCapabilitiesException` branches at
  `remote_spawn_cache.rs:164` and `remote_spawn_runner.rs:889` cannot be reached from an RPC.
- Java: `remote/GoogleChannelConnectionFactory.java:86-104` creates every connection through
  `serverCapabilitiesSingle.map(...)` when the requirement is not NONE, so each RPC fails with
  `RemoteExecutionCapabilitiesException` (:167). `remote/RemoteSpawnCache.java:189-197` turns it
  into "Failed to query remote execution capabilities" unless both `--remote_local_fallback` and
  `--incompatible_remote_local_fallback_for_remote_cache` are set; `RemoteSpawnRunner.java:591`
  does the same. Upstream's `remote_execution_test.sh:86,118,959` expects that text and a failed
  build.
- Scenario A: `--remote_cache=grpc://unreachable:1` or a server that rejects GetCapabilities
  (missing credentials). Bazel fails the build; Blaze prints "WARNING: Remote Cache: ..." and
  succeeds.
- Scenario B: a server that lacks what the flags need (`--remote_cache_compression` without ZSTD,
  digest function mismatch, unsupported API version, `exec_enabled=false`). Bazel fails every
  action with the capability error. Blaze prints nothing when there is one error and keeps sending
  RPCs.
- Fix: await `get_server_capabilities_async()` in `start_call` for every method except
  GetCapabilities when the requirement is not None. Port `RemoteModuleTest.testVerifyCapabilities_*`.

### R4. An interrupt does not cancel in-flight RPCs, backoff sleeps or background uploads

- Rust: `blaze_remote/src/runtime.rs:34` `get_from_future` is a bare `block_on`;
  `retrier.rs:162` sleeps with `std::thread::sleep` and :373 drops the `Thread.interrupted()`
  check; `remote_retrier.rs:39` treats CANCELLED as always transient;
  `remote_execution_service.rs:240` `shutdown_now` only stops new submissions and :2068 then joins
  every upload thread; `util/async_task_cache.rs:283` `shutdown_now` cancels nothing. The stated
  reason ("Blaze has no thread interruption") is stale: `blaze_shell::thread_interrupt` exists
  with `add_interrupt_listener` for exactly this, and `remote_spawn_runner.rs:849` already reads
  the flag. No listener is registered anywhere in `blaze_remote`.
- Java: `remote/util/Utils.getFromFuture` cancels the future on `InterruptedException`;
  `Retrier.java:262` and `RemoteRetrier.java:54` honour the flag;
  `RemoteExecutionService.java:2119-2125` interrupts the uploads.
- Scenario: `--remote_executor=...`, Ctrl-C (or a first failure without `-k`) during a long remote
  action. Execute/WaitExecution have no deadline, so the action thread stays blocked until the
  server ends the stream; `after_command` then waits for every background upload. The remote
  action is never cancelled.
- Fix: in `get_from_future`, select on the calling thread's interrupt (drop the future, return
  `errors::interrupted()`); make the sleeper interruptible; restore both flag checks; cancel
  running uploads in `shutdown_now`. Un-ignore `retrier_test.rs:221`.

### R5. In-process actions read remote-only files from the local disk

Java gives every action a `RemoteActionFileSystem`; Blaze has none, and three in-process readers
go to the local path.

- (a) `blaze_exec/src/analysis/actions/symlink_action.rs:144-159`
  `maybe_verify_target_is_executable` stats the local path. Java
  (`analysis/actions/SymlinkAction.java:302-323`) stats through the action file system, which
  answers from remote metadata. Scenario: a `sh_binary` whose `srcs` is a generated file, used as a
  genrule tool (so nothing of it is top-level), warm cache, default flags: Blaze fails with
  "'X' is not a file", Bazel succeeds.
- (b) `local_template_expansion_strategy.rs:75` reads the template from `Artifact.getPath()`. Java
  reads through `RemoteActionFileSystem.getInputStream` (:382), which downloads first. Scenario:
  `ctx.actions.expand_template` on a generated, non-top-level template, warm cache.
- (c) `blaze_exec/src/exec/standalone_test_strategy.rs:731` checks `xml_output_path.exists()`
  locally; Java (`exec/StandaloneTestStrategy.java:857`) sees the injected `test.xml`. Scenario:
  `blaze test --remote_download_outputs=minimal` with a cached test that wrote its own XML: Blaze
  runs the XML-generating spawn and writes a generic local `test.xml`, while the metadata store
  keeps the injected remote digest for that path.
- Fix: prefetch, or consult input/output metadata, before each in-process read; (c) must consult
  the remote output tree.

### R6. A blob lost from the remote cache gives the wrong failure and never recovers

- Rust: `blaze_exec/src/exec/action_execution_context.rs:110-123` maps every prefetch error to
  "Exec failed due to IOException". `ExecutionOptions.remote_retry_on_transient_cache_error`
  (`--experimental_remote_cache_eviction_retries`, default 5) is never read.
- Java: `exec/AbstractSpawnStrategy.java:273-299` turns a `BulkTransferException` into lost
  inputs; without rewinding the build exits 39 and `runtime/BlazeCommandDispatcher.java:851`
  retries it, with `knownMissingCasDigests` kept so the stale action result is not accepted again.
- Scenario: an action-cache hit references an evicted CAS blob and a local action needs it. Bazel
  retries and succeeds. Blaze fails with a different exit code; a rerun accepts the same stale
  entry again because the set of known missing digests does not survive the process.
- This is fail-closed (no wrong output). The other lost-input path is loud
  (`common/bulk_transfer_exception.rs:56` `unported!`).
- Fix: port the catch, exit 39 and the retry; persist or rebuild the missing-digest knowledge.

## S2: deviations masked today

### R7. (security) The remote output tree is build-wide and accepts paths the action does not own

- Rust: `remote_execution_service_download.rs:1388` and :1464 inject every file an ActionResult
  lists and that is not downloaded; `RemoteOutputTree` is one map for the whole build; the output
  metadata store consults it first for any artifact
  (`skyframe_action_executor.rs:1791-1792`), before the local file.
- Java: the injection goes into the `RemoteActionFileSystem` of that one action, and only that
  action's declared outputs are read back.
- Scenario: a cache entry for action A (the action cache is not content-addressed; anyone who can
  write it can craft this) lists an extra `output_files` entry at the exec path of action B's
  output with a digest of the attacker's choice. A is a cache hit early in the build. B later runs
  locally and writes its real output, but its metadata is taken from the tree: B's output is
  recorded as a remote file with the attacker's digest. Remote consumers of B are sent that digest
  in their input root. In Bazel the extra entry is ignored in this mode.
- Fix: inject only paths that are declared outputs of the injecting spawn (or under its declared
  output directories), or scope the injected metadata to the action.

### R8. Proto strings bypass the strings seam in the Merkle tree and on the download path

- Rust: `merkletree/merkle_tree_computer.rs:1319-1323` `internal_to_unicode` is a hard
  `s.to_string()` (used for node names and symlink targets at 809, 827, 872);
  `remote_execution_service_download.rs` has ten "StringEncoding identity" sites (output paths,
  Tree node names, symlink targets). Every other site in the crate goes through
  `strings_are_internal()`.
- Java: `MerkleTreeComputer.java:629,639,659`; `RemoteExecutionService.java:1086-1200`.
- Correct today because `STRINGS_ARE_INTERNAL` is false. After the switch ruled on 2026-11-18,
  an input `é.txt` is hashed as C3 83 C2 A9 where Bazel writes C3 A9: the input root digest
  differs for any non-ASCII path, and downloaded non-ASCII outputs land under the wrong name.
  No test on either side covers a non-ASCII tree.
- Fix: use the seam helper at these sites; add a non-ASCII tree test run on both sides of the seam.

### R9. `argv[0]` is not rewritten for a Windows execution platform, silently

- Rust: `remote_execution_service.rs:1079-1088` applies the host policy ("Windows only").
- Java: `RemoteExecutionService.java:312-316` keys the policy on the execution platform's OS
  constraint, not the host.
- Scenario: Linux host, remote executors on Windows: the Command digest differs from Bazel's and
  `.bat` tools do not start. `blaze_exec`'s `PlatformInfo` carries no constraints, so the case
  cannot be detected. Fix: carry the OS constraint, or `unported!` for a Windows exec platform.

### R10. Upload resume at the end of a blob panics

- Rust: `chunker.rs:287` (`data_mut().finished()`) reached from `byte_stream_uploader.rs:509`.
- Java: the same NPE happens inside the gRPC on-ready handler (`ByteStreamUploader.java:386-443`),
  where it becomes CANCELLED "Failed to call onReady.", is retried and ends as an `IOException`.
- Scenario: all chunks sent, Write fails with UNAVAILABLE, QueryWriteStatus answers
  `committed_size == size, complete=false`. Blaze panics on the action thread or on a background
  upload thread. Fix: map unchecked failures of seek/next in `Writer::write` to that status, as the
  port already does for the sibling case at :513-518.

### R11. `AsyncTaskCache` semantics differ beyond what the ignored tests disclose

- Rust: `util/async_task_cache.rs:267-275` `await_termination` returns when nothing is in
  progress even in state ACTIVE (Java blocks until TERMINATED); :50-73 and :220-234 cancel the
  shared task when its first caller is dropped and a waiter restarts it from byte 0 (Java keeps
  one execution while any subscriber remains). The cancel difference is disclosed by ignored
  tests; the termination difference is not. `remote_action_input_fetcher_test.rs:1936-1943` was
  adapted to pass with the Blaze behaviour (Java asserts the shared download is not cancelled,
  `ActionInputPrefetcherTestBase.java:1065`).

### R12. The build event artifact uploader is silently missing

- Rust: `remote_module.rs:831` is a comment. Java: `RemoteModule.java:905-916` installs the
  ByteStream uploader whenever a gRPC cache is set.
- Scenario: `--remote_cache=grpc://... --build_event_json_file=x`: Bazel uploads and emits
  `bytestream://` URIs; Blaze emits local file URIs. `--remote_build_event_upload` and
  `--remote_bytestream_uri_prefix` are accepted and ignored. Fix: `unported!` when BEP and a gRPC
  cache are both set, or port it.

### R13. Flags accepted and ignored

- `--remote_max_connections`, `--experimental_remote_max_concurrency_per_connection`
  (`remote_module.rs:555`, comment only; one HTTP/2 connection). Behind a proxy that caps streams
  at 100, long Execute streams can starve cache calls inside their `--remote_timeout`.
- `--experimental_remote_cache_lease_extension` (no reader; Java `RemoteModule.java:1259-1296`).
- `--experimental_disk_cache_gc_max_size` / `_max_age` / `_idle_delay` (`remote_module.rs:425`,
  comment only). This equals Bazel `--batch`, but a user who sets a limit gets an unbounded cache
  and no message; the ported collector is dead code.
- docs/remote.md rule 6 asks for `unported!` (or at least a warning) in each case.

### R14. Channel construction fails eagerly with a guessed exit code

- Rust: `remote_module.rs:686-692` maps any `new_channel` error to exit 37 at startup.
- Java: the channel is built lazily (`GoogleChannelConnectionFactory.java:87`); a bad
  `--tls_certificate` or proxy is a per-action warning for cache-only builds. Fails closed.

### R15. `afterCommand` and setup error texts and exit codes are invented

- Rust `remote_module.rs:853` "Failed to close the remote gRPC log: ..." vs Java
  `RemoteModule.java:1166-1169` "Partially wrote RPC log file" with LOCAL_ENVIRONMENTAL_ERROR.
- Rust :861-871 turns a temp-dir deletion failure into an error; Java :1156-1160 ignores it.
- `create_exit_exception` (:158) drops Java's explicit exit code ("Failed to delete stale
  downloads": 34 in Blaze, 36 in Java, `RemoteModule.java:1225`).
- `after_command` is skipped when an `unported!` panic unwinds the build, so background uploads
  and the gRPC log are dropped.

### R16. Action execution salt is empty without remote options (root's cross-check)

- Java: for every command that has `RemoteOptions`, `RemoteModule.setup` leaves a placeholder
  provider when nothing remote is enabled (`RemoteModule.java:526-531`), so `executorInit` does not
  return early (:1244) and always sets the salt (:1308):
  `computeActionExecutionSalt` = fingerprint of `isRemoteCacheEnabled()` and the default exec
  properties (:1312-1332). Without remote options the salt is the hex digest of `(false, {})`, not
  the empty string. `ExecutorBuilder.getActionExecutionSalt` returns "" only when no module set it.
- Rust: `blaze_runtime/src/commands/build_remote.rs:79` returns `None` when no remote option is
  set, and `blaze_buildtool/src/buildtool/execution_tool.rs:420-429` then uses "" (the comment
  there says so). With a remote option, `remote_module.rs:303` computes Java's value.
- Reuse between setups: confirmed equivalent. A build without a cache uses "" in Blaze and
  `fp(false, {})` in Java; a build with any cache (`--disk_cache`, `--remote_cache`,
  `--remote_executor`) uses `fp(true, props)` in both. The two salts differ on both sides, and the
  salt is part of the entry digest (`actions/cache/ActionCache.java:413`,
  `blaze_exec/src/actions/cache/action_cache.rs:676`), so entries are never reused across the
  boundary in either direction, as in Java.
- What differs: (1) changing `--remote_default_exec_properties` without a cache invalidates the
  local action cache in Java and not in Blaze (no effect on outputs, a difference in what
  re-executes); (2) the entry digests of a no-remote build differ from Bazel's, so an action cache
  written by Bazel is never hit by Blaze and the reverse (re-execution, the safe direction).
- Fix: use `compute_action_execution_salt(Some(options))` whenever the command has `RemoteOptions`.

### R17. Remote metadata is never stored or trusted across invocations

- Rust: `execution_tool.rs:321` `set_store_output_metadata(false)`;
  `skyframe_action_executor.rs:1012` `TrustLocalOnly`. `RemoteOutputChecker::should_trust_metadata`
  and the TTL check are dead code; the expiration is stamped
  (`remote_execution_service_download.rs:1327`) and never read.
- Java: `RemoteOutputService.shouldStoreRemoteOutputMetadataInActionCache` is true.
- Safe (a deleted or expired output is always noticed), but a null second build re-checks the
  cache for every action with a remote-only output where Bazel reports action-cache hits.

## Verified correct (the parts the brotli evidence cannot show)

- Downloads: every ByteStream read is verified over the running hash across resume attempts
  before the bytes leave the temp file (`--remote_verify_downloads`); with verification off the
  size is checked. A size-limiting stream under the zstd decoder bounds extra bytes and
  decompression bombs by `digest.size_bytes`. Write-through to the disk cache goes temp file,
  verify, fsync, rename. Disk cache reads are unverified, exactly as in Java.
- Disk cache layout, temp protocol, mtime refresh, AC integrity walk and the GC's fcntl lock match
  Bazel 9.3.2.
- Uploads: only `SUCCESS` with exit code 0 is stored; `no-cache`, `no-remote`, `no-remote-cache`,
  `no-remote-cache-upload`, `--remote_upload_local_results` and
  `mayModifySpawnOutputsAfterExecution` are honoured as in Java; committed-size checks and the
  UploadManifest symlink rules match.
- Action, Command, Directory, Tree and salt bytes: no deviation found; Java field order;
  comparators equal Java's in both string models; the three golden digests of Java's tests are in
  the Rust tests.
- TLS is on unless the target starts with `grpc://` or `unix:`, with no plaintext fallback; trust
  roots are webpki only, as ruled; header scoping, RequestMetadata, message-size limits, retriable
  code sets, backoff and the Execute/WaitExecution loop match. The gRPC log does not record
  authorization headers.
- `RemoteSpawnCache.lookup`, `RemoteSpawnRunner.exec` and `downloadOutputs` follow Java branch by
  branch, including the catch order and the texts.
- No `unsafe` in the crate or the integration file; nothing keyed to brotli, re2, localhost or the
  test worker.

## For a ruling (not findings against the port)

The download path trusts the server exactly as far as Bazel 9.3.2 does, and the lead marked each
place with a `SECURITY:` comment. Java at the pin does not confine these, and neither does Blaze:

- output symlink paths and targets (`createSymlinks`, `RemoteExecutionService.java:950`): a symlink
  can be created outside the exec root, with an absolute or `..` target;
- Tree node names: a file can land anywhere under the exec root, not only under its tree root (a
  path outside the exec root is a crash in both);
- `ExecuteResponse.server_logs` keys (`RemoteExecutionService.java:2075`): `..` escapes the log
  directory;
- inlined `OutputFile.contents` and inline stdout/stderr are not compared with their digests.

Root should record whether Blaze stays byte-for-byte with Bazel here or hardens beyond it. If it
stays, R7 is the one place where Blaze is weaker than Bazel and should be closed first.

## Unverified suspicions

- tonic may treat a 200 response that ends without trailers as a clean end where grpc-java raises
  an error and Bazel resumes; Blaze would then fail with a digest mismatch that is not retried
  (integrity holds).
- `errors::is_interrupted` is `kind == Interrupted`, so an EINTR from a file read on FUSE/NFS would
  look like a build interrupt.
- The source-directory memo in `merkle_tree_computer.rs:122-125` is keyed by value and never
  purged; harmless with one command per process, a stale-digest risk once there is a server.
- A `force=true` upload can join a finished no-op shared task (`remote_execution_cache.rs:593`).
