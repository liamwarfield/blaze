## Findings

### F1 (S1, daemon mode; blocking). Nothing releases the build arena, and per-command state was written to depend on that release

`blaze_util::build_arena::release_if_unused` (`crates/blaze_util/src/build_arena.rs:178`) has
no caller outside its own unit tests (grep over the repository). The module comment says "only
the server makes" the call "once a command has completely ended"; the server does not. STATUS
says "release not switched on", but three places state the opposite as a fact and rely on it:

- `crates/blaze_sky_loading/src/package_progress_receiver.rs:1-18, 57-70`: the receiver is a
  process static that resets itself "at the first use in a new generation of the build arena
  ... the server releases the arena after every command". The generation never changes, so the
  state is never reset on the build path (`blaze_sky_top/src/skyframe_executor.rs:968-972`
  posts `LoadingPhaseStartedEvent` without a reset; only `query` resets explicitly,
  `blaze_query/src/commands/query_command.rs:294`).
  Java: `skyframe/SkyframeExecutor.java:1742` `packageProgress.reset()` in
  `preparePackageLoading`, once per command.
  Input: one daemon, `blaze build //...` twice. The second command's first progress line is
  `Loading: 89 packages loaded` where Bazel prints `Loading: 0 packages loaded`: recorded by
  the implementer in `soak/base-brotli-build/report.tsv` rows 2-12 (and `base-re2-build`: 115)
  against `soak/oracle-brotli-build/report.tsv`; the build with the release on
  (`soak/arena1-brotli-build`) prints 0. Second input, from the code only: `build //a:x` then
  `build //b:y` on one daemon. `completed_set` still holds the first command's packages, so
  they are not counted again, and `packages_completed` still holds the first command's total:
  the second command's `(N packages loaded, ...)` is the count of distinct packages over both
  commands, not the packages the second command loaded.
- `crates/blaze_sky_top/src/execution_seam.rs:849-871` (`TopLevelAspectDrivers`, "which the
  server releases after every command") and
  `crates/blaze_sky_analysis/src/dependency_resolver.rs:668-688` (`Loaded`, "the server
  releases it after every command, as Java's graph reset drops the BZL_LOAD node"). I found no
  wrong output from these two today (the first is overwritten per build, the second only
  memoizes bundled builtins), but both comments are false at this commit.

The same missing call is the memory growth: see "Known open problems" below.

Fix expected: per-command state must not hang on the arena's generation. Reset
`PackageProgressReceiver` where Java does (the per-command sync that creates the executor),
keep the other "State" slots per executor or reset them at command start, and correct the
comments. Then switch the release on in the server after `afterCommand` (with the lease count
at zero) and show a two-command sequence against the oracle.

### F2 (S2; blocking). `afterCommand` drops the event-bus teardown silently, and the command's event bus is in a reference cycle

Java `runtime/BlazeRuntime.java:810` `env.getBlazeWorkspace().clearEventBus()` and `:832`
`env.getReporter().clearEventBus()` (`events/Reporter.java:148`). Rust
`crates/blaze_runtime/src/dispatcher.rs:898-991` (`after_command`) has neither call and no
`// PORT:` line for them; `Reporter::clear_event_bus` exists
(`crates/blaze_events/src/reporter.rs:146`) and has no caller.

In Java this is hygiene (the collector frees cycles). In Rust it is a leak:
`crates/blaze_runtime/src/commands/build.rs:657-668` registers an
`ExecutionProgressReceiverSetup` on the command's `CommandEventBus` and hands it
`env.get_event_bus().clone()`, which it stores as a strong `Arc`
(`crates/blaze_buildtool/src/buildtool/execution_progress_receiver.rs:161-163`).
`CommandEventBus` (`command_environment.rs:898-907`) can only add subscribers. So bus →
subscriber → bus, and after every `build` that executes the bus and every subscriber on it
stay allocated for the life of the process: the `ExecutionEventCollector`, the
`UiEventSubscriber` with its `UiEventHandler`, state tracker and the command's `OutErr` (the
`RpcOutputStream`s), the `BepSubscriber` with its streamer and metrics, the
`BuildResultListener`, the `BuildConfigurationCreatedCallback`. New since the baseline (the
field is not in ef66f55). `TestCommandSupport` and `TestResultAggregator` also store the bus
(`blaze_buildtool/src/runtime/test_command_support.rs:145`, `test_result_aggregator.rs:27`);
I did not trace whether their subscriber closes a second cycle.

Masked today because a process runs one command. In a daemon it is one leaked object graph per
build; it is my candidate for part of the leak "outside the arena" (below).

Fix expected: port the two `clearEventBus` calls, with `CommandEventBus` dropping its
subscribers there, or hold the bus weakly in subscribers; then re-measure the soak.

### F3 (S2). A panic on a thread nobody joins does not end the server

Java: the default uncaught exception handler is `BugReport.handleCrash(..., halt)` for every
thread (`BlazeRuntime.java:1610`): exit code file, `blazeShutdownOnCrash`, halt 37; the client
prints "Server terminated abruptly". Rust: the hook only records
(`crates/blaze_runtime/src/bugreport.rs:131-158`); the halt handler runs only for the threads
`blaze_server` starts (`uncaught_exception.rs:49`) and where a panic reaches the command
boundary. The module comment says so ("such a panic stays recorded and ends only its thread",
`bugreport.rs:18-20`), but the behaviour is neither Java's nor a loud failure. Thread spawns
outside the two crates exist in about 40 files (grep; not each opened), among them
`blaze_events/src/ui.rs`, `blaze_bep/.../file_transport.rs`,
`blaze_util/src/profiler/json_trace_file_writer.rs`,
`blaze_exec/src/worker/worker_lifecycle_manager.rs`,
`blaze_runtime/src/collect_local_resource_usage.rs`. A panic there leaves a server that keeps
serving, and a command that waits on that thread keeps the command lock, so every later
client waits in "Another command (pid=N) is running" (risk 6 of the plan; decision 2026-11-19
ranks a worker-thread panic that hangs the process S1). I did not construct such a hang, hence
S2. Fix expected: one spawn wrapper for detached threads that hands an escaping panic to the
installed uncaught handler, except where the Java counterpart keeps the exception in a future.

## What I checked and found faithful

- **Command lock and concurrent clients** (`dispatcher.rs:174-231` against
  `BlazeCommandDispatcher.java:235-274, 333-338`): both texts, the 500 ms wait, `ERROR_OUT`
  with `ANOTHER_COMMAND_RUNNING`, wait time forced to 0 on the first try, idle results taken
  after the lock, release on return and on unwind, the shutdown reason for later commands. An
  interrupt during the wait leaves `exec` as `InterruptedException` and gives "Command
  dispatch interrupted" with an empty command id, as `GrpcServerImpl.java:639-643`.
- **Cancellation and interrupts.** Client: `CancelThread`, pending cancel until the command id
  arrives, 10 s deadline, messages, third SIGINT killing the server and `_exit(1)`, SIGQUIT
  forwarded, SIGWINCH (`signal_handler.rs:118-170`, `blaze.rs:896-1031` against
  `blaze.cc:1844-1944`, `blaze_util_posix.cc:144-193`). Server: `doCancel` interrupts the
  command's thread and starts the watcher; each command runs on a fresh `grpc-command-N`
  thread, so the interrupt status cannot reach the next command
  (`grpc_server_impl.rs:373-380`, `interrupt.rs:41-52`). The sticky `COMMAND_THREAD` flag the
  plan listed is gone.
- **Output streaming**: one bounded channel per call, so stdout and stderr keep their order;
  8192-byte chunks; the writer blocks on the client's flow control and is not woken by an
  interrupt; a cancelled stream sets the writer's interrupt status
  (`grpc_server_impl.rs:127-251`, `grpc.rs:31-61` against `GrpcServerImpl.java:161-306`).
- **stdout/stderr redirection**: `SystemPatcher` is ported and closed on return and on unwind
  (`io.rs:281-312`, `dispatcher.rs:444, 624, 1105-1112`); the direct-output sites of the
  plan's table now go through the patched streams or are startup, crash or batch paths.
- **Server death and exit codes**: abrupt-exit and OOM files, "Server terminated abruptly",
  "Server finished RPC without an explicit exit code", bad cookie (37), 36 after a broken
  pipe then SIGPIPE re-raised, `termination_expected` wait and kill (`blaze.rs:756-819,
  2682-2748` against `blaze.cc:2135-2205, 1421-1449`). Pid file watcher halts 37 without
  hooks; SIGTERM and SIGHUP run the hooks and exit 128+n.
- **Panic inside a command**: caught at `exec_exclusively` (`bugreport.rs:551-560`,
  `dispatcher.rs:261-290`): crash message to the client, exit 37, `createShutdown`, shutdown
  reason "due to a crash", the lock released, the server shuts down in order, as
  `BlazeCommandDispatcher.java:862-868` and `GrpcServerImpl.java:672`. A panic outside it on a
  `grpc-command-N` thread halts with the exit code file, as Java's default handler.
- **Startup-option mismatch and restart**: `IsVolatileArg`, multiset comparison in
  libstdc++'s order, the warning text, `KillRunningServer`, restart reasons, the server-cwd
  check, `ConnectOrDie` (`blaze.rs:1756-1836, 2041-2219, 2382-2474`).
- **Idle timeout and shutdown**: `ServerWatcherRunnable`, `ShutdownHooks` (disabled by
  `clean --expunge`), orderly `server.shutdown()` after the final response, `exit` killing
  children and running the hooks (`runtime.rs:317-332`).
- **Per-command state in the runtime**: reporter and event bus are created per command
  (`command_environment.rs:144-145`); client environment and cwd come from `--client_env` and
  `--client_cwd`; the remaining `env::var` and `current_dir` reads are server-lifetime values
  that Java also reads from the server process.

## Known open problems

- **About 90 MB more per build command.** Explained by the code: F1. With no release, every
  command adds a full set to the arena's slots, all strong: `KeepAlive` (every `FrozenModule`
  loaded, `bzl_load.rs:737`), `KeptHeaps` and `DepsetMemos` (`depsets.rs:80, 138`),
  `GeneratorNameHeaps`, `ConvertedTransitions`, `StarlarkTransitionCache`, `MapEachAdaptors`,
  `ActionInputSets`, `LoadingPhaseHeaderInfos`; and the graph is discarded per command (D2),
  so everything is loaded again. The soak agrees: `base-brotli-build` grows about 95 MB of
  anonymous memory per build (180 MB to 1,180 MB in 12 builds), `arena1-brotli-build` about
  35 to 78 MB.
- **The leak outside the arena (about 35 MB per build, about 11 MB per query with the release
  on).** Partly explained, as a candidate: F2 leaks the event bus and its subscribers on every
  build that executes. I did not measure its share. It does not apply to `query` (no
  `ExecutionProgressReceiverSetup`), so the per-query growth is not explained by anything I
  read. Not examined: allocator retention (no `#[global_allocator]`, so glibc's per-thread
  arenas with a new thread set per command; the shrinking increments of `arena1-brotli-build`,
  78 MB then 56 then 35, fit a part that levels off), `OPTIONS_DATA_CACHE`, the Merkle subtree
  caches, the interner tables.
- **Broken pipe in daemon mode** (STATUS): I found nothing wrong in the client path
  (`blaze.rs:714-746, 814-819`, `util/file.rs:624-640`, `signal_handler.rs:234-282`); it
  needs a probe.

## Open items, not blocking

1. `exec_exclusively` returns `after_command`'s result on the early-exit path
   (`dispatcher.rs:490`; the same pattern at `:636, 667, 762, 788, 817`, whose Java
   counterparts I did not each open); Java returns the early result and discards
   `afterCommand`'s (`BlazeCommandDispatcher.java:522-523, 884-889`). Differs only when a
   module's `afterCommand` fails after an early exit. The pattern is present at the baseline.
2. `Cancel` and `UpdateTerminalSize` with a bad cookie answer OK without a message
   (`grpc_server_impl.rs:862-864`). What grpc-java at the pin sends for `onCompleted()` without
   `onNext()` on a unary call was not checked. No correct client sends a bad cookie.
3. In daemon mode the client no longer refuses a live Bazel server in a shared output base
   (`blaze.rs:2843-2866`): it shuts it down as a Bazel of another version would. That is the
   planned end state (decision 2026-11-18); say so in the S5 notes.
4. `env.getTimestampGranularityMonitor().waitForTimestampGranularity`
   (`BlazeCommandDispatcher.java:899`) is skipped as incremental; revisit with Track I.
5. `ByFilename` (`blaze_packages/src/bzl_context.rs:69`) is last-writer-wins across commands
   while the arena is not released; I saw no wrong read, but it should be per executor.

## To lift the STOP

F1: reset per-command state where Java does, independent of the arena; correct the comments;
switch the release on or state the growth as a known limit in STATUS. F2: port the event-bus
teardown and remove the cycle. Evidence for both from `blaze-<commit>` built clean: a
two-command and a two-target sequence on one daemon against the oracle, and the soak rerun.
Then this reviewer role re-checks.
