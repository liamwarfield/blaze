## New findings

### S1

**E2-9 (blocking). Exclusive tests still run in another order than Bazel when a top-level target
is skipped as incompatible.**

- Rust: `crates/blaze_runtime/src/commands/build.rs:1576-1602` builds the replay's entries from
  `main_evaluation_result.values`. That evaluation is given `keys_to_execute` only
  (`build.rs:2034-2053`, `execution_tool.rs:835`); the keys of skipped targets go to
  `skipped_keys` and are never evaluated.
- Java: `SkyframeExecutor.evaluateBuildDriverKeys` (`SkyframeExecutor.java:2503`) evaluates every
  `BuildDriverKey`. For an incompatible target `BuildDriverFunction.compute` returns
  `new BuildDriverValue(topLevelSkyValue, /* skipped= */ true)` (`BuildDriverFunction.java:292`),
  so the key has a value and is an entry of the result map that
  `SkyframeBuildView.getExclusiveTests` iterates (`SkyframeBuildView.java:1103`).
- Effect: each skipped target makes Java's map one entry larger than Blaze's, which changes the
  pre-sized table at the sizes of E2-1.
- Input: `test //blaze_tests_probe:excl_b //blaze_tests_probe:excl_c` plus one target that is
  skipped (`target_compatible_with` not satisfied, reached by a wildcard or with
  `--skip_incompatible_explicit_targets`). Java: 4 entries, copy table of 8, `excl_b` (bucket 2)
  then `excl_c` (bucket 4). Blaze: 3 entries, table of 4, `excl_c` (bucket 0) then `excl_b`
  (bucket 2). The skipped key's own hash does not matter. Computed from the round-1 hash values
  and the Java source; not run (suite active).
- Why the fixer's 55 oracle orders did not see it: none has a skipped target.
- Fix expected: the replay receives every `BuildDriverKey` that has a value in Java, in root
  order (the configured-target keys in their set order, skipped ones included, with their hash),
  then the aspect keys, then the workspace status key. An oracle case with two exclusive tests
  and one skipped target, and one with five and one.

**E2-11 (blocking until fixed or refuted). A `test.xml` with a malformed byte sequence makes
Bazel print a line that Blaze does not print.**

- Java: for a malformed UTF-8, US-ASCII or UTF-16 sequence the JDK scanner reports through the
  five-argument `XMLErrorReporter.reportError`, which the StAX reporter does not override; with
  no handler set, the default handler prints to `System.err` before the exception is thrown.
  Measured with Bazel's parser on the oracle's JDK:
  `[Fatal Error] :-1:-1: Invalid byte 2 of 3-byte UTF-8 sequence.`,
  `[Fatal Error] :-1:-1: Invalid byte 1 of 1-byte UTF-8 sequence.`,
  `[Fatal Error] :-1:-1: Byte "233" is not a member of the (7-bit) ASCII character set.`,
  `[Fatal Error] :-1:-1: Expected byte 2 of 2-byte UTF-8 sequence.` (the last one for an odd
  UTF-16 byte). During a command `System.err` is the reporter's stream
  (`BlazeCommandDispatcher.java:485`, `:630`, `OutErr.SystemPatcher`), so the line reaches the
  console.
- Rust: `test_xml_output_parser.rs:83-86` and the module comment of `xml_stream_reader.rs:15`
  ("The exception messages are not Java's: Bazel drops them"). Nothing is printed.
- Input: a test whose `test.xml` holds a byte that is not valid UTF-8 inside the top-level
  element (gtest writes failure messages bytewise), with `--test_summary=detailed` or
  `testcase`.
- Not confirmed with an oracle run (suite active); the two halves are measured and read
  separately. The gap is older than this change, but the new reader states the opposite.
- Fix expected: one oracle run of that input. If the line appears, print it (the JDK's message
  for each malformed-sequence kind, `:-1:-1:`) where Java does; if it does not, record the run
  in the response and this finding is withdrawn.

### S2

**E2-10. The new reader still accepts documents the JDK rejects.** All masked for the output of
Bazel's generator and gtest.

- JDK 25 processing limits are not ported (`xml_stream_reader.rs` has none). Measured: more than
  100 nested elements, more than 200 attributes on one element, and a name longer than 1,000
  characters are `XMLStreamException`s (`depth_101`, `attrs_201`, `name_1001`; `depth_100`,
  `attrs_200`, `name_1000` pass). Java then drops the test cases; Blaze keeps them.
- Decoding errors are not always lazy. `decode` (`:886-923`, `:926-952`) lets every error
  surface only when the scanner reaches it. That holds for the JDK's UTF-8 reader, but its ASCII
  and UTF-16 readers fail for the whole chunk they load: `<?xml version="1.0"
  encoding="US-ASCII"?><testsuite name="s"/>` followed by `0xE9`, and a UTF-16 document followed
  by one odd byte, are rejected by Java and accepted by Blaze (`ascii_high_after_root`,
  `utf16_odd_near`). With 200,000 spaces before the bad byte both accept.
- Fix expected: port the three limits (or fail loudly at them), and make the ASCII and UTF-16
  errors chunk-eager as the JDK's readers are, with these documents as cases.

**E2-12. A hexadecimal float in `time` is rejected silently.** `test_xml_output_parser.rs:327`
(`PORT: hexadecimal floating-point literals are not accepted`) returns a number-format failure,
so the whole tree is dropped; `Float.parseFloat("0x1.8p1")` is 3.0 and Java returns 3000 ms
(`hexfloat_time`). Masked: no known writer emits it. Fix: parse it or `unported!`.
