## Round-1 findings

- **BES-1 (S1, was blocking): fixed.** `bep.rs` `TimedCloseFuture` now has a `timed_out` flag
  set by a timer thread started at construction (`bes-close-<name>-0`, Java
  `BuildEventServiceModule.java:596-611`), and `outcome` answers `TimedOut` whenever the flag is
  set, before and after it asks the close future, so a completion after the deadline still
  reads as the timeout. The timer starts where Java's does (in `PendingUpload::new`, called from
  `close_bep_transports`), is not started for a zero timeout or a future that is already done,
  and a waiter that reaches the deadline first sets the flag itself. Both futures of a transport
  go through the type, so the three modes are covered: `wait_for_upload_complete` fails in
  `wait_for_build_event_transports_to_close` with `BES_UPLOAD_TIMEOUT_ERROR`;
  `nowait_for_upload_complete` waits on the close future and `fully_async` on the half-close
  future in `wait_for_previous_invocation`, each taking the "failed due to a network timeout"
  branch. `cancel` still goes to the close future itself, as Java's forwarding future does.
  Test: `before_second_command_no_wait_bes_timeout_late_completion_warning`.
- **BES-2 (S2): fixed.** `bazel_modules.rs:1373-1379` records `--keep_backend_connections` for
  every command; `after_command` clears the client for a command without a streamer
  (`:1399-1409`), and `BepCommandSupport::after_command` clears it after the transports closed
  and not when closing failed (`bep.rs:2893`), as Java `:662-687`.
- **BES-3 (S2): local part fixed; remote part accepted as not reachable.** `uploader.rs:895-916`
  waits in 10 ms steps and returns `Interrupted` when the uploader thread is interrupted. The
  three sources of pending remote uploads each stop with `unported!`
  (`unported_options.rs:113`, `profiler_init.rs:272`); the `PORT` note says so. Reclassified S3.
- **BES-4 (S2): fixed.** `uploader.rs:465-476` runs `finish_run` (release, complete the close
  future) before the `IllegalStateException` panic.
- **Module tests (S3): ported.** 48 tests (47 Java methods and the BES-1 case), 23 run, 25
  `#[ignore]` with reasons (2 `@Ignore` in Java, 3 OOM, 1 connectivity provider, 1 event without

## Abort path

`ReferenceCountedChannel::cancellable_request` takes tonic's `CancellationHandle`
(`Request::cancellation_handle`), which makes tonic's encoder end the request body with
`CANCELLED` and so resets the HTTP/2 stream; the guard is dropped with the response stream or
with the call's future. `BesGrpcStreamContext::abort_stream` sets the status and wakes the
call's task, whose `select!` drops the call (`grpc_client.rs:226-238`), so the reset is sent
while the request side is open. `test_file_upload_fails` is no longer ignored and waits for the
server-side error (`CANCELLED` or `INTERNAL`, as the Java test accepts both); the fake server
tells a reset from a half-close by the error of the request body. The earlier `PORT: deviation`
note is gone. Not run by me (no Cargo).

## Package metrics

- `Extrema`: `min`/`max`/`create` and both subclasses as Java. The queue is a re-implementation
  of `java.util.PriorityQueue`'s array (`siftUpUsingComparator`, `siftDownUsingComparator`,
  `poll` moving the last element to the root), and `get_extreme_elements` sorts a copy of that
  array stably, which is `ImmutableList.sortedCopyOf` over `toArray()`. Ties keep the heap's
  array order, as in Java.
- Recorders: the extrema recorder aggregates in Java's order with the overhead queue only when
  the field is set, returns `LinkedHashMap` semantics, and de-duplicates
  `getPackageLoadMetrics` by message equality in stream order. The complete recorder models
  `HashMap` iteration (bucket of `PackageIdentifier.hashCode()` spread, table size from the
  largest size, insertion order inside a bucket). The listener and the module follow Java
  (`max(n, 0)`, `loadingFinished` in `afterCommand`); `MetricsCollector` applies the `5 * n`
  limit for the extrema recorder only.
- Probe (oracle and blaze-dad60f0, one workspace of 30 small packages, one server per side,
  `--experimental_publish_package_metrics_in_bep` with the default, with
  `--record_metrics_for_all_packages` and with `--log_top_n_packages=3`; files kept in
  `~/.cache/blaze/work/review-bes/`):
  - all-packages mode: 34 entries on both sides; `name`, `numTargets`, `numTransitiveLoads` and
