## S1: wrong output or behaviour on valid input

### S1-1 Cached test results are never reported (second `blaze test` run)

- Rust: `SkyframeActionExecutor::notify_on_action_cache_hit`
  (`crates/blaze_sky_exec/src/skyframe_action_executor.rs` ~810) does
  `action.as_any().downcast_ref::<blaze_exec::analysis::test::test_runner_action::TestRunnerAction>()?`.
  The action in the graph is `blaze_analysis::test::test_runner_action::TestRunnerAction`, whose
  `as_any()` returns itself (`crates/blaze_analysis/src/test/test_runner_action.rs` ~712) and which
  only delegates to the exec type through `execution_action()`. The downcast is `None`, so the
  function returns `None` and `action_cache_hit` is never called.
- Java: `skyframe/SkyframeActionExecutor.java:801-838` (`action instanceof NotifyOnActionCacheHit`
  → `notify.actionCacheHit(context)`; on `false` the action is re-executed);
  `analysis/test/TestRunnerAction.java:685 actionCacheHit` posts the cached `TestResult`.
- Scenario: `blaze test //:t` passes; run it again unchanged. `execute_unconditionally` is false
  (previous result passed and cachable), the action cache hits, and no `TestResult` is posted.
  Bazel prints `//:t (cached) PASSED`; Blaze's test listener receives nothing for the target.
  The unreadable-cache-status fallback (re-run the test) is lost too.
- Not caught by replay: `blaze-test-replay` builds the exec-level action directly.
- Fix: use `blaze_exec::analysis::test::as_test_runner_action(action)` (already used by
  `test_completion_function.rs`) instead of the downcast.

### S1-2 A file output that is a directory is accepted

- Rust: `SkyframeActionExecutor::check_outputs` (~642). The comment says
  "checkForUnsoundDirectoryOutput and addOutputToMetrics (metrics) are not ported", but the first
  is a correctness check, not a metric. `construct_file_artifact_value_from_filesystem` returns a
  `Directory { mtime }` value for a directory, so the output passes.
- Java: `SkyframeActionExecutor.java:1762 checkForUnsoundDirectoryOutput` reports
  `output '<x>' of <label> is a directory but was not declared as such` as an ERROR and
  `checkOutputs` returns false ("not all outputs were created or valid").
- Scenario: `genrule(name="g", outs=["d"], cmd="mkdir $@")`. Bazel 9.3.2 fails the build; Blaze
  succeeds and feeds a directory with mtime-only metadata to consumers.
- Also missing: `checkForUnsoundDirectoryInputs` (Java :1727), the warning
  `input '<x>' of <label> is a directory; dependency checking of directories is unsound` for a
  source directory input. No text of either message exists in the three crates.
- Fix: port both checks.

### S1-3 Output directory creation is not the pinned algorithm

- Rust: `SkyframeActionExecutor::create_output_directories` (~696) calls
  `dir.create_directory_and_parents()` and nothing else. Its marker cites
  `skyframe/OutputDirectoryHelper.java:117`, a file that does not exist at the pin (the class is
  `actions/ActionOutputDirectoryHelper.java`).
- Java: `ActionOutputDirectoryHelper.createOutputDirectories` (:149),
  `createAndCheckForSymlinks` (:260), `forceCreateDirectoryAndParents` (:191): rejects symlinks
  between the output root and the output, deletes a file or symlink that is in the way, and makes
  an existing non-writable directory writable.
- Scenarios (incremental builds, which replay never ran):
  1. Build 1 produces file `bazel-out/k8-fastbuild/bin/p/foo`. A BUILD edit makes build 2 produce
     `p/foo/bar.o`. Bazel deletes the stale file and continues; Blaze fails with
     `failed to create output directory ...` until `clean`.
  2. A stale symlink left at an ancestor of an output is followed: Blaze writes outputs through
     it; Bazel replaces it with a directory.
  3. An ancestor directory left read-only is not made writable.
- Fix: port `ActionOutputDirectoryHelper` from the pin.

### S1-5 Top-level target with a missing or unreadable source input: wrong messages

- Rust: `compute_target_completion` (`crates/blaze_sky_exec/src/completion_function.rs` ~98-156).
- Java: `skyframe/CompletionFunction.java:197-290`, `TargetCompletor.getRootCauseError` (:66) and
  `getLocationIdentifier` (:74), `ActionExecutionFunction.createSourceErrorCodeAndMessage`.
- Differences:
  1. Java reports one error per cause at the target's location,
     `<label>: <cause message>` (for example `//p:t: missing input file '//p:x.txt'`). Blaze
     reports none.
  2. Final error: Java `Event.error(<target location>, "N input file(s) do not exist")` (or
     `are in error`, or `are in error or do not exist`). Blaze emits
     `<label> N input file(s) do not exist` with no location, the label as a prefix, and always
     "do not exist", also for `SourceArtifactException` (I/O error) causes.
  3. `TargetCompletor.createSucceeded` (:120) warns `<label> is a source file, nothing will be
     built for it. If you want to build a target that consumes this file, try
     --compile_one_dependency` for an input-file target. The text exists nowhere in `crates/`.
- Scenario: `exports_files(["missing.txt"])`, then `blaze build //p:missing.txt`; or
  `blaze build //p:existing.cc` (no warning).
- Fix: port `handleSourceFileError`, `createSourceErrorCodeAndMessage` and the location through
  the seam; add the source-file warning.

### S1-6 Shared actions: the second owner gets the first owner's value untransformed

- Rust: `ActionExecutionFunction::check_cache_and_execute_if_needed`, `previous_execution` branch
  (`action_execution_function.rs` ~303-325), and `SkyframeActionExecutor::execute_action` (~378):
  the `OnceLock` result of the first execution is returned as is. There is no
  `transform_for_shared_action` anywhere in the crate.
- Java: `skyframe/ActionExecutionState.java:132-137` calls
  `result.transformForSharedAction(action)` (`ActionExecutionValue.java:310`), which re-keys the
  outputs to the second action's artifacts, and posts `SharedActionEvent`.
- Why it matters: `Artifact` equality includes the owner (`blaze_actions` `owners_equal`
  compares generating action keys), and `ActionExecutionValue` maps are keyed by `Artifact`. A
  consumer of the second action's artifacts looks them up in a map keyed by the first action's.
- Scenario: two action lookup keys (for example the same aspect reached on two paths) register
  equal actions for one output.
  - Tree artifact output: `compute_artifact` (`artifact_function.rs` ~155) panics
    `NullPointerException: <artifact>`.
  - Output used as a discovered input (generated header): `add_discovered_inputs` (~515) panics
    `NullPointerException`.
  - Plain file output: `add_to_map` (~799) skips the missing value silently (Java's
    `getExistingFileArtifactValue` is a `checkNotNull`), and
    `ActionInputMetadata::get_input_metadata` then stats the file. The build works by accident;
    see S2-1.
- Fix: port `transformForSharedAction` and apply it when `action_lookup_data` differs from the
  one that ran; restore the null check in `add_to_map`.

## S2: deviations masked today

### S2-1 Missing input metadata is replaced by a stat

`ActionInputMetadata::get_input_metadata` (`skyframe_action_executor.rs` ~2045) stats any exec
path the map lacks and caches the result (including "absent"). Java's
`ActionInputMetadataProvider.getInputMetadataChecked` returns null for inputs not in the map; the
per-build file cache is consulted only by the execution-time composite provider, not by the cache
check. Runfiles members are not put in the map at all (Java: `addToMap` →
`runfilesArtifactValue.forEachFile(inputMap::put)`). Together with the silent skip in
`add_to_map` this hides wiring errors (S1-6) and makes the action cache digest depend on a stat
taken at check time rather than on the Skyframe value. Fix: fill the map as Java does and return
`None` otherwise.

### S2-2 Conflicting actions are merged instead of rejected (cross-area)

`blaze_sky_top/src/skyframe_build_view.rs` ~99 says `ArtifactConflictFinder` is not ported (a
comment, no `unported!`). `SkyframeActionExecutor::execute_action` keys `build_action_map` by
`OwnerlessArtifactWrapper(primary output)` and assumes, as Java does, that equal keys mean
shareable actions. Two different actions that write the same path (Bazel: "file '<x>' is
generated by these conflicting actions", analysis error) are run once in Blaze, whichever is
requested first, and the other gets its result. Fix: port the conflict finder, or fail loudly in
`execute_action` when the second action's key differs.

### S2-3 Tree artifact values are not built as Java builds them

`ActionOutputMetadataStore::construct_tree_artifact_value_from_filesystem`, `visit_tree`,
`set_tree_read_only_and_executable` (~1256-1494) versus `ActionOutputMetadataStore.java:236` and
`TreeArtifactValue.java:548 Visitor.visit`:
- Java follows symlinks inside the tree (a symlink to a directory is traversed and its files
  become children); Blaze records the symlink as one child with a directory value.
- Java fails with `child <p> is a dangling symbolic link` / `child <p> has an unsupported type`;
  Blaze surfaces a raw not-found error, reported as "was not created".
- Java chmods every visited entry, directories included, to the output mode (0555). Blaze sets
  directories to 0755. The comment "Java chmods each visited entry (not through symlinks) during
  the visit" does not describe what the Rust does.
Masked because `check_action_cache_inputs_supported` (~853) panics `unported!` for any tree
artifact input or output while the action cache is on (the default). With `--nouse_action_cache`
these paths run. Trees of symlinked directories are normal for JS rules (workerd).

### S2-4 Action stdout/stderr directory is a made-up path

`prepare_for_execution_with_action_cache` (`execution_tool.rs` ~240) uses
`<output_base>/action_outs` and ignores a failed `delete_tree`. Java:
`BlazeDirectories.getActionTempsDirectory` = `<execroot>/<product>-out/_tmp/actions`
(`analysis/BlazeDirectories.java:214`), and a failed delete is the
"Couldn't delete action output directory" error. Visible in `ActionExecutedEvent` stdout/stderr
paths (BEP) and in "output too large" messages. `blaze_runtime/src/directories.rs:227` already
has the right path.

### S2-5 Accepted flags that do nothing

None of these fails or warns:
- `--experimental_writable_outputs`: `output_permissions: OutputPermissions::READONLY` is
  hard-coded in `execution_tool.rs` ~336 (Java: `SkyframeActionExecutor.getOutputPermissions`
  :452).
- `--check_up_to_date`, `--check_tests_up_to_date`: `blaze_sky_top/src/execution_phase.rs` ~126
  builds `ActionCacheOptions { ..default() }`, so both are always false and the
  `unported!("CheckUpToDateFilter")` in `execution_tool.rs` is unreachable. Bazel fails the build
  without executing; Blaze executes. `test_check_up_to_date` is still read by the test summary
  code, which then assumes tests were not run.
- `--output_filter` / `--auto_output_filter`: `actually_complete_action` (~559) always dumps
  output (Java :1309 `reporter.showOutput(...)`).
- `--subcommands`: `ActionExecutionContextImpl::maybe_report_subcommand` (~2129) is empty.
Fix: wire them or call `unported!` when set.

### S2-6 Sandbox seams filled with constants or skipped (cross-area, `blaze_runtime/src/commands/build.rs`)

- `package_path_entries: vec![workspace]`, `repo_contents_cache_path: None` (~253): with
  `--package_path` or a repository contents cache under `/tmp`,
  `LinuxSandboxedSpawnRunner::collect_paths_to_mount_under_hermetic_tmp` misses mounts that Java
  adds (:187-191), and sandboxed actions cannot see those paths under hermetic `/tmp`.
- `SandboxModule.afterCommand` is not called (comment at ~619): the runner's
  `cleanup_sandbox_base` never runs, so `<sandbox_base>/linux-sandbox` and the inaccessible
  helper file and directory stay after every command (Java `SandboxModule.java:452-469`).

### S2-7 Compact execution log guesses

`compact_spawn_log_context.rs` ~97: "every other virtual input is treated as a parameter file";
~31: runfiles symlink sets are logged as one flat set instead of mirroring the nested set nodes.
Both are stated as seam gaps; the first is a guess about input kinds. Not verified further.

### S2-8 `StringEncoding identity` claims versus the 2026-11-18 strings decision

`spawn_log_context.rs`, `compact_spawn_log_context.rs`, `local_spawn_runner.rs`, the action cache
digest code and others mark `internalToUnicode`/`unicodeToInternal` as identity. The decision of
2026-11-18 makes Rust strings carry Bazel's internal (Latin-1 of UTF-8 bytes) form, at which
point these are no longer identities (exec log paths and env values with non-ASCII bytes). Each
marked site needs revisiting in the migration.

## Two-phase error model (functions may run twice)

Checked, no finding:
- Action execution is not repeated: the owner's re-run takes the `previous_execution` branch and
  gets the stored `OnceLock` result; `ActionStartedEvent`/`ActionCompletionEvent` are posted in
  `run_action` only.
- Output deletion and directory creation happen inside `run_action` only.
- A first run that stops on a hidden dep error returns before any print or event in
  `check_inputs` (the handler sees no exception; `values_missing` is checked before missing
  inputs are accumulated) and in `compute_target_completion` (errors are reported only for
  values and exceptions it can see).
- An input-discovering action that returns `None` after `check_action_cache` re-runs the cache
  check and input discovery; the stale cache entry is already removed, as in Java before
  execution. Idempotent.
- `BuildDriverFunction` posts each status event once per key (`post_event_if_necessary`).

## NEW

### R5 (S2) 256 MB action threads scale with `--jobs`

The design is sound for the default: at most `parallelism` (`--jobs`) evaluator threads compute
at once, each holds its permit while it waits for its action thread, so at most `--jobs` 256 MB
stacks exist when a spawn forks. The bound is the user's flag, though. The implementer measured
that 400 such threads make `fork` fail with ENOMEM on this machine and 200 do not;
`--jobs=400`, ordinary with remote execution or caching, reaches that for any local spawn. The
thread also lives for the whole `execute`, including the wait for resources and for the child,
not only for the Starlark calls. Options: hop only around key and command-line expansion, or
spawn children without accounting the parent's mappings.

### R6 (S2, narrow) The input-set memo ignores `Order`

`convert_set` (`blaze_exec/src/analysis/actions/mod.rs` ~270) keys the process-wide memo by
node only. Two sets that share a node but differ in order (all empty sets; equal singletons; a
set that wraps one transitive set) get the converted set of whichever came first, with its
order. Every current caller adds the result to a STABLE_ORDER builder or uses it unordered, so
nothing fails today. The lock is held across the whole conversion, which serializes it across
actions (S4).
