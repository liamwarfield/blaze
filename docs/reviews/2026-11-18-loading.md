## Findings

### S1: wrong behaviour on valid input

**S1-1. `.bzl` type annotations are rejected; Bazel 9.3.2 accepts them by default.**
- Rust: `crates/blaze_starlark/src/file_kind.rs:52` (`allow_type_syntax: false` in `DEFAULT`),
  `:83-85` ("type syntax off unless --experimental_starlark_type_syntax applies, which Blaze does
  not support yet"), `:111` (`DialectTypes::Disable`).
  `crates/blaze_sky_loading/src/bzl_compile.rs:462-474` picks the `FileKind` from the key only; the
  PORT comment there says the flag is handled by `FileKind`, but no code reads
  `semantics.experimental_starlark_type_syntax` (`blaze_starlark/src/semantics.rs:228`, default
  `true`).
- Java: `lib/packages/semantics/FlagConstants.java:36`
  (`DEFAULT_EXPERIMENTAL_STARLARK_TYPE_SYNTAX = "true"`), `:38` (allowed paths `""`);
  `lib/skyframe/BzlCompileFunction.java:249-268` `shouldUseTypeSyntax` (true for every non-prelude,
  non-.scl file when the allowlist is empty), `:212` `.allowTypeSyntax(useTypeSyntax)`, `:214`
  `.tolerateInvalidTypeExpressions(!doTypeChecking)`.
- Differs:
  ```python
  # defs.bzl
  def f(x: int) -> int:
      return x + 1
  # BUILD
  load(":defs.bzl", "f")
  ```
  Bazel loads the package. Blaze reports starlark-rust's "type annotations are not allowed in this
  dialect" and "compilation of module 'defs.bzl' failed". (`bzl_compile.rs:508` also matches on
  Java's text "type annotations are disallowed", which starlark-rust never emits.)
- Fix: port `shouldUseTypeSyntax` into BZL_COMPILE and parse with types enabled
  (`DialectTypes::ParseOnly`) when it is true. Queue a starlark-rust patch for Java type syntax the
  parser lacks; until then fail with `unported!`, not with a user syntax error.

**S1-2. The BUILD prelude drops symbols bound by `load()` and names starting with `_`.**
- Rust: `crates/blaze_sky_loading/src/package_function.rs:1194-1203` copies
  `prelude.names()` / `prelude.get_option(name)`. `FrozenModule::names()` yields public names only
  (`third_party/starlark-rust/starlark/src/environment/modules.rs:458-468`). Load bindings are
  private because every dialect sets `enable_load_reexport: false`
  (`crates/blaze_starlark/src/file_kind.rs:118`); `_x` names are private by
  `Module::default_visibility` (`modules.rs:592-597`).
- Java: `lib/skyframe/PackageFunction.java:1068` `preludeBindings = prelude.getGlobals()`, `:1400`
  `predeclared.putAll(preludeBindings)`; `lib/skyframe/BzlCompileFunction.java:204`
  `.loadBindsGlobally(key.isBuildPrelude())` ("the BUILD prelude typically contains nothing but
  load statements whose bindings are intended to be visible in all BUILD files").
- Differs:
  ```
  tools/build_rules/BUILD            (empty)
  tools/build_rules/prelude_bazel    load("//util:common.bzl", "foo")
  util/BUILD                         (empty)
  util/common.bzl                    foo = "FOO"
  pkg/BUILD                          print(foo)
  ```
  Bazel prints `FOO` (`PackageFunctionTest.testPreludeAutomaticallyReexportsLoadedSymbols`,
  `testPreludeCanExportUnderscoreSymbols`). Blaze: `foo` is undefined, package in error.
- The 13 ported prelude tests are ignored with "needs a rule class provider with a prelude label"
  (`crates/blaze_sky_loading/src/tests/package_function_test.rs:277-289`), but the label is set
  (`crates/blaze_packages/src/native_rules/rule_class_provider.rs:348`). The stale reason hides this.

**S1-3. Package-loading flags are accepted and silently ignored.**

**S1-4. `checkAspectAllowedValues` is a redesign that disagrees with Java in both directions.**
- Rust: `crates/blaze_packages/src/rule_class/rule_class.rs:632-703`. Lines 651-668: the value is
  `None` whenever the rule attribute is configurable; the rule's value is used only when the name
  is in `get_required_parameters()` (Java `paramAttributes`: attributes without a default,
  `starlark_defs/aspect.rs:297,547`); otherwise the aspect default.
- Java: `lib/packages/RuleClass.java:2158-2190` checks `attrOfAspect.getDefaultValue(null)` of the
  definition built from `lib/packages/StarlarkDefinedAspect.java:299-343`
  `getDefaultParametersExtractor`. Lines 333-338 copy the rule's value for every non-implicit aspect
  attribute with a same-named, same-typed, non-configurable rule attribute; this is not gated on
  `paramAttributes`. `isConfigurable` is consulted only after the allowed-values check fails.
- Differs:
  ```python
  # defs.bzl
  def _a(target, ctx): return []
  my_aspect = aspect(_a, attrs = {"mode": attr.string(default = "a", values = ["a", "b"])})
  def _r(ctx): pass
  r = rule(_r, attrs = {"deps": attr.label_list(aspects = [my_aspect]), "mode": attr.string()})
  # BUILD

  r(name = "x", mode = "c")                                      # (b)
  ```
  (a) Bazel: no parameter is added, the default "a" is allowed, no error. Blaze: "attribute 'mode'
  has a select() and aspect my_aspect also declares ..." and the package is in error.
  (b) Bazel: "//pkg:x: invalid value in 'mode' attribute: has to be one of 'a' or 'b' instead of
  'c'". Blaze: no error.
- Fix: port the default parameter extractor literally and apply the allowed-values check to the
  resulting value; consult `isConfigurable` only in the failure branch.

**S1-5. `select()` rejects a positional `no_match_error`.**

## Unsafe and lifetime assumptions (item 8)

- `frozen_into` (`blaze_starlark/src/eval.rs:235-239`) is sound: `owned_frozen_value` adds the
  owner heap to the module's frozen heap.
- The other `OwnedFrozenValue::new` sites (`builtins/env.rs:211,262`, `starlark_builtins.rs:224`,
  `depset.rs:404`, `attr_module.rs:845`) pair a value with the heap that owns it or owns it
  transitively; each has a SAFETY comment and is sound. All `unsafe impl Coerce` types are
  `#[repr(C)]`.
- `StarlarkCallable::to_owned_frozen_value` (`rule_class/starlark_callable.rs:50-54`) uses an empty
  heap reference and relies on `KEEP_ALIVE` (`blaze_sky_loading/src/bzl_load.rs:748,1483`), which
  holds every successfully executed .bzl module for the process. The only constructor of handles is
  `PendingValue::new` (`starlark_defs/value_cell.rs:127-137`), which uses already-frozen values or a
  cell on `eval.frozen_heap()`. That holds for BZL_LOAD threads. It does not hold for a BUILD
  thread, whose module is not in `KEEP_ALIVE`; `attr.*` and `rule()` accept BUILD threads, and the
  only consumer there (`testing.analysis_test`) is `unported!`. When that is ported, the BUILD
  module's heap must be kept alive or the handle must carry its heap.
- The assumption "one build per process" is stated in DESIGN.md and decisions.md. `KEEP_ALIVE` and
  `BY_FILENAME` (S2-2) are the two process globals that break if a process ever runs two builds.
