## Findings

### S1-1. Action keys are wrong when a non-ASCII string goes through `Fingerprint::add_string`

Java strings in keys are in Bazel's internal form (one Latin-1 char per UTF-8 byte), and
`Fingerprint.addString` (`util/Fingerprint.java:235`, `writeStringNoTag`) UTF-8-encodes them once
more. `blaze_util/src/fingerprint.rs` has two methods: `add_string` (130) writes the Rust UTF-8
bytes once, `add_internal_string` (140) reproduces Java. `add_strings` (167), `add_string_map`
(195), `add_iterable_strings` (182) and `add_nullable_string` (159) all use `add_string`. Call
sites in the area are split between the two, so the same key mixes both conventions.

Sites that use the single encoding and therefore differ from Java for non-ASCII input:

| Rust | Java |
| --- | --- |
| `blaze_collect/src/nestedset/nested_set_fingerprint_cache.rs:259` (every nested-set element: strings, exec paths, map-fn output) | `collect/nestedset/NestedSetFingerprintCache.java:122` |
| `blaze_actions/src/analysis/starlark/starlark_custom_command_line.rs:802, 849, 948, 987, 1015, 1021, 1027, 1032, 1037, 1044, 1421, 1430, 1475` | `analysis/starlark/StarlarkCustomCommandLine.java:574, 598, 621-645, 838, 983, 989` |
| `blaze_actions/src/actions/action_environment.rs:171, 173` | `actions/ActionEnvironment.java:134` |
| `blaze_actions/src/analysis/actions/spawn_action.rs:342`, `blaze_actions/src/actions/action.rs:248` (execution info, exec properties) | `analysis/actions/SpawnAction.java:409`, `actions/ActionKeyComputer.java:56` |
| `blaze_rules/src/cpp/cpp_compile_action.rs:556, 623, 628` (compiler options, feature environment, execution info) | `rules/cpp/CppCompileAction.java:1479, 1431-1432` |

Also on `add_string` with user-controlled text, not probed: `platform_info.rs` (exec properties,
flags, remote execution properties), `runfiles.rs` (prefix), `repo_mapping_manifest_action.rs`.

Sites that already use `add_internal_string` and match the oracle with non-ASCII input:
`CustomCommandLine`, the default `AbstractCommandLine` fingerprint (plain string arguments,
`run_shell` commands, `LinkCommandLine`), `FileWriteAction` contents, `TemplateExpansionAction`,
`UnresolvedSymlinkAction` target, param file flag format, paths.

Inputs that give a wrong key (all confirmed against the oracle; argv, env and file contents were
identical, only `actionKey` differed):

```python
a = ctx.actions.args()
a.add(out)
a.add("é")          # also: add("--n", "é"), add("x", format = "é%s"), add_all(["é"]),
                    # add_all(depset(["é"])), add_all("é", ["x"]), format_each = "é%s",
                    # before_each = "é", terminate_with = "é", join_with = "é",
                    # format_joined = "é%s", map_each returning x + "é" (list and depset)
ctx.actions.run(executable = tool, arguments = [a], outputs = [out])
ctx.actions.run(..., env = {"K": "é"})      # and env = {"é": "v"}
ctx.actions.write(output = f, content = args_with("--y=é"))
```

15 of the 20 non-ASCII placements probed gave a different key. The five that matched are four
`add_internal_string` sites (plain string argument, `run_shell` command, `use_param_file("é%s")`,
`ctx.actions.write` of a plain string) and an execution requirement that Bazel filters out before
the key. For C++, `--copt=-DUNI=é` (or `copts = ["-DUNI=é"]`) changed
the key of all 8 `CppCompile` actions of the probe while `--linkopt=-Wl,-rpath,é` left the
`CppLink` keys equal to the oracle's.

This is the known item "NestedSetFingerprintCache uses add_string where Java double-encodes", but
it is wider than the nested-set cache and it is observable today: `aquery` prints a wrong
`actionKey` for valid input, and the action cache key differs from Bazel's.

Fix direction: one convention. Either make the listed sites (or `add_string` and the four helpers
built on it) use the internal encoding now, or do the docs/research/07 migration first; in the
second case every current `add_internal_string` site becomes wrong at the moment strings turn
Latin-1-decoded, because it would encode twice. Whichever comes first, the two methods should not
both stay in use. Add one oracle probe per site class with a non-ASCII string (the existing
`oracle_non_ascii_file_write_key` is the model).

### S2-1. `.d` parsing replaces bytes that are not valid UTF-8

`blaze_cc_features/src/dependency_set.rs:224-226` builds each dependency path and the output file
name with `String::from_utf8_lossy`. Java keeps the bytes (`util/DependencySet.java:151, 165, 179`,
`new String(content, 0, w, ISO_8859_1)`). PORTING.md "Strings" rules out lossy conversion.

Input: a header whose file name contains a byte sequence that is not UTF-8 (for example a Latin-1
`caf\xe9.h`), listed by gcc in the `.d` file. Java resolves the path; Blaze looks up
`caf\u{fffd}.h`, finds no artifact, and reports an undeclared inclusion or drops the discovered
input. Fix direction: carry the bytes into the path, or call `unported!` on invalid UTF-8 as
`template.rs:59` does.

### S2-2. A frozen function that is not a module global is accepted as `map_each`

`blaze_actions/src/analysis/starlark/args.rs:895-903` (`is_global_function`, also used by
`template_dict.rs`) treats every frozen function whose name is not `lambda` as global. Java asks
the defining module: `module.getGlobal(getName()) == this` (`net/starlark/java/eval/StarlarkFunction.java:91-93`,
used at `analysis/starlark/Args.java:379` and `analysis/starlark/TemplateDict.java:71`).

Input (probe `nested_top`):

```python
def _mk():
    def inner(x):
        return x
    return inner
_nested = _mk()
...
a.add_all(["x"], map_each = _nested)
```

Oracle: `Error in add_all: to avoid unintended retention of analysis data structures, the
map_each function (declared at .../defs.bzl:11:9) must be declared by a top-level def statement`.
Blaze: analysis succeeds and the action is created. A function rebound at top level after its
`def` is accepted the same way. Fix direction: look the name up in the function's own (frozen)
module and compare identity.

`json.as_bytes()`. Java prints the internal strings through `new PrintStream(out)`
(`query2/aquery/AqueryThreadsafeCallback.java:38`), whose charset is ISO-8859-1, so one byte per
char. Today the two agree. With `STRINGS_ARE_INTERNAL = true` and nothing else changed, every
non-ASCII byte of `aquery --output=jsonproto` comes out as two. The response says the switch is
one edit; this is a second one, and the after-switch side of `non_ascii_action_keys.rs` compares
keys only, so it does not see it. Fix direction: `internal_string_bytes(&json)`, and compare the
dump bytes with the recording on both sides.

**N2 (S2). A non-ASCII mnemonic is accepted.** `spawn_action.rs:1116` (and the copy at
`blaze_analysis/src/starlark/starlark_action_factory.rs:549`) tests `char::is_alphanumeric` on
the Unicode string. Java tests the internal chars (`SpawnAction.java:1258`,
`CharMatcher.javaLetterOrDigit`), so `mnemonic = "Qé"` is `Ã` then `©` and is rejected: `Error in
run_shell: mnemonic must only contain letters and/or digits, and have non-zero length, was: "Qé"`.
Blaze creates the action. Fix direction: test the chars of `to_internal(mnemonic)`.

**N3 (S4). Nothing ties the constant to the decoding.** `STRINGS_ARE_INTERNAL` lives in
`blaze_util`; the decoding lives in other crates. If one flips without the other, every non-ASCII
key is encoded once too often or once too few, silently, and the forced-side tests still pass.
Only the end-to-end probe (`scripts/actions-probe/run --binary`) sees it. Have the decoders read
`strings_are_internal()`, or gate the switch on that probe.

Also at the switch, text only: the position in `StringValueParser`'s error
(`cc_toolchain_variables.rs:89`) is a byte offset and will stop matching Java's char offset for a
non-ASCII flag.
