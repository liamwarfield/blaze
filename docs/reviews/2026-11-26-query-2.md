## S1

### S1-1 genquery `compressed_output = True` writes other bytes than Bazel (blocking)

- Rust: `crates/blaze_rules/src/genquery/gen_query_output_stream.rs:13` (`gzip_output_stream`),
  used at `:115` and `:171`. `flate2` is built with its default backend (`Cargo.toml:29`
  `flate2 = "1"`, no features; flate2 1.1.11 default is `rust_backend` = miniz_oxide).
- Java: `rules/genquery/GenQueryOutputStream.java:94` and `:142`,
  `new GZIPOutputStream(bytesOut, 8192)`: the JDK's zlib deflater at the default level.
- With `compressed_output = True` the result is `SimpleResult(bytesOut)`
  (`GenQueryOutputStream.java:127`): the gzip stream itself is the output file's content and what
  `QueryResultAction.computeKey` fingerprints. miniz_oxide and zlib choose matches and blocks
  differently, so the deflate bytes differ for ordinary inputs although they decompress to the
  same text. The header (mtime 0, XFL 0, OS 255) is right.
- Input: `genquery(name = "q", expression = "deps(//a:all)", scope = ["//a:all"],
  compressed_output = True)` with a few hundred labels; compare the sha256 of `bazel-bin/q`
  from the oracle and from Blaze. Consequence: other output digest, so every action that reads
  the file has another input digest (remote cache keys) than Bazel's.
- The path without `compressed_output` is not affected: the compressed buffer above 1 MiB is
  only held in memory and always decompressed before use.
- Not executed. Expected fix: deflate with real zlib (flate2's `zlib` feature, stock zlib, not
  zlib-ng/zlib-rs) for this stream, plus an oracle scenario that compares the bytes. If the
  probe shows equal bytes for realistic sizes, this drops to S2.

### S1-2 `print()` in the cquery Starlark formatter bypasses `System.err` (blocking)

- Rust: `starlark_output_formatter_callback.rs:66-79` (`StderrPrint`) uses `eprintln!`.
- Java: `net/starlark/java/eval/StarlarkThread.java:366` `System.err.println(location + ": " +
  msg)`; `System.err` is the per-command patched stream.
- Blaze models that stream as `blaze_events::io::system_err_println`
  (`crates/blaze_events/src/io.rs:258`), and the two other ports of the same Java line use it
  (`starlark_action_factory.rs:764`). `eprintln!` writes to the process's own stderr: in a
  server the text goes to the server's stderr and not to the client, and an internal (Latin-1
  decoded) string is written as UTF-8, so a non-ASCII message is double-encoded in every mode.
- Input: `cquery //a:all --output=starlark --starlark:file=f.cquery` with
  `def format(target): print("é", target.label); return ""`.
- Fix: call `blaze_events::io::system_err_println`.

### S2-1 aquery `--skyframe_state` / dump after build: order is random per process

`aquery_processor.rs` `dump_skyframe_state` iterates `get_all_keys_for_testing()`, which is the
order of `InMemoryGraphImpl`'s shards and `HashMap`s, hashed with `RandomState`
(`blaze_skyframe/src/in_memory_graph.rs:247-248`). The marker `PORT: java-hash-order` admits
that the order is not Java's (`SequencedSkyframeExecutor.java:634`), but not that it changes
from one server to the next: with two or more targets that have actions, the order of the
messages and the ids differ between two runs of the same build, where Bazel's output for the
same graph is stable. Expected: a fixed order (for example sorted by key) and a ruling in
`docs/decisions.md` that Java's `ConcurrentHashMap` order is not reproduced. Not blocking: the
content is the same and Java's own order is an accident of its table.

### S2-2 CQUERY_TRANSITION_RESOLVER can change results (the Blaze-only node)

`blaze_sky_analysis/src/cquery_transition_resolver.rs`, called from
`transitions_output_formatter_callback.rs:128`. For a graph where every value the resolver asks
for is done, the output equals Java's; I found the formatting half faithful. Differences that
remain:

1. Java reads a lookup environment and never computes: a missing value gives
   `Failed to evaluate <label>: ...EvaluateException: DependencyResolver.evaluate did not
   complete` and ends the output (`CqueryTransitionResolver.java:147`). Blaze returns
   `Ok(None)`, Skyframe computes the missing value (loading or analysis included) and the
   transitions are printed. No input found by reading where a value is missing after analysis,
   so this is masked; it is a real difference wherever Bazel prints that error.
2. The node stays in the graph: one per rule in the result. `BuildGraphMetrics.
   post_invocation_skyframe_node_count` (`blaze_bep/src/metrics/metrics_collector.rs:805`) of a
   `cquery --output=transitions` therefore counts nodes Bazel does not have. With a kept graph
   (D6) the nodes also survive into later commands: they are not matched by
   `should_delete_on_analysis_invalidating_change` (`blaze_sky_top/src/incremental.rs:1002`), so
   after a configuration change each keeps its `PrerequisiteMap` (configured targets) alive, and
   they are counted in later graph statistics.
3. With a kept graph a second query reads the memoized value; events the resolution posted the
   first time (`handle_dependency_root_cause_error`) are only repeated if Skyframe replays them.
4. An interrupted or failed evaluation is `unported!` (a panic) where Java propagates
   `InterruptedException` (S3).

Expected: run `DependencyResolver` on an environment that only reads done values (the cquery
environment already has `graph_lookup()`), or delete the nodes when the formatter closes; in
either case record the mechanism in `docs/decisions.md`. Not blocking today.

## The two Blaze-only mechanisms

### `blaze_analysis::skyframe_env` (the `unsafe` block): sound

- Lifetime: the pointer is made from the `&mut Environment` that `with_skyframe_env` holds for
  the whole call of `f`; `Restore` puts the previous slot back before that borrow ends, on
  return and on unwinding. `f` cannot capture `env` (it is mutably borrowed), and the parameter
  is not touched while the pointer is live, so no second path to the environment exists.
- Exclusivity: `get_skyframe_env` takes the pointer out of the slot before it makes the
  `&mut`; a nested `get_skyframe_env` finds the slot empty and panics instead of aliasing.
  The closure is `for<'e> FnOnce(&mut Environment<'e>)`, so neither the reference nor anything
  of lifetime `'e` can leave it; the cast to `'static` is not observable.
- Re-entrancy: a nested `with_skyframe_env` (another node computed on the same thread) lends
  its own environment and restores the outer one, also while the outer one is taken out.
- Panic while set: both guards restore on unwind. Another thread: the slot is thread-local, so
  a use from another thread panics ("no Skyframe environment"); it cannot reach a foreign
  environment. A restart of the function: the scope has ended, the next call lends again.
- Not unsound, but a logic hazard: if a factory ever blocks in a work-stealing pool inside
  `with_skyframe_env`, a stolen job on the same thread that calls `get_skyframe_env` without
  its own `with_skyframe_env` would register dependencies on the wrong node. Today only
  `GenQuery` calls it, on the function's thread (`Rc`/`Cell` in its preloader confirm that).
- Safe formulation: yes, pass the environment as an argument (a `&mut Environment` parameter
  on `ConfiguredTargetFactory::create_configured_target` down to
  `RuleConfiguredTargetFactory::create`, or a `RuleContext<'e>` field). It costs a signature
  change through every factory; a thread-local cannot hold a non-`'static` borrow without
  `unsafe`. The present form is acceptable; the argument form is the one to prefer if the
  factory trait is touched again.
