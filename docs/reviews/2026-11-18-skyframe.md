## Concurrency: interleavings checked (no finding)

Notation: `T`, `U`, `V` threads; `P` a thread in `eval_keys`; `H` a helper; `stack[T]` and
`waiting[T]` as in `WaitGraph`; a wait `(frames, keys)` blocks stack indices `< frames`.

1. Lost wakeup on a node. Waiter: lock `state`, see `InProgress`, `Condvar::wait` (enqueues, then
   unlocks). Finisher (`finish`, evaluator.rs:1089): takes the same lock, stores `Done`, unlocks,
   `notify_all`. The store cannot fall between the waiter's check and its enqueue. Sound.
   `Permits` (evaluator.rs:159-170) is the same pattern with one `notify_one` per release.
2. Permit balance. `wait_for` releases before blocking and reacquires after (1132/1142), and
   returns without touching permits on the cycle path. `eval_keys` releases only around the join
   (1283/1291); helpers acquire/release their own. `compute_on_fresh_thread` lends the parent's
   permit to the child, whose own release/acquire pairs are balanced. Every blocking point either
   holds no permit or lends it to exactly one running thread, so permit holders always make
   progress and a blocked thread reacquiring cannot deadlock.
3. Lock order. `waits` -> shard -> `node.state` in `find_cycle` and `compute_claimed`; `finish`
   and the waiter loop take `node.state` alone; `get_or_claim` takes a shard alone. No inversion.
   The `if let` guard at evaluator.rs:766 is dropped before `wait_for` (edition 2024).
4. Claim window. `get_or_claim` sets `InProgress{owner: A}` before `compute_claimed` pushes the
   key on `stack[A]`. `U` walking through that key in the window gets no edge
   (`position` is `None`). No cycle is missed: an ownership edge alone cannot close a loop,
   because `A` has no wait with `frames > index` until after the push, and that later wait runs
   its own check under the lock with all edges visible. Same argument for the hand-off window in
   `compute_on_fresh_thread` (owner still the parent, key on nobody's stack) and for the finish
   window (key popped at 833, `Done` at 1089).
5. Two threads closing one cycle (`T` owns A and asks B, `U` owns B and asks A). Both checks run
   under `waits`; the second one sees the first one's wait and returns the private `InCycle`
   entry. Exactly one detection.
6. Batch helper asks for the parent's inline key (the old false cycle). `P` at stack `[.., X]`
   (len F) pushes `(F, [k2])`, computes `k1` inline at index F. `H` computes `k2`, asks `k1`:
   walk `H -> k1 (P, F) -> waits of P with frames > F`: the batch wait has `frames == F`, skipped.
   No false cycle. If `k1` then asks `k2`: `P` pushes `(F+1, [k2])`, walk reaches `H`, whose wait
   on `k1` leads to `P`: real cycle, found by whichever waits second.
7. Batch contains the requester's own key (the deadlock fix). `X` asks `[Y, X]`: `rest = [X]`,
   the registration check at 1242 walks `P -> X -> owner P`, `closes_cycle`, the batch runs inline
   and `wait_for(X)` returns `InCycle`. With `[X, Y]`, `X` is `first` and `wait_for(X)` on `P`
   finds it. Without the check a helper with an empty stack (no check, evaluator.rs:1191) would
   block on `X` while `P` joins it.
8. Helper with an empty stack blocked on a batch key owned by `V`, `V` (transitively) waiting on
   `X` of `P`. Covered from both sides: if `V` waited first, `P`'s registration check finds it; if
   `P` registered first, `V`'s check walks `X -> batch wait -> key -> owner V`. A batch key claimed
   by `P` itself later (inside `first`'s subtree) makes the helper wait on a thread that is
   running, not blocked: no deadlock.
9. Soundness of "reached `me`" (evaluator.rs:1181) for any stack index: every frame of `me` is a
   dependency of the frame below it (inline call, or a batch key drained at index F under its
   requester at F-1), and `me`'s innermost wait blocks all of them. So a detected loop is a real
   dependency cycle, and every node that receives a private `InCycle` entry is on one. Stale wait
   entries (waiter woken but still in `permits.acquire`) point at `Done` nodes and add no edge.
10. Panic in a function: caught at evaluator.rs:819, node finishes `Aborted`, waiters wake,
    `aborting` stops new work, `evaluate` rethrows after `cleanup`. No hang on this path.

## Findings

### S1-1 keep_going catastrophe: the bubbling path is lost when a parent rethrows; `evaluate` panics

- Where: `Run::resolve`, evaluator.rs:964-973 (catastrophic throw dropped as "not the first
  error"), 977-987 and 995-1003 (the path is recognised only by `is_catastrophic()` of the child
  error), `construct_result` 1372-1384.
- Java: `J:AbstractParallelEvaluator.java:511-525` applies "not the first error, ignore" to nodes
  in normal evaluation. The parents of the catastrophic node are then re-run by
  `J:ParallelEvaluator.java:290-487`; a parent that throws gets
  `fromChildErrors(parent, {fromException(parentException)})` (433-447), whatever its
  `isCatastrophic()`, and the walk always ends at a root, so the result has an error and
  `maybeEnsureCatastrophe` succeeds. Real functions rethrow both ways:
  `ArtifactNestedSetFunction.java:103-140` and `CompletionFunction.java:485` keep the catastrophic
  bit; `PackageLookupFunction` wraps into a non-catastrophic exception.
- Scenario A (catastrophic rethrow; keep_going, any parallelism, deterministic). `cat` throws
  `SkyFunctionException::catastrophic`. Root `top` calls `get_value_or_throw(cat)`, gets `Err(e)`,
  throws its own catastrophic exception. `cat`: `compare_exchange` succeeds, committed.
  `top`: `e.is_catastrophic()`, `compare_exchange` fails, `return Aborted` (972). The only root
  is `Aborted`: `check_state!("No result for keys ...")` panics. Java returns
  `errorMap = {top}` and `catastrophe` set.
- Scenario B (non-catastrophic wrap; keep_going, parallelism 1, deterministic). `mid` catches
  `cat`'s error and throws a persistent non-catastrophic exception (exactly
  `catastrophe_bubbles_into_non_catastrophe`, one level deeper). Root `top` requests the batch
  `[mid, other]`, `other` not started. `mid`: `Bubbled`, with an error whose `is_catastrophic()`
  is false (981-986). `other`: claimed after `aborting`, `Aborted`. `top`: `catastrophic_child`
  is false, `aborted_dep` is true, `Aborted` (997-999). Same panic. Java re-runs `top` in
  bubbling and reports `fromChildErrors(top, {mid's error})` plus the catastrophe.
  This shape is live today: `file_state.rs:258-264` throws a catastrophic
  `InconsistentFilesystemException`, `package_lookup.rs:477-484` catches it and rethrows it as a persistent, non-catastrophic
  exception (as Java does), and
  every caller above requests batches.
- Also on this path: when no dep is aborted, the ancestors of a wrapped catastrophe are
  `Committed` (988, 1048) and memoized, with a dep edge to a `Bubbled` node that `cleanup`
  removes. Java commits nothing above the catastrophic node.
- Rule violated on the way: a panic from `construct_result` (evaluator.rs:508) skips
  `run.cleanup()` (509), so `Aborted`/`Bubbled` nodes stay in the graph for the next call.
- Fix direction: mark the bubbling path by node kind, not by the error's catastrophic bit: a node
  that observed the committed catastrophe or a `Bubbled` child is on the path. On the path,
  a thrower always becomes `Bubbled` with `from_child_errors(key, [from_exception(e, false)])`
  (no `compare_exchange`), a non-thrower becomes `Bubbled` with the child's error, and neither
  aborted nor in-cycle deps demote it. Run `cleanup` on every exit of `evaluate` (drop guard).
  Port a test for A and B.

### S1-2 no keep_going: every in-flight parent of a failed node observes the exception and has its stored events and posts reported; Java does that for one chain only

- Where: `unwrap_or_throw`, environment.rs:351-356 (the exception always propagates);
  `Run::resolve`, evaluator.rs:887-906, `listener.flush()` at 900; PORT comments at
  environment.rs:97-100 and evaluator.rs:1342-1345.
- Java: outside bubbling an errored dep is null and sets `valuesMissing`
  (`J:SkyFunctionEnvironment.java:649-653`, `handleError` 788-792), so no parent runs its catch
  block during normal evaluation, and the events of a run that returns null are discarded
  (`J:SkyFunction.java` `getListener` contract). `bubbleErrorUp` then re-runs exactly one parent
  per level, `Iterables.getFirst(reverseDeps)` (`J:ParallelEvaluator.java:342`), and reports only
  those runs' events (440-445, 480-485).
- Scenario (no keep_going, parallelism >= 2). Roots `p1`, `p2`; both call
  `get_value_or_throw(err)`, on `Err` emit `Event::error("p<i>: dep failed")` (or post a failed
  completion event) and throw. `err` throws once both parents are in flight: worker 1 computes
  `err` inline under `p1`, worker 2 is in `wait_for(err)`, or `p2` requests `err` just after it
  committed (it is `Done`, not a new claim, so `aborting` does not stop it). Both parents get
  `Err(e)`, both resolve `Bubbled`, both flush: the handler receives two error events and two
  posts. Java reports one. The result map hides it (only the first `Bubbled` root is reported,
  evaluator.rs:1346), and `no_keep_going_reports_one_bubbled_root_and_drops_aborted_roots` does
  not look at events. Consumers that emit in the catch block: "... and referenced by '//a:x'"
  errors in dependency resolution, `TargetCompleteEvent{failed}` in
  `blaze_sky_exec/src/completion_function.rs` near line 458 (dirty file) (two top-level targets on one failing
  action: Bazel posts one failed completion, Blaze one per in-flight target).
- Fix direction: do not flush on the `Bubbled` path. Keep the stored events and posts in the
  `Bubbled` `DoneEntry`; in `construct_result`, after choosing the reported root, walk its chain
  of `dep_error` children downward and report those nodes' events child first. Port
  `MemoizingEvaluatorTest.errorOnlyBubblesToRequestingParents`, `errorOnlyEmittedOnce`,
  `warningAndErrorOnFailFastBuild` and add a two-parent event test.

### S1-3 `in_error_bubbling()` is always false, so Java code guarded by `env.inErrorBubbling()` never runs although the function is doing exactly what Java does in bubbling

- Where: environment.rs:95-104; contract in PORTING.md ("`in_error_bubbling()` is always
  false"); test `in_error_bubbling_is_always_false` (tests.rs:1111) pins the deviation.
- Java: `J:SkyFunctionEnvironment.java:1036`. A dep's exception reaches a function without
  keep_going only when `bubbleErrorInfo != null` (788), that is only when `inErrorBubbling()` is
  true. `ParallelEvaluatorTest.runDepOnErrorHaltsNoKeepGoingBuildEagerly` (test file line 2679)
  asserts it: "child error propagated during normal evaluation ... that(env.inErrorBubbling())
  .isTrue()".
- Scenario (no keep_going, deterministic): `blaze build //pkg:all` where `pkg` loads but
  contains errors. Java `TargetPatternFunction.java:122-129`: in the bubbling re-run the provider
  catches `BuildFileContainsErrorsException`
  (`EnvironmentBackedRecursivePackageProvider.java:134-148`), the function completes, and
  `if (env.inErrorBubbling()) maybeThrowEncounteredException(...)` throws
  `TargetParsingException("Error evaluating '//pkg:all': ...", PACKAGE_NOT_FOUND)`; that is the
  TARGET_PATTERN node's error. Rust, ported literally at
  `blaze_sky_loading/src/target_pattern_function.rs:968-977`: the guard is false, the function
  returns a value, the engine discards it (evaluator.rs:892-897) and reports the child's raw
  `BuildFileContainsErrorsException`. The parent's `getOrThrow(key, TargetParsingException.class)`
  then does not match. Other Java users of the guard: `IncludeParser.java:311-371`,
  `CompletionFunction.java:248`, `SkyValueRetrieverUtils.java:52`.
- Fix direction: return `!keep_going && st.dep_error.is_some()` (the function has observed an
  errored dep, which in Java happens only in bubbling); update PORTING.md and the PORT comment;
  port `runDepOnErrorHaltsNoKeepGoingBuildEagerly`. Java also sets the thread's interrupt bit at
  that point (`J:SkyFunctionEnvironment.java:624-630`); making `check_interrupted()` return
  `Err` once `dep_error` is set would mirror it.

### S2-1 no keep_going: an error under a node of a cycle is always reported as the error; Java reports the cycle when bubbling runs into it

- Where: `construct_result`, evaluator.rs:1307 and 1352-1357 (`bubbled` suppresses the detector
  for good); `resolve` 887-906.
- Java: `J:ParallelEvaluator.java:343-349` ("Bubbled into a cycle ... Cycle detection will kick
  in", returns null, so `constructResult` runs the detector, 529-534).
  `ParallelEvaluatorTest.cycleAndErrorInBubbleUp`, `cycleAndErrorAndOtherInBubbleUp`,
  `cycleAndErrorAndError` (test file 1922-2082) require the cycle for `keepGoing=false`.
- Scenario (parallelism 1, deterministic in Rust): root `A` requests `B`; `B` requests the batch
  `[err, A]`. Rust: `err` commits its error, `A` comes back as the private `InCycle`, `B` has
  `dep_error`, `B` and `A` are `Bubbled`: result `{A: exception "err", no cycle}`. Java: bubbling
  goes `err -> B -> A -> B` (A's only in-progress rdep is B), returns null, the detector reports
  `{A: CycleInfo([], [A, B]), no exception}` (when `B` registered on `A` before `err` threw; the
  Java test pins that order with latches). Rust can never produce Java's answer.
- Fix direction: when the reported `Bubbled` chain passes through a node that also had
  `in_cycle_dep` and no root is reachable outside the cycle, fall back to the detector. Port the
  three tests.

### S2-2 `SkyframeLookupResult` only knows the keys of its own call

- Where: environment.rs:222-236 (`entries` = this call's keys), 426-430 (`Ok(None)`, values not
  marked missing; the comment says this is Java's "should never happen" case).
- Java: `getOrThrow` reads `maybeGetValueFromErrorOrDeps` (`J:SkyFunctionEnvironment.java:463-476,
  667-680`): every dep this environment requested by any earlier `getValue`/batch call. The bug
  report fires only for a key never requested at all.
- Scenario: a function calls `get_value(a)`, later `r = get_values_and_exceptions([b])`, and a
  shared helper reads `r.get(a)`. Java: the value. Rust: `None` with `values_missing() == false`;
  a function that returns `Ok(None)` on it panics with "failed and no dependencies were
  requested", one that treats `None` as optional computes a different value.
- Fix direction: resolve misses through `st.requested` (share it with the result).

### S2-3 A failed thread spawn after a claim leaves the node `InProgress` forever

- Where: `compute_on_fresh_thread`, evaluator.rs:784-794 (`.expect("spawn evaluator thread")`
  after `get_or_claim` at 759). The depth guard force-reserves beyond `max_threads`, so the
  number of live threads grows with dependency depth / `max_inline_depth` and is not capped.
- Interleaving: `P` claims `K`, spawn fails (EAGAIN, `TasksMax`, map count). The panic is caught
  by the catch_unwind of `P`'s enclosing function; `K` is never finished and is not in
  `uncommitted`. `U` already in `wait_for(K)` sleeps forever, `evaluate_roots` never joins: a hang
  where a crash was due. `P`'s wait entry and the reserved thread slot also leak.
- Fix direction: on spawn failure compute inline (or finish `K` as `Aborted` and record the
  crash) before unwinding.

### S2-4 Shape of bubbled errors differs from `bubbleErrorUp` in two corners

- A parent that does not throw: Rust `from_child_errors(key, [child's bubbled error])`
  (evaluator.rs:896-898); Java `fromChildErrors(key, {error})` with `error` the leaf failure or
  the last *thrown* error, not the intermediate wrapper (`J:ParallelEvaluator.java:298, 438,
  480-484`). Identical unless the leaf error carries cycles (a cached keep_going error reused
  without keep_going): Java's path to the cycle is `[grandparent, ...]`, Rust's
  `[grandparent, parent, ...]`.
- A function that throws for its own reason while an errored dep was merely requested is
  `Bubbled` (not memoized, `is_directly_transient` false); Java commits it as the first error
  (`J:AbstractParallelEvaluator.java:487-546`).

## What I checked and found faithful

`processDepValue` / `unwrapOrThrow` / `handleError` for keep_going (value with error returned,
cycle always marks missing, caught exception does not), including `get_value_or_throw_with` and
`get_or_throw_with`; dep groups and duplicate keys; `removeUndoneNewlyRequestedDeps`; the
keep_going "throw with missing deps is ignored" rule; `ErrorInfo.fromException` /
`fromChildErrors` / `withValue` and transitive transience; `ErrorTransienceValue` as last dep and
`invalidate_transient_errors`; `ParallelEvaluator.eval` shortcuts (all done; cached error roots);
`constructResult` for committed roots; `SimpleCycleDetector` (statement-for-statement, and the
blocking engine does leave a real cycle among the non-done nodes' recorded deps for it to find);
warning dedup (warnings are not stored, tagged before dedup, reported at once) and stored events
reported at commit, dropped for nodes that do not finish; no-replay under one command per process.
