## Findings

### S1: wrong output or wrong behaviour on valid input

**S1-1. Starlark flags on the command line and in `.bazelrc` are dropped without a message.**
- Rust: `blaze_runtime/src/dispatcher.rs:501` `exec_exclusively` (only a `// PORT:` comment where
  Java parses them; the parser is built with `skip_starlark_option_prefixes()` at :580 and
  `get_skipped_args` has no caller outside `blaze_options`). `BuildOptions::of`
  (`blaze_build_config/src/build_options.rs:150`) would call `unported!`, but it never sees them.
- Java: `runtime/BlazeCommandDispatcher.java:768`, `runtime/BlazeOptionHandler.java:417`
  `parseStarlarkOptions`.
- Scenario: `blaze cquery --//config:mode=fast //x` (or the line in `.bazelrc`, or a
  `--flag_alias`). Bazel changes the configuration, so `select()`/`config_setting(flag_values)`
  branches, `label_flag` targets, the configuration checksum and output paths change. Blaze
  analyses the default configuration and exits 0. Known as docs/workerd.md #13; still silent.
- Fix: port `StarlarkOptionsParser`; until then `unported!` when skipped args are non-empty.

**S1-2. All but two `BuildLanguageOptions` are ignored.**
- Rust: `blaze_build_config/src/top_level.rs:35` `starlark_semantics_from`, used by
  `blaze_sky_top/src/skyframe_executor.rs:166` `SkyframeExecutor::create` for loading, bzlmod,
  repository rules and analysis.
- Java: `skyframe/SkyframeExecutor.java:1722` (`BuildLanguageOptions.toStarlarkSemantics`).
- Scenario: `--incompatible_autoload_externally=...`, `--nocheck_bzl_visibility`,
  `--experimental_platforms_api`, any `--incompatible_*`
  Starlark flag: Bazel honours it, Blaze keeps the default and says nothing.
- Fix: port `toStarlarkSemantics` in full (the key/value table already exists in
  `blaze_optdefs/src/command/build_language_options.rs:1447`).

**S1-3. `Args` and `TemplateDict` are read after the rule returns instead of at the action call.**
- Rust: `blaze_analysis/src/starlark/starlark_action_factory.rs:594` `build_command_line` keeps the
  live value (`keep_alive_push`, :607); `finish_pending_actions` (:1779) calls `build_args` on the
  frozen value. Same for `write(content = args)` and `expand_template(computed_substitutions)`.
- Java: `analysis/starlark/StarlarkActionFactory.java:695` `buildCommandLine` calls `args.build()`
  at the call; `analysis/starlark/StarlarkCustomCommandLine.java:882` copies `arguments.toArray`.
- Scenario: `a = ctx.actions.args(); a.add("x"); ctx.actions.run(arguments = [a], ...);
  a.add("y"); ctx.actions.run(arguments = [a], ...)`. Bazel: first action `[x]`, second `[x, y]`.
  Blaze: both `[x, y]` (wrong argv, wrong action key). Also `use_param_file` set afterwards.
- Fix: snapshot the Args state (and TemplateDict entries) when the action is recorded.

**S1-4. Incompatible top-level targets are neither rejected nor skipped.**
- Rust: `blaze_sky_top/src/build_view.rs:227` `update` (`targets_to_skip` is always empty; the
  PORT comment says so), `analysis_phase_runner.rs:89` `run_analysis_phase`;
  `BuildRequest.report_incompatible_targets` (`build_tool.rs:57`) is stored and never read.
- Java: `analysis/BuildView.java:468` (`TopLevelConstraintSemantics`).
- Scenario: `aquery //pkg:t` or `build //pkg:t` with
  `target_compatible_with = ["@platforms//:incompatible"]`: Bazel fails with "Target //pkg:t is
  incompatible and cannot be built, but was explicitly requested."; Blaze exits 0. With
  `build //pkg/...` Bazel skips and reports the target; Blaze does not skip it.
- Fix: port `TopLevelConstraintSemantics`, or `unported!` when a top-level target carries
  `IncompatiblePlatformProvider`.

**S1-5. `--output_file` is parsed and ignored by cquery and aquery.**
- Rust: `blaze_cquery/src/cquery/cquery_options.rs:142` copies it; nothing reads it
  (`PostAnalysisCommandEnvironment.output` always writes stdout).
- Java: `query2/common/QueryRuntimeHelper.java:72`.
- Scenario: `cquery //x --output_file=out.txt`: Bazel writes the file and prints nothing; Blaze
  prints to stdout and writes no file.
- Fix: port the file helper or `unported!` when the option is set.

**S1-6. CppCompile execution info loses the tag order.**
- Rust: `blaze_rules/src/cpp/cc_starlark_internal.rs:114` `target_execution_info` feeds
  `java_hash_map_order` with the keys of a `BTreeMap`
  (`blaze_packages/src/target/target_utils.rs:273` `get_execution_info`), so tags that share a
  `HashMap` bucket come out sorted instead of in attribute order.
- Java: `packages/TargetUtils.java:243` (tags put into a `HashMap` in attribute order, then
  `ImmutableMap.copyOf`), kept by the `LinkedHashMap` in `rules/cpp/CppCompileActionBuilder.java:71`.
- Scenario: `cc_library(srcs = ["x.cc"], tags = ["no-remote-exec", "no-remote"])`. Both keys land

  no-remote-exec`. aquery `executionInfo` order and the action key differ. Same for
  `["no-cache", "exclusive"]` (bucket 9) and `["no-sandbox", "no-asan"]` (bucket 4).
- Fix: return the legal tags in attribute order (deduplicated) from `get_execution_info`.

**S1-7. `HeaderInfo`, the cc toolchain variables, `CppConfiguration` and every fragment value are

- Scenario: rules_rust `depset(deps)` over structs that hold a compilation context

  hashable" (a Starlark error, not an `unported!`). `{ctx.fragments.cpp: 1}` likewise.
- Fix: identity `write_hash` on the `Arc` address.

**S1-8. aquery `rdeps` is filtered where Bazel does not filter.**
- Rust: `blaze_cquery/src/post_analysis_query_environment.rs:663` `filter_reverse_deps` tests
  `get_configured_target()` for both node types.
- Java: `query2/PostAnalysisQueryEnvironment.java:348` tests
  `parent.dependency instanceof RuleConfiguredTarget`, never true for aquery's
  `ConfiguredTargetValue`.
- Scenario: `aquery --noimplicit_deps 'rdeps(//a/..., //a:tool)'`: Blaze drops rdeps Bazel keeps.
- Fix: make the test specific to the cquery node type.

**S1-9. The `run_shell` helper script action is registered before every pending action.**
- Rust: `starlark_action_factory.rs:1495` `run_shell` (the PORT comment states it) through
  `rule/command_helper.rs` `command_helper_script_maybe`.
- Java: `analysis/starlark/StarlarkActionFactory.java:640` registers it in place.
- Scenario: `ctx.actions.write(a, "x")` then `run_shell(command = <more than 64000 chars>)`:

**S1-10. `print()` inside a transition implementation prints nothing.**
- Rust: `blaze_build_config/src/starlark_transition.rs:1166` `evaluate_with_attrs` runs the

- Fix: route `debug` to the handler passed to `evaluate_with_attrs`.

**S1-11. `config_setting(flag_values)` converts int build settings with the wrong parser.**
- Rust: `blaze_rules/src/config/config_setting.rs:598` `convert_build_setting_value`
  (`value.trim().parse::<i64>()`).
- Java: `analysis/config/CoreOptionConverters.java:109` `StarlarkIntConverter`

- Scenario: `flag_values = {"//:level": "0x10"}` with the flag at 16: Bazel matches, Blaze reports

**S1-12. `--experimental_use_validation_aspect` is ignored. (sub)**

### S2: deviations masked today

**S2-1. Action conflicts between targets and artifact prefix conflicts are never reported.**
`blaze_sky_top/src/skyframe_build_view.rs:115` `configure_targets` computes only the statistics
(PORT comment); Java `skyframe/SkyframeBuildView.java:428-500`, `actions/Actions.java:320`
`findArtifactPrefixConflicts`. Two targets of one rule that both
`declare_file("out.txt")` in a package: Bazel "file 'p/out.txt' is generated by these conflicting
actions", Blaze builds. Outputs `x` and `x/y`: same. Conflicts inside one target are loud
(`actions_util.rs:122` `verify_generating_action_keys`). Fix: port `ArtifactConflictFinder` or
`unported!` on the first conflict.

**S2-2. Starlark list option values would hash differently from Bazel.**
`blaze_build_config/src/build_options.rs:82` `StarlarkOptionValue::java_to_string` prints every
list as `[a, b]`. A value set by a transition is a `StarlarkList` in Java, whose `toString` is the
Starlark repr `["a", "b"]` (`net/starlark/java/eval/StarlarkList.java:272`); it feeds
`BuildOptions.checksum` (`analysis/config/BuildOptions.java:180`,
`com/google/devtools/common/options/OptionsBase.java:96`) and the ST hash
(`analysis/config/OutputPathMnemonicComputer.java:366`). A transition returning
`{"//:copts": ["-DX", "-DY"]}` gives another configuration id and output directory. Masked: any
configuration with a Starlark option stops at
`unported!("BuildConfigurationKeyProducer.findBuildOptionsScopes")` (`skyframe.rs:309`). Fix:
keep the Java class (ImmutableList vs StarlarkList) in the value.

**S2-3. At-default detection of allow-multiple settings differs from Java.**
`blaze_analysis/src/config/starlark_transition.rs:361` `validate_and_check_if_at_default`
(:409) compares the converted list with `[default]`; Java
(`analysis/starlark/StarlarkTransition.java:238`) compares it with
`ImmutableList.of(buildSettingToDefault)`, which is already a list
(`skyframe/StarlarkBuildSettingsDetailsFunction.java:93`), so the Java comparison is never true
and the option stays in the configuration. With `config.string(flag = True, allow_multiple =
True)` and a transition returning `[default]`, Blaze removes the option and Bazel keeps it
(different checksum). The Rust comment misreads the Java. Masked as S2-2.

  to run(), parameter 'x'" prefix. (sub)
- `post_analysis_query_environment.rs:1033`: universe-scope error prefixed "Evaluation of query

## The probe change

- The script now compares full normalised transcripts step by step. It still drops blank
  stderr lines and progress lines (including `[n / m]` lines, which carry `progress_message`
  text), normalises durations, and for `aquery` steps sorts inputs and outputs and turns env
  into a map. The `--messages` view sorts messages and drops every `discarding analysis cache`
  warning. A Blaze step missing from `ORACLE.txt` prints DIFF without changing the count or the
  exit status; not active now (step counts agree in all 35 scenarios).
- Counts from the oracle transcripts: 694 steps, 600 of which run the binary; 94 are `cat` /
  `stat`. `Critical Path:` is in 510 steps (206 of them failing, so not only successful builds).
  `Starting local Bazel server` is in 36 steps; the other 564 binary steps would differ if Blaze
  prints it each time. `INFO: 1 process: 1 internal.` is on 118 failing steps. 63 steps have a
  traceback; 5 are the `hasattr` / `getattr` steps.
- So the reported numbers are consistent with the listed causes: causes (1)-(3) touch 599 of
  the 600 binary steps, and 94 equals the number of `cat` + `stat` steps. In the message view
  causes (2) and (3) touch 468 binary steps, leaving at most 226; 225 was reported.
- Cause (2) is real but misdescribed. The probe does not kill a server (no `--max_idle_secs`,
  one `shutdown` at the end, the same scope launcher for both binaries). Blaze has no persistent
  server at all until W8 (`blaze_client/src/blaze.rs`; decisions.md 2026-11-18), so every
  command starts one. Blaze's probe output bases hold one server log per step, the oracle's one
  per scenario. Ownership outside the analysis crates holds for (1)-(3); (4) is the vendored
  interpreter.
- Analysis-owned mismatches that the code predicts: the five S2-7 steps, the `graph-order` line
  (R2-3), `ctx-toolchains-string` step 6 (S2-8). Whether there are others cannot be told: in
  468 of 600 binary steps, including 277 of the 384 that carry ERROR / WARNING / DEBUG lines,
  neither view can confirm analysis-owned text today.
- Recommendation: add a view that masks exactly the three non-analysis line classes (the
  Elapsed / Critical Path line, the server-start and packages-loaded lines with the
  `discarding analysis cache` warning, the process-count line) and keeps order and all other
  text; and have `compare` write Blaze's transcript next to `ORACLE.txt` (or under
  `~/.cache/blaze`) with the binary's hash, so the count can be checked.
