## Findings

### S1

**C1. SIGTERM/SIGHUP skips the worker and cgroup shutdown hooks: the server's cgroup and its
workers are left behind.**
Rust: `crates/blaze_runtime/src/jvm_signals.rs:90-98` runs only
`blaze_server::shutdown_hooks::run_registered_shutdown_hooks()` (pid file, server info files) and
then `libc::_exit`. The worker hooks and `VirtualCgroup::delete_instance` are registered in a
different list (`crates/blaze_exec/src/worker/shutdown_hooks.rs:57-70`,
`cgroups/mod.rs:269`) that only a C `atexit` handler runs, and `_exit` does not run `atexit`
handlers. Java: `VirtualCgroup.java:94` and `SingleplexWorker.addShutdownHook` use
`Runtime.addShutdownHook`; on SIGTERM/SIGHUP the JVM runs every registered hook before it halts.
Input: any build with default flags on a host where the parent cgroup is writable (systemd user
session with delegation), then `kill -TERM <server pid>`. Bazel removes
`…/blaze_<pid>_spawns.slice` (and destroys its workers first or concurrently); Blaze leaves the
directory, every `worker_<id>.scope` under it, and the worker processes alive. Not probed (suite
running); the two hook lists and the `_exit` are unambiguous.
Fix: the signal path (and any other path that stands for `Shutdown.exit`) must run the
`blaze_exec` hook list too, before `_exit`; one list for both is simplest.

### S2

**C2. `BlazeRuntime.<init>` does not create the server cgroup.** Java
`runtime/BlazeRuntime.java:268` calls `VirtualCgroup.getInstance()` at server start, so every
server on Linux creates `blaze_<pid>_spawns.slice` and writes `cgroup.subtree_control` of the
parent, whatever the command. Blaze calls `get_instance()` only from
`worker_module.rs:169/257` and `linux_sandboxed_spawn_runner.rs:100`, so `info`, `query`,
`version` and the like never create it, and there is no `// PORT:` note or `unported!` for it.
Masked: nothing in the corpus looks at the cgroup tree. Fix: call it where the runtime is built
(and keep `getCgroupsInfo`), or record the deviation.

**C3. Shutdown-hook order is a Blaze invention.** `shutdown_hooks.rs:83-95` runs hooks one after
the other, newest first. Java's `Runtime` hooks (`ApplicationShutdownHooks`) are started all at
once as threads, in no order, and joined; Bazel adds no order of its own (its ordered
`lib/server/ShutdownHooks` is a separate object for files). So "newest first" is neither Java's
nor Bazel's behaviour. It is declared as `PORT:` and its effect is a superset of Java's good
outcome (the worker is dead before its cgroup is removed, where Java races and may leave the
directory with EBUSY), so it does not block; it needs an entry in `docs/decisions.md`. Two
details: the doc comment at `shutdown_hooks.rs:81-82` still says "in registration order", and
the order only helps when the cgroup hook was registered before the workers' hooks (true today
because `WorkerModule.buildStarting` calls `get_instance()` before any worker exists; it would
also be true by construction after C2).

### S4

- `read_lines` (`mod.rs:55`) does not split on a lone `\r`; `Files.readLines` does. `/proc` never
  contains one.
- `Mount::parse_line` (`mod.rs:111`) cannot produce Java's match with an empty `file` group
  (`dev␠␠cgroup2 rw`); not a real `/proc/self/mounts` line.
- `SandboxOptions::get_limits` comment says `buildKeepingLast` keeps the position of the first
  occurrence; Guava keeps the last. Only lookups read the map, so no effect.

## Questions of the task, answered

- Parsing: `/proc/self/mounts` (not `mountinfo`) and `/proc/self/cgroup`, as Java. Hybrid mounts,
  missing controllers, duplicate controller keys (`IllegalArgumentException` → panic), the
  `/../..` paths of a cgroup namespace, `String.split` trailing-empty rules and the v2 "go up one
  level" rule match the Java line by line.
- No permission: a non-writable cgroup is recorded in `CgroupsInfo` and skipped; an `IOException`
  from `cgroup.controllers`, `cgroup.subtree_control` or a controller file makes `createInstance`
  return NULL; `mkdirs` failures are ignored. Same as Java. Messages are log-only in Java and are
  not printed by either.
- Controllers enabled on the parent: every controller listed in the parent's
  `cgroup.controllers`, written as `+a +b ` in one write before each child `mkdir`, only when
  `subtree_control` is writable and `controllers` readable; once per controller object (so twice
  per child when both memory and cpu exist). Same as Java.
- Creation and removal: child registered in the parent's list and in the factory map before the
  limits are written; `remove` destroys children then `rmdir`s; sandbox cgroups are removed in
  `verifyPostCondition` only (so, as in Java, a failed or interrupted spawn leaves its
  `sandbox_<id>.scope` until `cleanupSandboxBase`/exit calls `deleteInstance`). After SIGKILL or a
  crash both leak; after SIGTERM only Blaze leaks (C1).
- Limits: memory in bytes (`MB * 1024 * 1024`, truncated), v2 also `memory.swap.max = 0`; cpu as
  `round(cpus * period)` with the period read back from `cpu.max` / `cpu.cfs_period_us`; `max`
  in `cpu.max` reads as "all processors". Same as Java.

## Open items (do not block)

- `linux_sandboxed_spawn_runner.rs:334` turns the `ExecException` of `spawn.getLocalResources()`
  into an `io::Error`; Java lets it propagate as `ExecException`. Reachable only with
  `--experimental_sandbox_enforce_resources_regexp` and a failing `resource_set` callback that
  did not already fail in the resource manager.
- `destroy_and_wait_at_exit` kills with SIGKILL after 10 s where Java waits without limit
  (declared `PORT:`, older than this change).
