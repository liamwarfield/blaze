## Findings

### S1

**F1. `run` prints `, Critical Path: 0.00s` when the target validator rejects the targets.**

- Rust: `crates/blaze_runtime/src/commands/build.rs:860-870` initialises the build summary
  statistics when `target_patterns_were_evaluated` (`build.rs:1217-1238`) is true. That function
  only asks whether the `TARGET_PATTERN_PHASE` node is done without error. The validator runs
  after that node (`crates/blaze_sky_top/src/build_tool.rs:831-842`), so a validator failure
  still counts as "patterns evaluated". The same predicate also guards `build.rs:799-852`
  (sets empty target sets on the build result and calls the result printer).
- Java: `buildtool/BuildTool.java:488-491` calls `validator.validateTargets` inside
  `evaluateTargetPatterns`. Its `LoadingFailedException` leaves `buildTargets` before
  `buildTargetsWithMergedAnalysisExecution` (`BuildTool.java:613`), where the `ExecutionTool`
  is created and `BuildSummaryStatsModule.executorInit` sets up the critical path computer.
- Input: `run //pkg:not_executable`, `run //pkg:all` with more than one target, or a pattern
  that matches nothing (`RunCommand.java:1064-1105`).
- Evidence: `run-compare/audit4-run/{oracle,blaze}/brotli/not-executable.stderr` and
  `two-targets.stderr`:
  - oracle: `INFO: Elapsed time: 0.063s`
  - Blaze: `INFO: Elapsed time: 0.746s, Critical Path: 0.00s`
  The other lines and the exit code (2) agree. `build.rs` and `build_tool.rs` are unchanged on
  this path between `f58ddb4` and `e8b79c0` (`git diff f58ddb4 e8b79c0`, no hunk touches the
  predicate, the executor-init block or the validator call).
- Not checked: whether the block at `build.rs:799-852` changes the build event stream in this
  case (Java leaves the result's target sets null).
- Fix expected: `BuildTool.process_request` reports whether `evaluate_target_patterns` returned
  normally (validator included), and `build.rs` uses that instead of the graph lookup. Then
  re-run the three `run` cases against the oracle.

### S2

**F2. Order of repeatable sub-flags in an expanded policy is taken as arbitrary; it is not.**

- Rust: `crates/blaze_options/src/invocation_policy.rs:563-568` groups repeatable sub-flags in
  first-appearance order. The comment says Java's key order is arbitrary because
  `OptionDescription.hashCode` is the identity hash.
- Java: `common/options/InvocationPolicyEnforcer.java:356-405` iterates
  `ArrayListMultimap.keySet()`, a `HashMap` order. `OptionsParser.java:417-419` defines
  `OptionDescription.hashCode` as `optionDefinition.hashCode() + evaluatedExpansion.hashCode()`,
  and `FieldOptionDefinition.java:376-378` returns `field.hashCode()` (class name hash XOR
  field name hash). The order is deterministic.
- Masked: it needs a `SetValue` policy on a flag whose direct expansion or implicit
  requirements name two or more different `allowMultiple` flags. I found none at the pin in a
  search of the common repeatable flags (the Android and Java expansions each name one).
- Effect when it happens: order of the policies in `canonicalize-flags --canonicalize_policy`,
  of the invocation-policy flag list, and of enforcement.
- Fix expected: reproduce the `HashMap` order (`help.rs` already has `JavaHashMap`), or fail
  with `unported!` when the map has more than one key; correct the comment either way.

**F3. Project-file flags: the command's parser is not updated, and a parse error is softened.**

- Rust: `crates/blaze_runtime/src/project_options.rs:86-133` parses the project's flags in a
  new parser and copies the results into the `BuildOptions`. On a parse error
  (`project_options.rs:71-79, 93-95, 158-160`) it reports `ERROR: <message>` and returns an
  `InvalidConfigurationException` with `INVALID_BUILD_OPTIONS`.
- Java: `buildtool/BuildTool.java:352-374` parses them into the command's own `OptionsParser`
  at `COMMAND_LINE` priority, then posts `CanonicalCommandLineEvent` and `UpdateOptionsEvent`.
  An `OptionsParsingException` there is caught by no specific clause of `processRequest`; it
  reaches `catch (Throwable)` (`BuildTool.java:1002-1006`) and is rethrown as
  `IllegalStateException`, a crash (exit 37). `FlagSetFunction.java:205-232` checks flag names
  only, not values.
- Inputs that differ:
  - `PROJECT.scl` with a bad value, for example `--compilation_mode=bogus`: Bazel crashes,
    Blaze exits 2 with an error. I could not probe this; the reading of the Java is the
    evidence.
  - Code that reads the parser after project resolution sees different values. In `run` on a
    test, `run.rs:1000-1006` compares the action's runfiles setting with
    `options.get_options::<CoreOptions>().build_runfile_links`; with `--nobuild_runfile_links`
    in the project file Java's parser holds false, Blaze's holds true, and the `check_state!`
    panics. `run.rs:1173-1176` (`--run_under`) has the same shape.
- Masked today: needs a project file with flags; none in the corpus.
- Fix expected: parse into the command's parser as Java does (or make the applied values
  visible to `env.get_options()`), and let the parse error take Java's path.

**F4. `mod` drops the cycle report.**

- Rust: `crates/blaze_runtime/src/commands/mod_command.rs:134-145`. The `CyclesReporter` is not
  ported (a `PORT:` comment says so) and the code continues with the generic message.
- Java: `bazel/commands/ModCommand.java:296-303` reports the cycle through
  `BzlmodRepoCycleReporter` and `BzlLoadCycleReporter` first.
- Input: `mod graph` in a workspace whose module extensions or `.bzl` loads form a cycle. Bazel
  prints the cycle, then `Unexpected error during module graph evaluation.`; Blaze prints only
  the last line. Exit code is the same.
- Fix expected: port the two reporters, or `unported!` when the error has cycle information.

**F5. Unknown fields of a binary invocation policy are dropped.**

- Rust: `invocation_policy.rs:129-138` (stated in a `PORT:` comment).
- Java: `InvocationPolicyParser.java:36`; protobuf-java keeps unknown fields and
  `toString()` prints them.
- Input: a base64 policy with a field this version does not know, with
  `--canonicalize_policy`, or with a `config` policy (the error text prints the policy,
  `InvocationPolicyEnforcer.java:253-260`).
- Fix expected: carry the unknown field set through, or `unported!` when one is present.

**F6. An interrupted `fetch` posts `NoBuildRequestFinishedEvent`; Java does not.**

- Rust: `commands/fetch.rs:131-133` (stated in a `PORT:` comment).
- Java: `bazel/commands/FetchCommand.java:133-136` returns from the `catch` before the post.
- Effect: one extra build event on an interrupted `fetch` with a build event file.

## Checked and found matching

- **`run`**: target and argument split, `--run_under` as command and as label, the working
  directory choice (`--run_in_cwd`, runfiles directory, exec root for tests), the four `BUILD_*`
  variables, `--run_env` set, inherit and unset with the five variables cleared always, the
  batch-mode overlay of the client environment, shell quoting in the argv and in the script,
  `--script_path` (written or returned in the request), `--norun`, `--subcommands`, the test
  path (one status artifact, test environment, `prepare`, test arguments), every message,
  `FailureDetails.RunCommand` code and the "Will continue anyway" warning. Of the 20 recorded
  cases, `args` and `re2-test` are identical. Thirteen (`exit-code`, `env`, `subdir`,
  `run-in-cwd`, `show-args`, `run-under-cmd`, `run-under-label`, `script-path`, `run-false`,
  `subcommands`, `test-target`, `build-fails`, `no-target`) are classed by
  `scripts/run/compare` as differing only in warm-server lines; that is the tool's verdict
  (the tool is still waiting for its audit re-check), I did not diff those thirteen by hand.
  Five are different: the two of F1, and `batch`, `re2-test-args`, `re2-runs-per-test`, whose
  raw stderr I read; they differ in server-restart and cold-server warnings, package counts,
  progress lines and times, not in anything `run` prints.
- **`help`**: all 81 recorded forms have identical stdout (index, every command at three
  verbosities, `startup_options`, `target-syntax`, `info-keys`, `completion` with and without
  `bash`, `flags-as-proto`, `everything-as-html`, the three error cases). That covers the
  category order, the option order, `paragraphFill` over every help text at the pin, and the
  `HashMap` order of `flags-as-proto`.
- **Invocation policy**: parsing (base64 first, text second, Guava's whitespace and padding
  rules), `--config` rejection, command filtering through the command-name cache, expansion
  and implicit requirements, "last policy per flag keeps its first position", the four
  `SetValue` behaviours, `UseDefault`, `AllowValues` and `DisallowValues` with new value and
  use-default, every error text, and the position of enforcement (after `editOptions`, before
  the warnings). The 48 recorded `canonicalize-flags` policy cases and the 15 startup-option
  policy cases (`info`, `build`, `version`) have identical stdout and exit code; their stderr
  differs only in timer-driven progress lines.
- **`canonicalize-flags`**: `--for_command`, residue and alias handling, Starlark flags,
  failure codes. 68 of the 69 recorded cases have a Blaze side and all 68 are identical
  (`in_brotli` has only the oracle side), including the crash outside a workspace, which Bazel
  has too (exit 37 on both sides; the stack trace text differs).
- **`mod`**: order of validation and evaluation, `show_repo` evaluation and output paths,
  `dump_repo_mapping`, `tidy`, the "Type '... help mod'" suffix rule, interrupt results.
- **`fetch`**, **`license`**, the response-proto handler of `info`, crash handling: match,
  apart from the findings above. The 33 recorded `fetch` cases agree in stdout and exit code
  (stderr differs in progress lines and elapsed time); the two `license` outputs differ only in
  the install-base path printed before each JDK license file.
