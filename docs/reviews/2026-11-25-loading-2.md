## Findings

### S1

**F1. `load()` of a symbol the file does not define prints starlark-rust's text. BLOCKING.**

- Rust: `third_party/starlark-rust/starlark/src/environment/modules.rs:632` `load_symbol` calls
  `get_any_visibility` (`:253`), whose errors are `EnvironmentError::ModuleHasNoSymbol` /
  `ModuleHasNoSymbolDidYouMean` / `ModuleSymbolIsNotExported` (`environment.rs:43-48`):
  "Module has no symbol `x`", "Module has no symbol `x`, did you mean `y`?", "Module symbol `x`
  is not exported". Nothing in `crates/` rewrites them; the string "does not contain symbol"
  occurs nowhere in `crates/` or the vendored sources.
- Java: `net/starlark/java/eval/Eval.java:264-270` execLoad:
  `file '%s' does not contain symbol '%s'%s` with
  `SpellChecker.didYouMean(name, module.getGlobals().keySet())`, located at the original name.
- Input: `a.bzl` with `foo = 1`; a BUILD or .bzl file with `load(":a.bzl", "fooo")`.
  Bazel: `file ':a.bzl' does not contain symbol 'fooo' (did you mean 'foo'?)`.
  Blaze: `Module has no symbol ...`. Second input: `b.bzl` does `load(":a.bzl", "foo")`, a third
  file does `load(":b.bzl", "foo")`. Bazel: the same "does not contain symbol" text (load
  bindings are file-local, `getGlobal` is null). Blaze: "Module symbol `foo` is not exported".
- Bookkeeping: `docs/starlark-errors.tsv` row `eval/Eval.java:267` has status `no-case` and an
  empty note; the guard list carries the three texts as "REVIEW: not yet classified". A typo in
  a load statement is among the most common user errors, and PORTING.md's rule is Bazel's text
  everywhere.
- Fix expected: a patch in the queue that makes `load_symbol` produce Java's text (file name as
  written in the load statement, suggestion over all globals of the loaded module through
  `spell_checker::did_you_mean`, location at the original name), for the missing and the
  load-bound case; the tsv row `matched` with a recorded case; the three guard rows removed.

### S2

**F2. A doc comment token in a syntax error prints the token kind, not the comment.**
`syntax/java/parser.rs:100-110` `token_string` falls to `kind.to_string()` for
`TokenValue::DocComments`, with the comment "its toString is not used by Bazel's error paths that
reach a user". It is: Java `Parser.tokenString` (Parser.java:188) prints `value.toString()`, and
`DocComments.toString` joins the comment lines. Input (any .bzl or BUILD file): `x = #: doc`.
Bazel: `syntax error at '#: doc': expected expression`. Blaze:
`syntax error at 'trailing #: ': expected expression`. Same for `if x #: doc` (`expected :`).
Fix: keep the comment text in the token value and print it.

**F3. `macro()`: order of checks differs from Java when two things are wrong.**
`starlark_defs/macro_function.rs:537-551` reports the dict type error ("got dict<string, int>
for 'attrs', want dict<string, Attribute|None>") before `check_attribute_name`; Java
(StarlarkRuleClassFunctions.java:432-437) casts the key, calls `checkAttributeName`, then casts
the value. Input: `macro(implementation = f, attrs = {"bad name!": 5})`: Bazel reports the
invalid attribute name, Blaze the dict type. Also `:519-527`: the `attrs` type check runs after
the flag check and `BzlInitThreadContext.fromOrFail`; in Java the parameter type check comes
first. Fix: reorder to Java's.

**F4. Spelling suggestion ties can be nondeterministic.**
`syntax/java/resolver.rs:378-386` `get_all_symbols` feeds `java_hash_set_order` from
`b.bindings.keys()` and `self.toplevel.keys()` of `std::collections::HashMap` (random iteration
order). `java_hash_set_order` keeps insertion order inside a bucket, so two equally near
candidates that land in one bucket come out in random order; Java's order there is the
insertion order of its `HashMap`s. Rare (needs a tie and a bucket collision), but the output of
"did you mean" can change between runs. Fix: `IndexMap` for `Block::bindings` and `toplevel`,
and feed them in Java's iteration order.

**F5. `java_regex`: `find()` spans differ from Java for a repeated group whose earlier
alternative (or inner quantifier) can match empty.**
`crates/blaze_util/src/java_regex.rs:445-464` writes every repetition as `(?:body){min,max}`;
`docs/java-regex.md` ("Matching") states that `find()` spans agree. Java ends a loop when an
iteration matched empty and then takes the continuation (`Pattern.Loop.match`, the
`i > locals[beginIndex]` test), before trying later alternatives. JDK 25, run for this review:
`(?:a*|b)*` on `abab` finds (0,1); `(?:[a-c]*|d)+` on `abcdabc` finds (0,3); `(?:\s*|#.*)*` on
`"  # x"` finds (0,2). The `regex` crate's leftmost-first automaton prefers the non-empty
alternative over leaving the loop and matches the whole input in each case. The crate side is
derived from its compilation of nullable repetitions (and its `(?:|a)*` test row), not executed:
no Cargo in this review. Boolean results (`is_match`, `matches`) are not affected; the span is
used by `blaze_remote/src/scrubber.rs:281` (`transformArgument`), where it decides what is
replaced and so the action key. Fix: add these rows to `JavaRegexRows.java`; if they differ as
derived, go LOUD in `Mode::Find` for a repetition whose body can match empty other than as its
last choice, or restrict the doc's claim and the span API.

**F6. The "want" part of parameter type errors is guessed for every builtin outside a short
list.** `third_party/starlark-rust/starlark/src/values/unpack.rs:352-402` `java_allowed_types`
derives the list from starlark-rust's type display, renames a few names and moves `NoneType`
last ("Java's usual order"). Java prints `@Param(allowedTypes)` in declaration order with
`Starlark.classType` names (ParamDescriptor.java:123-144), e.g. `sequence` for a parameter that
starlark-rust types as `list | tuple`, and Bazel's class names for its own types. The format
("a or b", "a, b, or c") matches. Every Blaze `#[starlark_module]` function that relies on the
derived text instead of an explicit `param_type_error` is exposed. Not shown with a failing
input here. Fix: carry Java's allowed-type list per parameter (the transcription already has
the `@Param`), or check the texts of the ported builtins against the Java annotations with a
script.

## Checked and found equal

- Scanner: indentation and dedent accounting (tabs count 1 and report at `pos` after the tab,
  `\r` skipped, blank and comment lines), the two-char operator quirk (`pos + 2 >= length`),
  string escapes (octal range and the ASCII-only checks, `\` + CRLF in raw and cooked strings,
  unknown escapes kept as `\c`), unclosed strings, `r"\` at end of file, number scanning with
  both errors for `0x`, octal and binary messages through `IntLiteral.scan`, float errors,
  doc-comment blocks, end-of-file NEWLINE and OUTDENT synthesis. Offsets are char offsets and
  columns are chars (the source is an internal string), as Java's.
- Parser: every production, `syncTo`/`syncPast`, recovery mode set and cleared at the same
  points, the five-error cap counting parser errors only while scanner errors go to the same
  list uncapped, forbidden keywords on every token, `not in` by mutating the token kind,
  string-literal folding, token text for ints (decimal) and floats (`Double.toString`).
- Resolver: load placement, private and duplicate load symbols, global/file-local conflicts,
  top-level rebinding, parameter order and duplicates, call argument order errors, top-level
  `if`/`for`/`return`, `break`/`continue` (no reset of the loop count in nested defs, as Java),
  comprehension scoping, "contains syntax errors" for error identifiers, `cannot assign to`
  with Java's abbreviated printer.
- BUILD checks: same messages, same traversal order; BUILD parse errors alone, then the
  checker's alone, then the resolver's; .bzl parse errors followed by resolver errors.
- Two front ends: patch 0037-0048 and the conformance test address the known lexer
  differences (tabs inside brackets, `\r`, `async`/`await`, number forms). A file the Java
  front end accepts and starlark-rust rejects surfaces as starlark-rust's first error with its
  location (`eval.rs:229-243`); I found no such input by reading, and the agreement test covers
  the corpus, `@bazel_tools` and Bazel's builtins. It does not cover adversarial files.
- Macros: attribute validation order in `instantiateMacro` (unknown attribute with suggestion
  over documented attributes, `None` skipped, implicit attribute, visibility lift and
  concatenation with the instantiating package, normalization, missing `name`, same-name depth),
  the non-finalizer-in-finalizer check, eager expansion and `markMacroComplete`, finalizer
  expansion order and the rules snapshot taken once before the first finalizer, the call-stack
  prefix for errors starting in a .bzl file, the non-None return error, the recursion message.
- PackageFunction with package pieces: exception mapping, the three error branches and their
  texts.
- AutoloadSymbols constructor: expansion of `@repo` entries, validation, the three symbol
  lists, the rdeps check and its messages.
- Regex classes: union on the right of `&&`, chained `&&`, `[^a&&b]`, `[a&&]`, `[&&a]`,
  `[a-\d]`, CIRange and CIRangeU against JDK 25 output; `(|a)*`, `(|a)+`, `(a*)*`, `(a*?)*`
  agree with the crate's documented results.

## Open items that do not block

- `MacroClass::execute_macro_implementation` gives the macro thread the BUILD thread's file
  label and repository mapping ("PORT" comment, `macro_class.rs:399-418`); Java stores only the
  builder. Not checked which builtins read them in a macro thread.
- Errors of a failed .bzl compile are replayed from BzlLoad (`bzl_load.rs:1085-1115`), not stored
  on the BzlCompile node; a second BzlLoad key for the same file would report them twice.
- `instantiate_macro` panics (ClassCastException) for `name = None`; Java does too.
- The order of `names` given to `PredeclaredModule` (`globals.names()`) decides suggestion ties
  among predeclared names; not compared with Java's predeclared map order.
- F5's crate-side behaviour should be confirmed by the implementer with the recorded rows.
