## Confirmed

- **Install base collector** (`idle_tasks.rs:154-229`): same candidates (32 lowercase hex, a
  directory, not our own), exclusive `try_get` on `<name>.lock` first, back off when the lock is
  held, when the directory is gone or younger than the maximum age, rename to `<uuid>.deleted`,
  delete the lock file, then delete the tree; `*.deleted` leftovers are deleted. Default-on
  (`install_base_gc_max_age`), as Java. The root is the parent of the install base
  (`<output_user_root>/install`), so output bases are not candidates. Blaze's client takes the
  shared lock and updates the mtime (`blaze.rs:243-268, 2309`).
- **Action cache collector**: runs only if a command loaded the cache; opens the cache from disk
  (Blaze loads it per command, so no in-memory copy can be overwritten) and calls `trim` with
  `threshold / 100` and the maximum age.
- **Disk cache collector**: policy (`mtime`, then path; size excess, then age cutoff), the
  re-stat before each delete and the exclusive `gc/lock` match DiskCacheGarbageCollector.java
  :85-110, :184-320. `create` returns nothing without a size or age limit.
- **Binary identity against blaze.cc**: Bazel logs "Killing running server because it is using
  another version of ..." at INFO (client log only), kills, sets `NEW_VERSION` (blaze.cc
  :1161-1167); the startup-options warning belongs to `KillRunningServerIfDifferentStartupOptions`
  (:1090) and is not printed. The Rust addition does the same before the symlink test. Two
  clients with different binaries on one output base: each holds the output-base lock from
  `acquire_locks` (`blaze.rs:2890`) through connect, kill and start, so they alternate (one
  restart per command, as two Bazel versions do); neither can kill a server while the other's
  command runs. A missing or unreadable record counts as different (kill), an unreadable own
  executable disables the check and removes the record.
- **`info`**: `prettyPrintBytes` thresholds and truncation; heap items per D15 as amended;
  `gc-count` `0`, `gc-time` `0ms`; `starlark-semantics` prints `StarlarkSemantics{k=v, ...}` in
  `TreeMap` order of the prefixed names, without prefixes, values by `String.valueOf`;
  `build-language`: rule and attribute order, the fields set, the default-value rule, the error
  message "Failed to load Starlark builtins".
- **Injected panic**: compiled only under `debug_assertions`; a release build ignores the variable.
- **`local_resources`**: the memory limit of the process's own cgroup only, with the oracle
  figures quoted in the code.

## Findings

### S1

### S2

**Q1. The cached MD5 can be stale, and then a server started by another binary is reused.**

- Rust: `binary_identity.rs:38-48` reads the digest from `<install_base>/blaze_binary_md5/<size>-<mtime>`
  and trusts it. The identity (`:68-74`) is size, mtime and that digest. A second binary with the
  same size and the same mtime (nanoseconds) as one already cached gets the first one's digest,
  so its identity equals the recorded one and `ensure_correct_running_version` keeps the server.
- Without the cache the digests would differ and the server would be replaced; the cache removes
  the MD5's value in the one case where it decides.
- Input: replace the executable by a different build of the same size with a preserved or fixed
  mtime (`cp -p`, `install -p`, `rsync -t`, an archive or a package build with clamped mtimes),
  then run a command against a live server of the old one.
- Ruling of 2026-11-26: "a rebuilt Blaze binary must not reuse a server started by an older one".
- Masked: a normal `cargo build` changes the mtime.
- Fix expected: key the cache by what a copy cannot forge as well (device, inode and ctime), or
  drop the cache.

**Q2. The identity holds size and mtime, so equal binaries count as different versions.**

- Rust: `binary_identity.rs:68-74`. Two copies of one binary (same MD5) with different mtimes, or
  one binary after `touch`, have different identities; each alternation kills the server.
- Bazel: the install MD5 is content only; the same binary at two paths shares the server.
- Input: a harness that copies the binary without preserving times and uses one output base.
  Effect: a restart and the loss of the kept graph, and the "Starting local ... server" line where
  Bazel prints none.
- Fix expected: the identity is the MD5 alone (size and mtime only key the cache).

**Q3. One unowned frozen handle is not stamped.**

- Rust: `blaze_analysis/src/config/transitions.rs:1003` builds
  `OwnedFrozenValue::new(FrozenHeapRef::default(), implementation)` for a Starlark transition's
  implementation with no `ArenaStamp`. The other two makers of such handles are stamped and
  checked (`starlark_callable.rs:32-66`, `repo_rule.rs:36,53`).
- `build_arena.rs` now says that unowned handles record their generation so that a holder past a
  release "is a crash with a message, not undefined behaviour"; for this handle it is still a
  read of freed memory.
- Masked: the safety comment there names its holders (the arena's memo and values of leased
  evaluators), and I found no holder outside them; I did not trace every cache of transitions.
- Fix expected: stamp the transition's handle and check it where the implementation is called.
  (The file is outside this review's diff; the task asked whether every unowned handle is
  stamped.)

**Q4. The disk cache collection cannot be interrupted.**

- Rust: `DiskCacheGarbageCollector::run` (`disk_cache_garbage_collector.rs:304-340`) returns
  `io::Result` and never tests the interrupt; `DiskCacheGcIdleTask.run` (`idle_tasks.rs:468-472`)
  can only report failure. The scan and the deletes run on one thread.
- Java: `run()` throws `InterruptedException` from `awaitQuiescence(true)`
  (DiskCacheGarbageCollector.java:184-232, :313); `IdleTaskManager.busy` interrupts the tasks when
  a command arrives.
- Input: `--disk_cache=... --experimental_disk_cache_gc_max_size=...` with a large cache, then a
  command during the idle collection: Blaze's command waits for the whole collection
  (`idle_task_manager.rs:180-184` joins), Bazel's starts at once and the task reports
  "interrupted".
- Masked: collection is off by default; the difference is latency and the task's status.
- Fix expected: test `thread_interrupt::interrupted()` per directory and per delete and return
  the interruption.

### S3

- `RepoContentsCacheGcIdleTask` skips the collection while this server holds the cache's shared
  lock (`idle_tasks.rs:432-446`); a server that keeps its graph never collects. Declared; it
  deletes less, not more.
- `[Idle GC]` and the disk cache statistics are not logged; a failure's cause is logged as
  `toString`, not a stack trace.
- `java-runtime` and `java-vm` print "Unknown runtime"/"Unknown VM" and `unknown` for what the
  `release` file lacks (ruling D15).
- `build-language` uses value equality where Java tests identity with the type's default
  (`build_language.rs:139-150`); equal for the canonical defaults, declared in a `PORT` note.
