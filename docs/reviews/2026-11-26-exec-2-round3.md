### E2-9

- `build.rs:1651-1711` (at e476a59) walks `root_keys`, which is the configured-target keys then
  the aspect keys (`build.rs:2081-2112`), and appends the non-`BuildDriverKey` values (the
  workspace status artifacts) last. That is the order of `Iterables.concat(buildDriverCTKeys,
  buildDriverAspectKeys, Artifact.keys(workspaceStatusArtifacts))`
  (`SkyframeExecutor.java:2518`), which `ParallelEvaluator.constructResult` (`:511`) iterates
  when it fills the result map.
- A skipped key is placed at its root position with its own hash
  (`BuildDriverFunction.java:292` returns a value for it). A key with no value in Java (analysis
  error, failed compatibility check, execution error) is left out, as `constructResult` leaves it
  out.
- `build_driver_keys` and `build_driver_aspect_keys` return de-duplicated sets, as Java's
  `ImmutableSet`s, so no root is counted twice.
- The fixer's 15 oracle orders equal the 15 `blaze-w3` orders (`e29-oracle.txt`, `e29-blaze.txt`,
  compared again by me).
- Not covered by any case: a skipped target that is not the last root. Position only matters
  inside one bucket, and the code places it by root order, so I see no gap.

### E2-11

- Which errors print: every scanner driver of the JDK catches `MalformedByteSequenceException`
  and reports it through the five-argument `reportError` (`XMLDocumentScannerImpl.java:795`,
  `:1029`, `:1214`, `:1489`; `XMLDocumentFragmentScannerImpl.java:3110`), so the line is printed
  wherever the scanner is when the reader fails. Measured: in the prolog, in a comment, in an
  attribute value, in text, right after `<`.
- Messages: `utf8_reader_error` (`xml_stream_reader.rs:109-165`) follows the branches of
  `UTF8Reader.read` one for one (2-, 3- and 4-byte leads, `Expected` at the end of input,
  `Invalid` otherwise, the surrogate message last, `Invalid byte 1 of 1-byte` for the rest). The
  ASCII and odd-byte UTF-16 messages equal the measured ones.
- When: the line is printed once, when `next()` returns the reader's error, before the parse
  fails. A scanner error found before the reader error prints nothing in both
  (`prolog_bad_then_scanerr`); an eager ASCII error behind a scanner error prints in both
  (`ascii_scanerr_then_bad`). No caller of `char_at` drops an error, so the printed text is always
  the reader's message.
- Stream and place: `blaze_events::io::system_err_println` is the patched `System.err`; the
  parser is called from the same place as Java's (`StandaloneTestStrategy.java:885`). The fixer's
  oracle and Blaze runs print the same two lines.

### E2-10

- Depth, attribute count (namespace declarations excluded, as the JDK's `fAttributes` excludes
  them with namespace binding on) and name length per part match `checkDepth`,
  `XMLNSDocumentScannerImpl.java:249` and `XMLEntityScanner.java:848-891`. My
  `depth_100_empty`/`depth_101_empty`, `dup_xmlns_attrs_200`, `prefixed_attrs_201` agree.
- Chunk approximation (`eager_chunk_start`, marked `PORT`). It only matters for a US-ASCII or
  UTF-16 document with a non-ASCII byte (or an odd last byte) **after** the end tag of the
  top-level element; a bad byte before that is rejected and printed by both.
  - 29 ASCII and 31 UTF-16 documents with the bad byte placed around the 8192-byte and 4096-unit
    boundaries: the first boundary is where the code puts it (declaration end + 8192 bytes;
    + 4096 units), and 59 of 60 agree.
  - One differs: `asciib_16400_16424` (root ends at byte 16,400, bad byte at 16,424). Java
    accepts, Blaze rejects: Java's second load started earlier than 41 + 2 x 8192 because a token
    spanned the first boundary. The reverse direction follows from the same drift (not measured).
  - So on documents above 8 KB the two can differ in both directions, but only when a chunk
    boundary of one model, and not of the other, falls between the end tag and the bad byte.
    For garbage right after the end tag that is a window of a few dozen bytes per 8 KB chunk.
    Accepted as a declared approximation; masked for every known writer.

## New findings

### S2

**E2-13. A malformed byte inside the XML declaration: Bazel prints the `[Fatal Error]` line,
Blaze prints nothing.**

- Rust: `decode` (`xml_stream_reader.rs:1040-1047`) parses the declaration from a Latin-1 view
  of the bytes before decoding; a declaration that does not parse returns the error from
  `XmlStreamReader::new`, which never prints. `next_event` (`:271`) also parses it from
  `self.chars` without `char_at`.
- Java: the declaration is scanned through the UTF-8 reader like the rest
  (`XMLDocumentScannerImpl.XMLDeclDriver`, catch at `:795`), so the reader's error is printed.
- Measured on the oracle's JDK, all print `[Fatal Error] :-1:-1: Invalid byte 1 of 1-byte UTF-8
  sequence.` (or the message named): `decl_trunc_bad` (`<?xml version="1.0"\xff`),
  `decl_inside_bad`, `decl_ver_bad`, `decl_enc_bad`, `ascii_decl_bad` (`Invalid byte 2 of 3-byte
  UTF-8 sequence.`: the UTF-8 reader's message although the declaration says US-ASCII),
  `ascii_decl_trunc` (`Expected byte 2 of 3-byte UTF-8 sequence.`). Blaze, as read: no line for
  any of the six. Both drop the test cases.
- Masked: no writer emits a corrupt declaration. Fix: scan the declaration through the same
  lazy UTF-8 error path, with these six documents as cases.

**E2-14. The name limit also applies to a namespace URI; Blaze does not check it.**

- Java: `XMLNSDocumentScannerImpl.java:457` (`tmpStr.length > fXMLNameLimit` for a namespace
  declaration) and `XMLEntityScanner.java:1171` (`isNSURI`).
- Rust: `scan_attribute_value` has no limit.
- Measured: `nsuri_1000` passes, `nsuri_1001` (`xmlns:p="` + 1,001 characters) and
  `default_nsuri_1001` are `XMLStreamException`s. Blaze accepts both and keeps the test cases.
- Masked: no real namespace URI is that long. Fix: `check_name_limit` on the value of a
  namespace declaration.
