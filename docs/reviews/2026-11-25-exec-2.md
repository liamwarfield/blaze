## Findings

### S1

**E2-1 (blocking). Exclusive tests run in another order than Bazel when the main evaluation has
3, 6, 12, 24, 48, ... results.**

- Rust: `crates/blaze_runtime/src/commands/exclusive_test_order.rs:188-189`
  (`let ft = (size as f32 / 0.75f32) + 1.0f32; table_size_for(ft as usize)`), used by
  `crates/blaze_runtime/src/commands/build.rs:1604`.
- Java: `SkyframeBuildView.java:760` `getExclusiveTests(mainEvaluationResult)` iterates
  `EvaluationResult.values()`; the map is the copy made by `EvaluationResult.Builder.mergeFrom`
  (`skyframe/EvaluationResult.java:198`, `result.putAll(...)`) in
  `AbstractInMemoryMemoizingEvaluator.evaluate`. `HashMap.putMapEntries` of the oracle's JDK
  (25.0.2, `embedded_tools/jdk/release`) pre-sizes with
  `tableSizeFor((int) Math.ceil(s / 0.75))`. The Rust formula is the one of JDK 18 and older.
- Measured on the oracle's embedded JDK and on the system JDK 25.0.5 with a reflection probe
  (`~/.cache/blaze/work/review-exec-2/jdkprobe/Probe.java`): `putAll` into an empty `HashMap`
  gives a table of 4, 8, 16, 32, 64, 128 for 3, 6, 12, 24, 48, 96 entries; the Rust formula
  gives 8, 16, 32, 64, 128, 256. For every other size both agree.
- Input: any `test` of exactly two top-level targets (three results: two `BuildDriverKey`s and
  the workspace status action), or five, or eleven. With the hash codes recorded in the module's
  own test (jdb, probe workspace) and `BuildDriverKey` hashes derived from them:
  `test //blaze_tests_probe:excl_b //blaze_tests_probe:excl_c` with both tests exclusive runs
  `excl_c` then `excl_b` in Bazel (table of 4: buckets 0 and 2) and `excl_b` then `excl_c` in
  Blaze (table of 8: buckets 2 and 4). Over the names `excl_a` to `excl_z` in that package, 148
  of 650 ordered pairs differ. The example is computed, not run (suite active).
- Why the port's own check did not see it: the unit test `merge_from_presizes_the_table`
  (line 221) and the jdb observation use four entries, where both formulas give a table of 8.
  The rest of the reproduction is derived from the real hash functions (`String`, `Label`,
  `PackageIdentifier`, `RepositoryName`, `ConfiguredTargetKey.computeHashCode`, the
  `TopLevelArtifactContext` record, `Objects.hash`), not fitted; I checked each against the Java.
- Fix expected: `tableSizeFor(ceil(size / 0.75))` (in `f64`), and oracle cases with 2, 5 and 11
  top-level targets whose order distinguishes the two table sizes.

**E2-2 (blocking). A worker I/O error prints Rust's error text, not Java's.**

- Rust: `crates/blaze_exec/src/worker/error_message.rs:56-63` `JavaException::from_io_error`
  uses `e.to_string()` for an `io::Error` that is not a wrapped `JavaException`. A raw OS error
  prints as `Broken pipe (os error 32)`.
- Java: the exception's `getMessage()` is `strerror(errno)` alone (`Broken pipe`), printed by
  `ErrorMessage.Builder.build` (`ErrorMessage.java:110-113`). Blaze already has the right
  function for it: `blaze_shell::java_process::java_io_message`.
- Input: a worker that exits at startup while Bazel writes a request larger than the pipe
  buffer (a few hundred inputs), or that dies between validation and the write.
  `WorkerSpawnRunner.executeRequest` (`WorkerSpawnRunner.java:557-568`) reports
  `Worker process quit or closed its stdin stream when we tried to send a WorkRequest:` with
  `java.io.IOException: Broken pipe` in the exception details; Blaze prints
  `java.io.IOException: Broken pipe (os error 32)`. The same function feeds
  `IOException while preparing the execution environment of a worker:`,
  `IOException while finishing worker execution:`, `IOException during worker execution:` and
  the unreadable-log text.
- Fix expected: map raw OS errors through `java_io_message` in `from_io_error`; an oracle case
  for the broken-pipe path.

**E2-3 (blocking). A valid `test.xml` that is not UTF-8 loses its test cases.**

- Rust: `crates/blaze_exec/src/exec/test_xml_output_parser.rs:108-119`. `quick-xml` 0.38.4 is
  built without its `encoding` feature (`crates/blaze_exec/Cargo.toml:35`; `Cargo.lock` lists
  only `memchr`), so names and attribute values are decoded with `str::from_utf8` whatever the
  XML declaration says.
- Java: `TestXmlOutputParser.java:54` uses the JDK's StAX reader, which honours the declared
  encoding and byte order marks.
- Input: `<?xml version="1.0" encoding="ISO-8859-1"?><testsuites><testsuite name="s"><testcase
  name="t\xE9st" time="1.5"/></testsuite></testsuites>`. Java returns the tree; Blaze fails on
  the attribute and `TestStrategy.parse_test_result` returns `None`. A UTF-16 file fails the same
  way. Visible in `--test_summary=detailed` and in the cached `TestResultData`.
- Fix expected: decode by the document's encoding (the `encoding` feature and
  `decode_and_unescape_value`, or transcode before parsing), with a Latin-1 and a UTF-16 case.
  See E2-5 for the opposite direction.

### S2

**E2-4. The `HashMap` replay for `unused_inputs_list` is wrong for tree bins, and its comment
says otherwise.** `crates/blaze_exec/src/analysis/actions/spawn_action.rs:404-407` states that a
treeified bin iterates in insertion order unless split by a later resize. In `java.util.HashMap`
`treeify` ends with `moveRootToFront`, and `putTreeVal` links a new node after its parent, so a
treeified bin almost never iterates in insertion order. Java: `StarlarkAction.java:420-441`
(`usedInputsByMappedPath.values()`). Masked: needs nine mapped exec paths in one bucket of a
table of 64 or more. The rest of the replay (spread, resize at 3/4, the early resize of
`treeifyBin` below 64 buckets, removal) matches the JDK for all inputs. The same gap is declared
in `exclusive_test_order.rs:176-177`; that function also omits the early `treeifyBin` resize of
the first map. Fix: port `TreeNode` ordering or fail loudly when a bin would be treeified.

**E2-5. The test.xml parser accepts documents StAX rejects.** `quick-xml` does not check
character validity (a raw `0x1B` in `system-out`), whether an entity referenced in text is
declared (the reader reports it as a `GeneralRef` event, which the port ignores), or whether a
namespace prefix is bound; Java throws `XMLStreamException` and Bazel drops the details
(`TestXmlOutputParser.java:71`), Blaze keeps them. Attribute values are also not
whitespace-normalised. Input: `<testsuites><testsuite name="s"><testcase name="t"><system-out>a
&nbsp; b</system-out></testcase></testsuite></testsuites>`. A dangling `&` is rejected by both.
Masked: Bazel's own `test.xml` generator and gtest escape these.

**E2-6. `lockOutputFiles` gets the action's `FileOutErr` where Java passes `null`.**
`worker_spawn_runner.rs:400-404` and `:481-485` against `WorkerSpawnRunner.java:443` and `:485`.
Masked: only the dynamic strategy reads it, and that is not ported.

**E2-7. Interrupted I/O is turned into `InterruptedException`.**
`worker_spawn_runner.rs:88-95` and `worker.rs` (`From<io::Error> for WorkerError`) map an
interrupted `io::Error` to `Interrupted`; Java keeps `InterruptedIOException` an `IOException`
(wrapped as `IOException during worker execution:` and so on) and restores the flag. Masked:
needs an interrupt during a blocking file operation.

**E2-8. `WorkerFilesHash`: a tool without a digest hashes as an empty digest.**
`worker_files_hash.rs:93-100`; Java puts `null` and `getCombinedHash` then throws
(`WorkerFilesHash.java:54`, a crash). Masked: source directory as a tool with
`BAZEL_TRACK_SOURCE_DIRECTORIES` off.

### S3 (honestly marked; the important ones)

- Java stack frames are absent from every "Exception details" block (`error_message.rs:13`).
  Every worker error that carries an exception differs from Bazel by those lines; the ruling on
  console identity is still open in `docs/STATUS.md`.
- Workers end with the command (no server by default): `Created new ...` appears on every build
  with `--worker_verbose`, and no worker is reused across builds. The stale-worker check after a
  tool change (`WorkerFactory.validateWorker` with the new key's combined hash at borrow,
  `worker_pool.rs:441-457`) is ported correctly but only takes effect inside one process.

  rest of `destroy()` (`singleplex_worker.rs:257`, `worker_multiplexer.rs:399`); they also give
  up on a lock after 100 ms and send SIGKILL after 10 s. Declared as `PORT`.

  worker sandbox, `EnhancedStarlarkAction.discoverInputs` with a shadowed action that discovers
  inputs.
- 81 ignored tests in `tests/worker_unported_tests.rs`, among them all of
  `WorkerSpawnRunnerTest`, `WorkerMultiplexerTest`, `WorkerModuleTest`, `WorkerFilesHashTest`
  and `SandboxedWorkerProxyTest`. The two most concurrent classes of the port have no unit test.
