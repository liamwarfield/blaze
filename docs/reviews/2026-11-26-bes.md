## What was checked and found faithful

- Event loop: the six commands, the ack queue, sequence numbers taken under the lock with the
  enqueue, and `SendLastBuildEvent` as the last sequence number. After a stream failure the
  unacknowledged events go back to the front of the command queue in ascending order with their
  original sequence numbers and serialized bytes, a re-sent last event half-closes again, the
  retry counter resets only when the failed stream had received an ack, and the back-off is
  `initial * 1.6^attempt`.
- Ack errors: a wrong sequence number or an unexpected ack aborts the stream with
  `FAILED_PRECONDITION`, which then ends the upload as `BES_UPLOAD_TIMEOUT_ERROR` ("Not
  retrying"), as in Java.
- Stream completion: the five outcomes of `StreamComplete` (success, unacked, unsent, remote
  error after the last event, retry or give up) carry Java's codes and texts, including the
  doubled `userReadableError` in the final message.
- Lifecycle events: `BuildEnqueued` and `InvocationStarted` before the stream opens,
  `InvocationFinished` and `BuildFinished` after it in the `finally` position, a lifecycle
  failure replacing the stream's result, retries with the same limits.
- The component-stream-finished event, stream ids, keywords on sequence number 1 and on the
  three lifecycle events, `--bes_instance_name` as project id, the `Any` type URL.
- Payload: the uploader sends `as_stream_proto(..).to_byte_array()`; the binary file transport
  writes the same message through the same serializer (`write_delimited_to`).
- Interrupt and cancel: cancelling the close future interrupts the uploader thread once; an
  interrupted loop aborts the open stream with `CANCELLED` and still publishes the two closing
  lifecycle events. A crash goes through `force_shutdown_build_event_streamer`.
- Modes: `wait_for_upload_complete` blocks and turns a failed or timed-out close into the
  `AbruptExitException`; the two asynchronous modes return at once; the next command waits five
  seconds for the close future (the half-close future for `fully_async`, the close future for
  `shutdown`).
- `--keep_backend_connections`: releasing the channel refuses new calls with "Channel shutdown
  invoked" and lets a running stream finish, as `ManagedChannel.shutdown()` does.
- `bidi_streaming`: requests keep their order, no deadline on the stream, dropping the response
  stream cancels the call.
- Profiler sites read: every one is a scope guard around an existing expression or to the end
  of the function. None adds an early return, changes a returned value or encloses a lock taken
  outside it. In `resource_manager.rs` the `?` before `complete_task` matches Java, where
  `completeTask` is skipped when `releaseResources` throws.

## Findings

### S1

- **BES-1. A background upload that outlives `--bes_timeout` but finishes before the next
  command is not reported.**
  Rust `blaze_runtime/src/commands/bep.rs:1346-1364` (`TimedCloseFuture::outcome`) asks the
  close future first and reports `TimedOut` only while it is still pending;
  `CloseFuture::get_outcome` (`blaze_bep/src/buildeventstream/transport.rs:135`) returns `Done`
  whenever the future is done. Java `BuildEventServiceModule.java:585-628`
  (`constructCloseFuturesMapWithTimeouts`) stores `Futures.withTimeout(...)`: once the timeout
  fires that future has failed with `TimeoutException` for good, whatever the upload does later.
  `waitForPreviousInvocation` (`:237-333`) then takes the `ExecutionException` branch.
  Input: `--bes_backend=... --bes_upload_mode=nowait_for_upload_complete --bes_timeout=1s`, a
  backend that closes the stream after 3 s, the next command 10 s later (the same holds for
  `fully_async` and the half-close future).
  Bazel prints `WARNING: The background upload of the Build Event Protocol for the previous
  invocation failed due to a network timeout. Ignoring the failure and starting a new
  invocation...`; Blaze prints nothing.
  Java's `testBeforeSecondCommand_noWaitForUploadComplete_besTimeout_slowFullCloseWarning` covers
  only the case where the upload is still running, which Blaze handles. Not probed (run active).
  Fix: make the timed future latch its timeout (a timer, or the completion time compared with
  the deadline) so a late completion still reads as `TimedOut`, and port the `besTimeout` tests
  of `BazelBuildEventServiceModuleTest` with a case for the late completion.

### S2

- **BES-2. The cached client is cleared only by commands that stream build events.**
  Rust `bep.rs:2778` calls `clear_bes_client` from the BEP support's `after_command`. Java
  `BuildEventServiceModule.afterCommand` (`:662-687`) clears it after every command whose
  `--keep_backend_connections` is false. Input: `build --bes_backend=X
  --keep_backend_connections`, then `info`, then the same build. Java opens a new channel for
  the third command, Blaze reuses the first. Masked: no output differs unless the kept
  connection has gone bad. Fix: clear in the module's `afterCommand` for every command.
- **BES-3. Waiting for file uploads cannot be interrupted, and remote uploads are not waited
  for.** Rust `uploader.rs:878-889` (declared `PORT`). Java `waitForUploads` (`:684`) blocks in
  interruptible `get()`s, so cancelling the close future (timeout, next command) ends a hung
  upload wait. In Blaze the uploader thread stays blocked until the upload returns. Masked
  unless an upload hangs.
- **BES-4. An interrupt that is not a cancel leaves the close future incomplete.**
  Rust `uploader.rs:462-468`: the `check_state!` panics outside `catch_unwind`, so `finish_run`
  never runs. Java's `finally` (`:372-376`) still releases the uploader and completes the
  future. Bug path only.

### S3

- `BazelBuildEventServiceModuleTest` (47 methods) is not ported and has no `#[ignore]` stubs;
  `docs/coverage/java-tests.tsv:146` records 0 matched. These tests cover exactly the three
  upload modes, `--bes_timeout` and the second-command waits in `bep.rs`. AGENTS.md asks for a
  port or an `#[ignore]` with a reason.
- Ported: `AbstractBuildEventServiceTransportTest` 21 of 21, `BuildEventServiceGrpcClientTest`
  3 of 3, `BuildEventServiceProtoUtilTest` 7 of 7. No `unported!` in the crate.

### S4

- `client/mod.rs:326`: `Status.toString()` prints the cause as a source chain where Java prints

  where Java stops at the first failure. `uploader.rs:536`: after a cancel the half-close future
  completes normally where Java's is cancelled.
