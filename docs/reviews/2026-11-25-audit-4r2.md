## Blocking findings, part (a)

### B1 (S1 by reading). `scripts/w4/probe` has F3, F4 and F5 open

The probe gained a lock, provenance lines and a denominator, but it does not use the shared
module and none of its guards.

- **F4.** `Run.exec` (`probe:300-308`) starts the binary with its own `systemd-run --scope`
  through `subprocess.run`: no supervisor, no OOM-kill detection, no timeout (a hung binary
  holds the lock for ever). The results of `shutdown` are dropped.
- **F3.** `record` (`probe:671-676`) writes `ORACLE.txt` with the binary at the oracle's path,
  without the pin check and without any provenance; `read_oracle` (`:532-537`) reuses it with
  no key: nothing ties it to the oracle's sha256, to the scenario's `ws/` or to the
  normaliser that wrote it. `Run.__init__` (`:283`) takes `$BLAZE` unchecked, so the oracle as
  the binary under test scores N of N.
- **F5.** There is no selftest. Nothing proves the lock, the refusal of unlocked probes or the
  three views.
- **Classes and exit rule.** A step whose exit code and text are equal is MATCH whatever the
  exit code (`:513`); there is no declared table and no BOTH-FAILED. `recount` returns 0
  whatever it counts (`:645`), and its provenance line prints the repository's present HEAD
  beside the counts of an old binary (`provenance_lines`, `:266-274`): my recount of
  `ef6f0b8e9fb1` printed `repository 70f2eb4…` for transcripts whose headers say `b101579`.
- Fix: run through `cc.run`, check the pin on `record` and store the oracle's sha256, the tool
  sha256 and the digest of `ws/` and `COMMANDS` beside `ORACLE.txt`; refuse on mismatch;
  refuse the oracle as `$BLAZE`; a selftest on fake binaries; `recount` never exits 0.

### B2 (S1 by reading, not observed). `textproto run` rewrites a directory under its old provenance

- `cmd_run` (`textproto/compare:248-320`) writes the step outputs first and `exit_codes.json`,
  `binary.txt` and `provenance.json` last, and removes none of them at the start. A run with a
  Blaze binary into a directory the oracle recorded, interrupted before the end, leaves Blaze's
  files under the oracle's provenance and the old exit codes. `check` then reports Blaze's
  printer against Blaze's own text as oracle evidence, and `bep-e2e` accepts the directory as
  the reference. This is the "key not removed before the outputs are rewritten" item of F3.
- `provenance.json` holds no digest of the files it describes, so a later change is not seen.
- Fix: remove the three files before the first step; store the files' digests in
  `provenance.json` and check them in `check` and `bep-e2e` (as `bytes/run` and
  `bytes/compare` do).

### B3 (S2). The gap rule `b1_found` blames the warm server for a difference of Blaze's

- `compare_common.py:508-509` removes every `INFO: Found N targets...` line as a B1 gap, with
  the reason "the warm server reports Found at another point of the command".
- Java: with merged analysis and execution the line is printed after
  `runAnalysisAndExecutionPhase` returns (`buildtool/AnalysisAndExecutionPhaseRunner.java:123-141`),
  and that call throws `BuildFailedException` when an action fails (`:170`). A failed build
  prints no `Found` line whatever the server holds. Round 4 said the same line was not
  explained by B1.
- Stored evidence, `~/.cache/blaze/run-compare/audit4-run`, `brotli/build-fails`: the oracle
  prints no `Found` line, Blaze prints `INFO: Found 1 target...` after `Analyzed`. The tool
  reports KNOWN-GAP `b1_found`; the true class is DIFFERENT. So "13 known gap, 5 different" is
  12 and 6. The same rule gives `stderr:fail.stderr` KNOWN-GAP in the stored `bytes` run.
- Because the line is removed on both sides, its position is never compared: equal `Found`
  lines at different points are IDENTICAL. No stored row is wrong for that reason (I compared
  the positions in all 20 cases of `audit4-run`).
- The rule is used by `run`, `java`, `config`, `tests`, `query`, `bep-matrix`,
  `bytes/compare` and `textproto bep-e2e`.
- Fix: delete the rule (the line is compared in place). If a position difference is ever shown
  to come from the warm server, declare it per case with the evidence.

### B4 (S2). Reduced or deviating comparisons counted as IDENTICAL

The module defines IDENTICAL-REDUCED and KNOWN-GAP for these; three tools do not use them.

- `textproto check`: the `bep` row is IDENTICAL when the records are equal only as a sorted
  list (`textproto/compare:150-157`, `:397-398`), and `bep-text-vs-json` compares sorted lists
  (`:408-421`). Stored `r4/textproto-oracle-brotli.log`: "record order differs at 21
  positions" and "order differs at 21 positions" above two IDENTICAL rows; the footer's "3
  identical, 1 identical-reduced" is 1 and 3.
- `bep-matrix`: `payloads` keeps four counters of `buildMetrics` and drops the rest
  (`bep-matrix:430-437`) as a "volatile mask". The referee compares the rest of that message
  (`scripts/oracle/surfaces.py:514-515` with its allow list). The reduction is in `help`, not
  in the report, and the class stays IDENTICAL.
- `workers`: the rule `java_frames` (`workers/compare:142-144`) removes the oracle's stack
  frames, "which Blaze cannot print", as a volatile rule. That is a deviation of Blaze, not a
  volatile line; a case that differs only there is IDENTICAL.
- Fix: IDENTICAL-REDUCED when the order was ignored or the mask applied to a field that is not
  volatile; `kind="gap"` for `java_frames`.

### B5 (S1). `interp-diff` reports packages IDENTICAL when a query did not run to its end

- `judge_packages` (`interp-diff:166-196`) derives every package row from stderr alone. A
  package the oracle accepts without printing is IDENTICAL "accepted" when Blaze's stderr says
  nothing about it, which is also what a Blaze that died before evaluating it leaves.
- The tool's own selftest shows it: scenario `both-sigpipe` (both queries killed by SIGPIPE)
  ends "both_failed 1, identical 4", two of them package rows; `blaze-sigpipe` the same with
  the termination row DIFFERENT. `cc.itemised()` (`compare_common.py:1158-1166`) relaxes the
  two failure scenarios to "a BOTH-FAILED row exists" so that this passes.
- The run exits 1 in these cases, but the footer's count of identical packages is not a count
  of packages both sides evaluated.
- Fix: when either termination is not a normal exit with code 0 or 3, every package row is
  SKIPPED. Keep `itemised()` for `bytes/compare`, whose items are files both sides wrote.

## (b) `ut_common.py`, commit `7e4c3bd`: PASS

- The mutual exclusion is the `flock` on `outer.lock` (`_Lock.acquire`, `:289-313`), held by
  `run` from before `wait_for_unlocked_runs` to the end of the outer job and by `prepare` for
  all of its work. The commit does not touch it. Two lock-aware runs cannot overlap.
- `unlocked_runs` is a second check for processes that do not take the lock. The commit
  narrows one of its three classes: a process counts as a harness script only when the script
  is its `argv[0]`, or `argv[1]` of a Python interpreter (`:412-415`). A wrapper (`timeout`,
  `env`, `bash -c`, an editor with the file open) no longer counts. The real harness process
  under a wrapper is its own process and still counts; it registers before anything else, so
  a waiting run is never taken for an unlocked one. The deadlock of 2026-11-19 cannot recur
  through a wrapper.
- The other two classes are unchanged and still cover a run whose `run` process died while its
  unit lived: `run _inner` (started as `[sys.executable, <script>, "_inner", …]`, so the
  script is `argv[1]`) and an outer Bazel client on the outer root.
- Live check: with the suite running, the heuristic sees the registered run (pid 37993), does
  not count its `bash -c` wrapper, and finds the outer Bazel client, as designed for a caller
  that does not hold the lock.
- Open, not blocking:
  - **U1 (S3).** A harness started as `python3 -B <script>` (an option before the script) is
    no longer seen, since `argv[1]` is the option. Every version since `99a74d0` registers and
    locks, so this only matters for a copy of the harness older than the lock (an old
    worktree). Accept `argv[k]` after interpreter options.
  - **U2 (S3).** `registered` is a set of pid numbers; a file left by a killed process hides
    an unrelated process that reuses the pid until the next `register_client` cleans it.

## (c) `scripts/server`: STOP

These tools do not use `compare_common.py`. Their own design is sound in three points: the
oracle is accepted by its pinned sha256 only; the tool itself runs in a memory-capped unit
under `unit-supervisor` and takes each client's true wait status (`Status`), so a signal death
is never an exit 0; servers are killed only when the pid's command line names the tool's own
output root. Blocking:

- **SV-1 (S1, the F1 criterion).** `seq` compares stderr through an include filter and as a
  multiset: `views` (`seq:461-472`) keeps the referee's `stderr_summary` lines plus lines with
  six prefixes; every other line and the order are not compared. A step is IDENTICAL on that.
- **SV-2 (S2).** Equal failures are not declared and do not fail a run. `seq run` exits 0 when
  no step is DIFFERENT or NOT-RUN (`seq:689`), `interop-client` and `interop-server` the same
  (`interop-client:859-860`, `interop-server:658-659`); a run in which every step fails the
  same way on both sides exits 0. `seq recompare` uses the strict rule (`seq:738-739`), so the
  two disagree on the same data. `interop-client` calls a case IDENTICAL when none of its
  steps is DIFFERENT, same-failure steps included, and a case with no step would be IDENTICAL.
- **SV-3 (S2).** An OOM kill is a note, not a class: `seq` appends "OOM KILL in the unit" to a
  row that stays IDENTICAL (`seq:519-521`); `interop-client`, `interop-server` and `soak` do
  not read the counter, though `common.py` says it is read before and after each step.
- **SV-4 (S2, F3).** The binary under test is not refused when it is the oracle (`seq:608-615`,
  `interop-client:767`, `interop-server:582`); `soak --oracle` takes any binary. `seq`'s
  reference cache has a completeness marker but no digest of its files.
- **SV-5 (S2, F5).** No tool of `scripts/server` has a selftest.
- Not blocking: **SV-6 (S2)** `interop-client` `EXPECTED_DEVIATIONS` waives every differing
  step of a whole case in one mode, not a named text. **SV-7 (S3)** `soak` judges nothing and
  its exit status says nothing about the commands; `ut-wrapper` is a maker of a wrapper and
  compares nothing; both are acceptable as such.
- Fix: whole stderr with named exclusion rules in `seq`; a declared table of expected failures
  per step and exit 0 only when every step is IDENTICAL or declared; an OOM kill makes the
  step DIFFERENT or SAME-FAILURE, never IDENTICAL; refuse the oracle as the binary under test
  outside `--control`; selftests on fake binaries. Moving the three tools onto
  `compare_common.py` gives all of this.
