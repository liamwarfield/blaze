# Review: incremental builds, package I3 (a persistent server keeps and invalidates its graph)

Reviewer role: read-only reviewer (Fable 5.2), 2026-11-26. Commit under review: **ce81d5a**
(checkpoint 39), read from `git archive ce81d5a` (the working tree has later edits; not read).
`J:` = `~/.cache/blaze/src/bazel-9.3.2/src/main/java/com/google/devtools/build/lib/`. No Cargo.
**No probe was run**: the unit `root-suite-5f68157` was active for the whole review. Every

## Verdict

**STOP** at ce81d5a. S1 2 (both blocking), S2 5, S3 4, S4 2.

Blocking:

- **S1-1** With a remote or disk cache, a kept graph keeps `ACTION_EXECUTION` and completion
  nodes that Java invalidates: the previous command's `RemoteOutputChecker` is not carried over,
  `maybeInvalidateSkyframeValues` is never called, and the "materialized as top-level output"
  record is not ported. A deleted output is not restored and the build reports success.
- **S1-2** `SkyframeExecutor.setSaltAndDeleteActionsIfChanged` is not ported: after a change of
  `--remote_default_exec_properties` every action node is kept and nothing is re-executed.

Both need remote options. For local builds (no remote cache, no disk cache, no remote
execution, `--watchfs` off) I found no path that keeps a stale node.

## Findings

### S1

**S1-1. Remote output metadata: three Java invalidations of a kept graph are missing.**

- `blaze_remote/src/remote_module.rs:655-661`: the checker is built with
  `RemoteOutputChecker::new`, no last checker, and the comment says why:
  "`maybeInvalidateSkyframeValues` compares with the checker of the previous command of the
  server; one command per process here". Java: `J:remote/RemoteModule.java:569-574` passes
  `lastRemoteOutputChecker` and calls `maybeInvalidateSkyframeValues(evaluator)`.
  `remote_output_checker.rs:590` (`maybe_invalidate_skyframe_values`) has no caller.
- `blaze_sky_exec/src/output_checker.rs:41-43,176-185` and
  `blaze_remote/src/remote_important_output_handler.rs:105-112`:
  `wasMaterializedAsToplevelOutput` is not ported, "such an output is never treated as deleted
  after materialization". Java: `J:skyframe/FilesystemValueChecker.java:539-553`,
  `J:remote/RemoteImportantOutputHandler.java:178`.
- `incremental.rs:699-730` runs the output check at executor creation, before analysis, so the
  current checker knows no top-level output; Java's protection at that point is exactly the two
  mechanisms above (`J:remote/RemoteOutputChecker.java:353-358`).

Sequence (remote or disk cache, default `--remote_download_outputs=toplevel`, one server):

1. `build //app` (depends on `//lib`; `lib.out` is a cache hit, metadata remote, not downloaded).
2. `build //lib`: the new completion node downloads `lib.out`.
3. `rm bazel-bin/lib.out`; `build //lib`.

Java: the last checker says the file was to be downloaded, the action is dirtied, re-run and the
file restored. Blaze: `should_trust_metadata` is true (no last checker, empty current checker),
the action and its completion node stay clean, the build succeeds and `lib.out` is missing.
Second sequence: `build --remote_download_minimal //x`, then `build
--remote_download_toplevel //x`. Java deletes `TARGET_COMPLETION` / `ASPECT_COMPLETION`; Blaze
keeps them and downloads nothing.

`i3-result.md` ("Not ported" item 3) says "remote outputs missing locally are always treated as
modified (re-evaluated; never stale)". The code does not do that when the output service has a
`RemoteOutputChecker`.

Fix expected: keep the last checker on the server (as Java's module field), call
`maybe_invalidate_skyframe_values`, port the materialization record; or, until then, fail safe:
treat every missing output with remote metadata as dirty and delete the completion nodes at each
command with a remote cache.

**S1-2. `setSaltAndDeleteActionsIfChanged` is not ported.**

- Java: `J:buildtool/ExecutionTool.java:332`, `J:skyframe/SkyframeExecutor.java:2066-2073`
  (`lastExecutionSalt`; a change deletes every `ACTION_EXECUTION` node);
  salt = remote cache enabled + default exec properties (`J:remote/RemoteModule.java:1312-1332`).
- Rust: the salt reaches only the action cache key (`skyframe_action_executor.rs:640,2160`,
  `build_remote.rs:663`). No `last_execution_salt`, no deletion; the only deletions of the
  runtime are in `incremental.rs`, `build_remote.rs:147` and `vendor.rs:508`. Not in the change
  list of `i3-result.md`.

Sequence: `build --remote_executor=E --remote_default_exec_properties=image=a //x`, then the same
with `image=b`. Java re-executes every action. Blaze: outputs are intact, no node is dirty,
0 actions run; the outputs of the old properties are reported up to date. (Remote cache switched
off after a build with it is caught by the output check with `TrustLocalOnly`, when
`--experimental_check_output_files` is on.)

Fix expected: port the method where `prepare_execution` configures the executor, with the last
salt in `SkyframeIncrementalState`.

### S2

**S2-1. Conflict-finding nodes are never deleted, and their function reads a cell.**
`skyframe_executor.rs:916-919` ("A command analyzes once, so they are never read with other
conflicts"), `skyframe_build_view.rs:402`, `action_lookup_conflict_finding_function.rs:235`
(reads `ActionConflictsCell`, a new empty cell per executor). Java deletes both node kinds after
each use (`J:skyframe/SkyframeExecutor.java:2560-2561,2612-2614`) because their input is
per build. With a kept graph a verdict of an earlier build ("no conflict" or a cached
`ActionConflictException`) is read again for a target whose configured target did not change,
whenever two builds on one server have different conflict sets (`--keep_going`). I did not build
a sequence I am sure of (which of two conflicting actions Java marks depends on registration
order), so it is not S1. Fix: port the two deletions. The conflict check itself always runs
(`should_check_for_conflicts` is true whenever the graph has a rule target): safe.

**S2-2. `--watchfs` is live at ce81d5a; the result document says it is not ported.**
`blaze_runtime/src/bazel_modules.rs:457` registers `LocalDiffAwarenessFactory`, and
`incremental.rs:774-812` takes Java's complete-diff path (only the named files are checked).
`i3-result.md` (change sources, "Not ported" item 1) and the comment at `incremental.rs:733-739`
say every root is always checked. This is the path where a missed event is a stale node, it has
no oracle evidence at this commit (`scripts/incremental/watchfs` is not in the commit), and I
read it for structure only: `collectChanges`, the inotify masks and event mapping, the blocking
poll loop and the overflow handling match the Java and the JDK; I found no stale path, and did
not verify `get_diff_with_inferred_ancestors` line by line. Expected: its own review with
oracle runs before `--watchfs` is accepted; correct the two texts.

**S2-3. `reset_evaluator` during a command is undone.** `incremental.rs:429-441` drops
`inner.kept`, which is `None` while an executor holds the graph; `put_back`
(`incremental.rs:1137-1161`) then keeps that graph. Caller during a command:
`build_remote.rs:321-330` (`invalidate_repo_directories`, where Java deletes the
`REPOSITORY_DIRECTORY` nodes). Fix: a reset must also make the next `put_back` drop the graph.

**S2-4. Server state is not tied to the graph it describes.** A Blaze-only discard
(`LoadingSignature`, a still-referenced evaluator, a failed sync) builds a new graph without
resetting `has_configuration` / `original_configuration_options` (a wrong "discarding analysis
cache" warning at most) or the diff awareness manager. If two executors of one command were
alive at once, the second gets a new graph, `note_new_graph` overwrites `deleted_packages`,
the environments and `main_repo_mapping`, and whichever graph is put back last is kept with the
other's state. Production creates executors one after the other, so this is masked. Fix: a
graph generation in the handle; `put_back` drops a graph that is not the current one.

**S2-5. The randomized test covers little of what can go stale** (section 6).

## 3. Kept or discarded

Java's conditions are all there: `--track_incremental_state`, `--batch` with
`--discard_analysis_cache`, `--nokeep_state_after_build`, `clean`. Blaze adds discards, all on
the safe side: signature change, an evaluator still referenced, an interrupt during the sync, a
stat failure of the diff, executor creation failing after the evaluator was built (the graph is
dropped with the local variable). A panic gives nothing back (`Drop` checks `panicking()`), and
`catch_crash` ends the server (`create_shutdown`), as Java. An interrupt or a failed
no-keep-going evaluation leaves in-flight nodes to the I1 mechanism (not re-reviewed).

## 4. Per-command state

- Events: emitted-event state cleared once per command; the dispatcher's stored events are
  replayed when its graph goes to the command's executor (`dispatcher.rs:846-858`). Transient
  errors invalidated at sync. Not probed.
- Arena: nothing the graph references is freed. A kept graph holds a lease taken in `put_back`
  before the executor's lease drops; `build_evaluator` drops the kept lease only after the new
  executor took its own; `release_build_arena` releases only at zero leases.
- Services, action cache, repository state: dropped with the executor at the end of the command.
- Statics and thread-locals: the implementer's table was not re-derived; I sampled
  `PACKAGE_PROGRESS`, the conflicts cell (S2-1) and the remote statics.

## 6. The randomized test

`stress random`: one binary, server A keeps its graph, server B is `BLAZE_INCREMENTAL=none` with
`clean` before each build; always `build --keep_going //...`; compares exit code, ERROR/WARNING
lines and the files of B's `bazel-bin`. The workspace has genrules, one write-action rule, one
`config_setting`, one local module, one extension repository. It cannot catch: anything both
sides get wrong, counts, INFO output, non-`build` commands, no-keep-going failures, interrupts,
remote state, anything outside `bazel-bin`.

The five edit kinds most likely to hide a stale result that it does not generate:

1. Symlinks: retarget a source symlink, edit its target, swap a file and a directory.
2. A BUILD file added or removed under a directory a parent package globs; `.bazelignore` and
   REPO.bazel edits.
3. Header edits for actions with discovered inputs (no C++ rule in the workspace), including a
   new header earlier on the include path.
4. Other commands and options between builds: `query`, `cquery`, `test`, `fetch`; Starlark
   flags, `--platforms`, `-c`, `--package_path`, `--deleted_packages`, `--repo_env`,
   `--override_repository`, remote and disk cache flags (S1-1 and S1-2 live here).
5. Load graph and module edits: add or remove a `load()`, a transitively loaded `.bzl`,
   MODULE.bazel, the lockfile, files a repository rule reads.

Also absent: tree artifacts and runfiles trees among the tampered outputs.

## The three reported differences

- **platform_mappings, 2 against 11 targets configured**: a count difference. Every use of the
  mapping goes through the `BuildConfigurationKeyValue` node, which depends on `PLATFORM_MAPPING`
  and is pruned only when the resulting key is equal; Java's configured targets depend on the
  mapping directly and are re-run to the same values.
- **3 against 13 targets after an aborted build**: a count difference, given I1's invariant (a
  node is committed only when its function returned; in-flight nodes and their reverse closure
  are deleted). Fewer nodes are in flight in Blaze's engine. Not probed.
- **Empty execution log on a loading failure**: not a kept-graph effect by the code I read; an
  output difference from Bazel (a file where Bazel writes none). Open item for the execution
  log owner.
