### S2-2: can the computed-count detection misfire or miss?

`computed` is incremented once per `compute()` call (`evaluator.rs:1892`); the formatter
reports "did not complete" when one resolver evaluation raised it by more than one
(`transitions_output_formatter_callback.rs:182`).

- Miss: none found. A value the resolver requests that is not done is computed by the request,
  so the count rises by at least two; a restart of the resolver itself counts too.
- Misfire: none found by reading. It needs a key the resolver requests that analysis left out of
  the graph. `DependencyResolver.evaluate` is the code analysis ran for the same key, and the
  two extra requests of `compute` (the target's package, its configuration) are done after
  analysis. The formatter is not `Sync` (`Cell`), and nothing else evaluates during the output
  phase of a cquery, so no foreign `compute()` falls into the window. The implementer's three
  probes (one with a Starlark transition, a rerun, a configuration change) agree.
- It stays an inference from a counter, not Java's mechanism. Residuals, all masked (S2, not
  blocking): (a) when it fires, the nodes it computed stay in the graph and in the statistics,
  where Java computed nothing; (b) a result with neither value nor error is `unported!`
  (`:189`); (c) on an interrupt `resolved_any` is not set, so nodes of earlier targets are not
  deleted for that command.

**P63-1 (blocking). A key-tracking `ctx.var` passed whole to a native records no key.**

- Rust: natives read a dict through `DictRef`, which patch 0063 does not hook:
  `crates/blaze_analysis/src/starlark/util.rs:210` `dict_cast_string_string` and `:256`
  `dict_cast_string_object` (used for `env` at `starlark_action_factory.rs:1034`,

  and the remaining `DictRef::from_value` readers in `blaze_analysis` and `blaze_rules`.
  PATCHES.md lists this as a limitation of 0063; nothing fails loudly and no ruling covers it.
- Java: `Dict.cast` iterates `((Map) x).entrySet()` (`Dict.java:666`), which on an
  `ImmutableKeyTrackingDict` records every key (`Dict.java:829`); `json.encode` reads
  `m.keySet()` (`Json.java:173`, `Dict.java:822`). `RuleContext.java:1170` turns each recorded
  key that is a `--define` into a required fragment.
- Input: a rule whose implementation calls `ctx.actions.run_shell(..., env = ctx.var)` (or
  `expand_template(substitutions = ctx.var)`, or `json.encode(ctx.var)`), then
  `cquery //p:t --define a=b --show_config_fragments=direct`. Bazel lists `--define:a` for the
  target; Blaze does not. `dict(ctx.var)` and `**ctx.var` are right (hooked).
- Fix expected: record all keys where Java's `Dict.cast` and the other `entrySet()`/`keySet()`
  readers are ported (`dict_record_all_keys_accessed(x)` in the two cast helpers and at each
  `DictRef::from_value` of a caller-supplied dict in the Blaze crates), a case per helper in
  `patch_0063_key_tracking_dict` or a Blaze test, and an oracle case with `env = ctx.var`.

### S2

**P63-2. `x == ctx.var` records nothing.** `value.rs` `equals` reads both sides' contents.
Java evaluates `x.equals(y)` = `x.contents.equals(y)`: with the tracking dict on the right, an
immutable `x` (`ImmutableMap.equals`) calls `y.entrySet()` and records every key, and a mutable
`x` (`AbstractMap.equals`) calls `y.get(k)` for its own keys when the sizes are equal. Only
`ctx.var == x` records nothing, which is the one case the patch's test covers. Input:
`{"a": "b"} == ctx.var` in a rule with one make variable. Not blocking (no realistic rule).

**Z-1. The gzip bytes depend on how Blaze was built.** libz-sys builds its bundled stock zlib
when pkg-config finds no system zlib; such a binary writes other bytes than Bazel on a
zlib-ng host and nothing reports it (the response and the decisions entry say so). Expected: a
build-time or start-up check that the linked zlib is the system library. Not blocking.
