# Coverage map: Bazel's Java against Blaze's Rust

A file- and method-level map of how much of Bazel 9.3.2's Java (`src/main/java`) Blaze has ported,
for planning the waves that complete the port (decisions.md, 2026-11-19).

Files here:

- `java-map.tsv`: one row per Java file (3,037): path, package, lines of code, methods, methods
  marked, status, reason, `unported!` sites, owning crate, then extra columns (crate basis,
  `PORT: skipped` comments, ignored tests naming the class, cluster, the rule that set the reason,
  top package).
- `java-methods.tsv.gz`: one row per method or constructor (33,579), with its line range and how it
  is marked (`name`, `line`, `impl`, `type`, `skipped`, or `-`).
- `java-tests.tsv`: one row per Java test class whose production class is PORTED or PARTIAL.
- `markers-unresolved.tsv`: every `// Java:` marker that does not resolve, with its Rust location.
- Generator: `scripts/coverage/java-map` (`help` prints usage). Parser check:
  `scripts/coverage/JavaMethods.java` (javac's own parser).

Every number below is generated except where a section says "by hand". The generated blocks are
rewritten in place by `scripts/coverage/java-map build`; edit the text outside them.

## Method

1. Java parsing. `strip_java` blanks comments, strings, char literals and text blocks while
   keeping offsets. A brace matcher walks each type body. In a body, a header is the text since
   the last `;`, `{` or `}` at that depth, with parenthesised groups skipped (so lambdas and
   annotation arguments do not end a header). A header containing `=` is a field (its braces are
   skipped); one with `class`/`interface`/`enum`/`record NAME(` opens a nested type; one that ends
   in `NAME(...)` plus optional `throws`/`default`/`[]` is a method or constructor (abstract when
   it ends in `;`). Enum constants (up to the first `;`) are skipped. The range of a method runs
   from its first modifier or annotation to its closing brace, as javac reports it. Members of
   anonymous and local classes and of enum-constant bodies belong to their enclosing method and
   are not listed; nor are record accessors the compiler generates.
2. Rust scanning (`crates/`, `third_party` not scanned). Markers: `Java: <path>[:line] [member]`
   and `Java: Class.member` in `//` comments. `unported!("…")` and `unimplemented!("Java: …")`
   calls outside comments (multi-line calls included). `// PORT: skipped, …` comments. `#[test]`
   functions with their `#[ignore = "…"]` reasons.
3. Marker resolution, per marker (table under "Accuracy"): if the marker names a member, the
   method of that name whose class path ends with the marker's class path is marked; if the line
   falls in that method only that overload is marked, otherwise every overload of that name. A
   marker whose name is not a method of the file but whose line falls inside a method marks that
   method. Markers that name a class, field or constant mark no method. Paths that moved since
   the marker was written are resolved by file name when it is unique.
4. Extra credit, so that structural ports are not counted as missing: an abstract method is
   marked (`impl`) when a direct subtype's method of the same name is marked (the Starlark API
   interfaces in `starlarkbuildapi` are ported through their implementations); a parameterless
   abstract accessor of an `@AutoValue`/`@AutoOneOf` class or record whose type a marker names is
   marked (`type`); a method named `Class.method` in a `// PORT: skipped` comment is marked
   (`skipped`).
5. Status: PORTED when more than half of the file's methods are marked and no `unported!` site
   names its class; PARTIAL when some method is marked or any marker, `unported!` site or
   `PORT: skipped` comment names the file; UNTOUCHED otherwise. A file without methods is PORTED
   when a marker names it.
6. Reason (files not PORTED only): the first matching rule of `SCOPE_RULES` in the script (listed
   under "Rules"), then GENERATED_OR_TRIVIAL for `package-info.java` or a file with no method
   body and at most 30 lines of code, else NEEDED. `STARLARK_RUST_DECISION` is a reason class
   added to the six asked for: `net/starlark/java` is replaced by starlark-rust by the user's
   decision, and counting it NEEDED would misstate the remainder.
7. Unported lines of a NEEDED file: all lines of code if UNTOUCHED; if PARTIAL, the lines of code
   inside unmarked methods plus the unmarked share of the lines outside methods.
8. Owning crate: the crate with most markers into the file; else the crate with most markers into
   its package (`package`); else the plan of docs/crates.md and docs/research/06 §5.1 (`plan`).
9. Clusters: `CLUSTER_RULES` in the script, first match wins, for NEEDED files only.
   Dependencies between clusters are import edges (plus same-package references by simple name)
   from a NEEDED file of one cluster to a NEEDED file of another.

### Error of the derived numbers

| source of error | direction | size |
| --- | --- | --- |
| parser | none | 0 differences from javac |
| a name-only marker marks every overload | marked too high | at most 1,615 methods (10.6% of marked methods) |
| ported code without a marker | marked too low | 12 UNTOUCHED NEEDED files (423 lines) have a Rust type of the same name; ports into a differently named type are not detected |
| structural ports (enum variants for `of` factories, nested overrides) | marked too low | seen in 2 of 20 hand-checked files |
| a marked method counts as fully ported | unported lines too low | 152 PARTIAL files with most methods marked have `unported!` sites inside marked code |
| status threshold (more than half marked) | status flips | 293 files (42.7k lines) have 40–60% marked |
| `unported!` attribution by first class name | sites on the wrong file or none | 92 of 812 sites name no Bazel class |

Taken together, the 139k unported lines of NEEDED code are an estimate within about ±15k: the
overload and threshold effects mostly move lines between PORTED and PARTIAL, while missing
markers and partly ported marked methods pull in opposite directions.

### Reading the clusters (by hand)

The dependency column counts edges into files that are themselves not ported, so it shows which
clusters wait for which. The main chains:

1. **skyframe-engine → incremental-evaluation → server-client-protocol.** The engine files left
   (`AbstractParallelEvaluator` 2/20, `SkyFunctionEnvironment` 24/60, `ParallelEvaluatorContext`,
   `ValueWithMetadata`) are what root's rewrite replaced; incremental evaluation (node entries,
   versions, invalidation, diff awareness, `FilesystemValueChecker`, `SequencedSkyframeExecutor`,
   `SkyframeExecutor` 52/250) has 147 edges into them. The persistent server
   (`GrpcServerImpl` 2/29, `BlazeRuntime` 25/82, `BlazeCommandDispatcher`, idle tasks) needs
   incremental evaluation to be worth having. docs/research/08 is planning this chain.
2. **concurrency** (29 files, 2.7k lines: `AbstractQueueVisitor`, `TaskGroup`, `RequestBatcher`,
   `MultiExecutorQueueVisitor`) has no outgoing edges and is imported by the engine, packages,
   execution and serialization. It goes first or is ruled a JVM-structure replacement.
3. **packages-and-loading → symbolic-macros-and-lazy-loading → query-and-genquery.** Macros need
   `PackagePiece` and the macro-instance functions; `genquery`, `SkyQueryEnvironment` (0/102) and
   the query output formatters need packages. `analysis-core` and
   `configuration-and-transitions` depend on packages too (143 and 32 edges).
4. **execution-and-action-graph → action-rewinding, dynamic-execution, workers,
   remote-execution-and-caching.** `SkyframeActionExecutor` (44/89), `BuildTool` (13/56),
   `FileArtifactValue` (57/178) are the shared base.
5. **profiler-and-metrics** (`Profiler` 1/76, `CollectLocalResourceUsage`, critical path,
   `ExecutionGraphModule`) is a leaf used by server, runtime and BEP; Bazel writes
   `command.profile.gz` on every command by default.
6. **remote-analysis-caching-serialization** depends on almost everything and nothing depends on
   it outside itself; it can go last.

Suggested order (each step only needs earlier ones): concurrency, base-libraries, vfs-and-hashing,
invocation-policy-and-options → skyframe-engine → packages-and-loading, symbolic macros →
configuration-and-transitions, analysis-core, native aspects, cpp/python/java rules, coverage →
execution-and-action-graph, sandboxing-and-local-exec, include scanning → workers, dynamic
execution, action rewinding, remote execution and caching → profiler-and-metrics,
build-event-service, runtime-and-ui, commands, query-and-genquery, starlark debugger and docs →
incremental-evaluation → server-client-protocol → remote-analysis-caching-serialization.
